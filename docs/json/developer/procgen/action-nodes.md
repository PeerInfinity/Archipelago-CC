# ActionNodes Substrate

The ActionNodes substrate (id `action_nodes`) is a puzzle played in loops: one region is one node, and a node is one action with a mana cost, stat and resource minimums, results and a limit per loop. Stats and resources reset with every loop; Archipelago items are boosts that apply at once and again at the start of every loop. A world is compiled from a graph document by `compileActionGraph`, with its Archipelago logic derived by an exact one-loop search and the guarantee that every loop not waiting on an item can earn a check proven at compile time. Slice 1 built the headless core: the format, the compiler, the logic, the bot planner and a committed example. Slice 2 made it playable in the browser, in and out of Loop mode: the runtime, the `act` verb with its start gate, the host ledger and the Resources panel ([The runtime](#the-runtime)). Slice 3 added click-to-play on the Region Graph and the Region Map, and the live bot ([The node states and the node card](#the-node-states-and-the-node-card), [The bot planner](#the-bot-planner)). AN-TIME-1 added time windows, a clock and knowledge to the headless core (§ Time windows, the clock and knowledge); the runtime and the panels do not read them yet.

The module is `frontend/modules/actionNodes/`. Nothing in it touches a generator or the maze engine.

## The graph document

One JSON document, kind `action-graph`, schema version 1, validated by `actionGraph.js` (`validateActionGraph`, `assertActionGraph`). Every refusal has a name in `ACTION_GRAPH_REFUSALS`; tests assert the name, never the wording. The field names (`requires`, `results`, `limit`, `after`) are the shared task shape's, so a later pack resolver can produce exactly this document and the compiler does not change.

| Field | Meaning |
|---|---|
| `loop.mana` | A loop's starting pool, before boosts. |
| `stats`, `resources` | `{<id>: {name}}`. Stats only go up; resources go up or down. Both reset with the loop. |
| `boons` | The Archipelago items: `{<id>: {name, count, gives: {stats, resources, mana}}}`. `gives` applies at once when received and at the start of every loop, so a boost resource spent during a loop is back at the next one. |
| `filler` | Optional: the boon id that fills the check locations the boons do not. |
| `start` | The start node's id. |
| `settings` | `xpGainScale` (default 1) and `xpEffect` (default `cost`; `none` on a timed graph), written onto every node's `loop_costs` entry. |
| `clock` | Optional; makes the graph TIMED: `{start: "HH:MM", minutesPerUnit}`, the clock time of a loop's time 0 and the minutes in one unit. Display only. |
| `knowledge` | Optional: `{<id>: {name}}`. A flag is learned by performing a node that teaches it and is kept across loops. An id may not also be a boon id. |
| `nodes.<id>` | `name`, `kind` (`start`, `action`, `check`, `use`, `goal`), `time` (mana per performance, 0 allowed), `requires` (`{stats, resources}` minimums, and `knowledge`: flags that must be known), `results` (`{stats, resources, mana}`, and `learns`: flags it teaches), `limit` (performances per loop, required on every node), `after` (a list of sets: the node is reached this loop when every node of one set is cleared), optional `window` (`{from?, until?}`, below), optional `position`, optional `src`. |
| `provenance` | The content-sets provenance block: `sources` (each `{type, …}`: `game`, `person`, `model`, `authored` or `derived` with that type's fields), `default`, and a per-entry `src` on a node or boon that differs from the default. |

**The per-item starting-mana boost.** A boon's `gives.mana` is the mana that item adds to every loop's starting pool. When a boon does not state it, it is `DEFAULT_MANA_PER_ITEM` (10), the constant the global "every received item adds mana" setting (`gameState.manaPerItem`, toggled by `includePerItemMaxMana`) uses, so a boon that says nothing behaves as every item does today. `resolvedBoostOf` is the only place the default is applied. The compiled `action_nodes[p].boosts` table states every item's value, and while an ActionNodes world is loaded the runtime takes each received item's mana from that table instead of the global flat term (`gameState.setPerItemManaTable`; [The runtime](#the-runtime)). Other substrates are unchanged.

**What the validator enforces, and why.** No boon amount and no stat result is negative, and every requirement is a minimum. With those, holding more items can never make a plan impossible, which is what lets the logic keep only minimal item combinations ([Gotchas](./gotchas.md#a-minimal-set-search-over-an-item-lattice-assumes-monotonicity-and-the-learning-walk-cannot-check-it)). It also requires exactly one start and one goal, an `after` on every other node, every node reachable through `after` chains, and an item pool that fits the check count. Forms the first version leaves out are refused by name: alternative requirement sets, result timing (`when`), growing limits, `modifies`, maximum requirements. A window and knowledge keep the guarantee; their refusals are `bad-window`, `window-on-start`, `bad-clock`, `unknown-knowledge`, `knowledge-never-learned`, and `unsupported-earlier-start` for a boost part (`earlier`, `clock`, `start`) that would move the start of the clock (§ Time windows, the clock and knowledge, below).

## Time windows, the clock and knowledge

AN-TIME-1, for the mystery game's present-time choices. ⚖ Robert, 2026-11-25 (the design `actionnodes-time-design`, Q1–Q5 and Q8, as recommended):

- **A window counts from the time spent this loop.** A node's `window: {from?, until?}` is in units of time since the loop began, waits included (`state.clock`). The clock starts at 0 in every loop, and items never move it.
- **Early, it waits.** A node started before `from` first waits until `from`, and the wait is paid from the pool. `whyNot` does not refuse it; `waitNote` says `waits 2 (opens 12:00)`.
- **The start decides.** A node may start at `until` exactly. After that it is refused by name: `too-late`, *too late: after 10:00 (it is 11:00)*.
- **An item may add time at the end, never move the start.** A boon's `gives.mana` lengthens the loop as before. A boost part that would start the clock earlier is refused (`unsupported-earlier-start`).
- **A timed graph (one with a `clock`) defaults to `xpEffect: none`** (`TIMED_GRAPH_SETTINGS`), so an hour always costs an hour. The graph's own `settings` still win.
- **Knowledge** is a flag learned by performing a node (`results.learns`) and kept across loops. A node may require flags (`requires.knowledge`): it can be performed once each is known, whether from an earlier loop or learned earlier in this one.

**Why the logic stays exact.** More items never make a plan impossible. The clock is a function of the actions taken alone, a window is checked against that clock, and a known flag only ever satisfies a minimum. Two readings would break it, and neither exists: a window read against the time LEFT, and an item that starts the clock earlier. Over random graphs each breaks about one graph in ten. `actionTimeLogic.slow.test.js` pins the real search against a full-state reference over 400 random graphs with windows and knowledge. It also makes each rejected reading go red.

**The search key.** With a window, two orders of the same actions can end at different clocks, because one of them waited. All plans to one count vector are the same length, so they sit in one BFS layer. `enumerateLoop` walks a windowed graph layer by layer and keeps, per count vector, the earliest clock (then the most mana). This is exact against the full-state search, which the plain counts key is not. A graph without windows takes the old walk unchanged.

**Knowledge in the logic.** Each flag is one more 0/1 dimension of the item lattice, after the boons (`itemCombinations`, `itemVectorOf`, `logicItemNamesOf`). The compiler places an EVENT location at every node that teaches a flag: `<node> (learns <flag>)`, no AP id, locked, the node's own perform rule. The location holds the event item `Knows: <flag>` (`knowledgeItemNameOf`), which is in the items table and `itempool_counts` like any event. A rule names that item only where the flag must come from an earlier loop. The fill never places an event item, and its in-logic test closes over the events (`closeKnowledge`). `procgen_metadata[p].action_logic.knowledge` reports each event's teachers and rule.

**What a compiled world carries.** The payload's `window`, `requires.knowledge` and `results.learns`, and the block's `clock` and `knowledge`, are written only when present. A graph without them compiles to the same bytes as before: the example and the omsi town presets are byte-identical. The registry's location carrier names a node's event locations too.

**Time in the app (AN-TIME-2).**

- **The runtime knows time.**
  - `runtimeModelOf` reads each payload's `window`, `requires.knowledge` and `results.learns`, and the block's `clock`, `knowledge` and `pool`. So `whyNotAct` and the start gate apply the model's rules: a late act is refused (`too-late`), and an unknown flag is refused (`knowledge`, *needs to know Paper A*).
  - The runtime keeps the loop's clock: each price paid plus each wait, back to 0 on every reset.
  - **The loop's pool is `loop.mana`.** Before this slice the app started every loop at gameState's default of 100, whatever the graph said; every committed world sets 100, so the two agreed by coincidence. The runtime now states the difference as its own max-mana bonus (`setSubstrateMaxManaBonus('action_nodes', loop.mana − 100)`), and refills the pool when that bonus moves. A world at 100 sets a bonus of 0.
- **The knowledge gap.** A `Knows:` event location's rule is the node's perform rule, so the state manager used to collect it as soon as the node was reachable, and the app held the flag before the player had done anything. Now the compiler marks each knowledge event location `event_kind: 'substrate_state'`.
  - That kind has a policy row in `stateManager/core/eventKinds.js`: never auto-collected, not player-checkable.
  - The runtime keeps its own learned set, filled by `perform`, and collects each new flag's location with a forced local check (`stateManagerProxy.checkLocation(location, true, true)`, as Seedling's obstacle events are).
  - A snapshot that holds a flag's event item (after a reload, or a `/sync` full reset, which re-adds a kind it never auto-collects) adds that flag to the learned set.
  - The logic is unchanged: the sphere log does not read `event_kind`.
- **The wait.** An early arrival waits and pays the time (E2), in the app as in the model.
  - A `wait` Loops entry: `{type: 'customAction', actionName: 'wait', params: {nodeId, units, label}}`. It is a row of `shared/procgen/loopCustomActions.js` that states its own price (`params.units`, `statesOwnCost`) and takes no region-XP discount (`xpDiscount: false`; `loopState`, `loopUI` and `queueAnalysis` skip it). Its completion moves the runtime's clock.
  - The click (`planPerform`'s `waits`), the panel's **Queue act** and the bot's route (`routeOfPlan`) each queue a wait of the exact length before an early act.
  - The start gate refuses a bare early act (`too-early`, *opens at 12:00: queue a wait first*), so a wait is always visible in the queue. `queueEndState` applies a wait and stops at an early act, as the gate would.
  - Outside Loop mode, `actNow` charges the wait together with the price.
- **The labels.**
  - The node card shows a window line (*available 12:00–13:00*, *available until 10:00*, or *any time*; a windowed world only). An early ready card also shows the click's text (*click: waits 3 h (opens 12:00), then 1 h*). A too-late card marks the window line.
  - The Resources panel shows *Time: 11:00 · 6 h left · the day ends 17:00* for a world with a `clock`.
  - Every user-facing "mana" listed in the design's § 4 table reads the pool's name. That name is the optional graph field `pool: {name, unit?}` (refusal `bad-pool`), compiled to `action_nodes[p].pool` only when present; with no `pool` it is "Mana", and every text is the old one.
  - The registry entry's `loopSupport.pool()` and `loopSupport.clockLine(mana)` carry them to the shared panels (`resourceChannels/poolName.js`). They are on `loopSupport` because the registry validates `sharing.mana`'s fields. The Loops panel's strings read them through the loaded world's entry.
- **"Completed before"** (⚖ Robert's Q6, minimal form).
  - The runtime keeps each node it has performed, with the loop it was FIRST performed in. Loop 1 is the load's loop, and a reset with nothing done does not count as a loop (so neither does the world load's own `loopState:loopReset`).
  - In a later loop, the node's card shows *completed before · loop 1*: a tag, not a grey card. The node panel lists the set under **Completed before**, each entry tagged *loop N*.
  - The set is saved per world (graph, seed, slot) in localStorage under the declared prefix `actionNodesHistory_v1_` (`historyStore.js`). A storage that fails keeps the set in memory.
  - Storing the actions of the first (or latest) completing loop is AN-TIME-3.

**The fixtures.** `fixtures/harbour-morning.json` is an original timed toy (seven nodes, 09:00, an hour a unit). `fixtures/visits-day.json` is the structure of a miniature case's visits under neutral names: five visits, a day of 3, one same-day `after`, three knowledge gates. Its answer's rule is `Has(Knows: Paper C)`, because Paper C cannot be learned on the same day as the answer. Both are test fixtures, not presets. The in-app rows `an-time-window-and-wait`, `an-time-knowledge-gate` and `an-time-completed-before` (category "ActionNodes", batch `fast`) compile them in the page and load the result in memory. ## The model and the search

`actionModel.js` is one loop. Movement is free, so a loop's whole state is how many times each node has been performed; mana, stats and resources follow from the counts. A node can be performed when, in this order: mana is above 0; the node is reached (the start always is, and is cleared from the beginning); its limit is not used up; every minimum is met; no resource would go below 0; every knowledge flag it requires is known; it is not too late for its window (after any wait); the mana left covers its price and any wait. A node may be started with too little mana, but it does not complete, so the logic and the bot count it only when it completes. An item received during a loop applies at once (`applyBoost`).

`actionSearch.js` enumerates every reachable state of one loop breadth-first, so each state's recorded plan has the fewest performances (a windowed graph keeps the earliest clock per count vector: § Time windows, the clock and knowledge, above). `deriveActionLogic` runs it once per item combination (each boon from 0 to its `count`) and keeps, per node, the minimal combinations under which some state performs it and some state reaches it. Both searches have budgets (`DEFAULT_STATE_BUDGET`, `DEFAULT_COMBINATION_BUDGET`); past one the search is refused by name (`search-budget-exceeded`, `combination-budget-exceeded`), never cut short. A hand-set intended path is the fallback for graphs too large to search; it is not built.

## The compiler

`compileActionGraph(graph, {playerId, seed, budget, graphPath, exists})` in `actionGraphCompiler.js` returns `{rules, report}`:

- **Regions:** `Menu` → the start node; one region per node, named by its id. **Two-way edges** (AN-1b): each `after` edge A→B is a forward exit `A -> B` and an ungated reverse exit `B -> A`, both named `<from> -> <to>`. There is no exit back to `Menu` and no return-to-start exit: the start is reached by the `Menu -> start` hop, as in every substrate. Moving between nodes reached this loop is free (the user, 2026-11-16: *"once a node becomes reachable in a loop, it stays reachable for the rest of the loop, and moving between nodes is free. Reachability resets when the loop resets."*). The Region Graph merges an exit pair into one edge, so it draws one edge per `after` edge.
- **Locations:** a check node's location is named by the node; the goal node's location holds `Victory` (`procgenCore/goalItem.js`), locked, and the completion condition is `item_check Victory`.
- **Rules:** a location's rule is "some one-loop plan performs the node with the items held"; a forward exit's is "some one-loop plan reaches the node it leads to"; a reverse exit's is `True`. The reverse exits change no meaning: every location and forward-exit rule is already the exact one-loop answer, and the search already assumes free movement. Each is the Or over the minimal combinations of And(Has(item, n)); an empty combination is True. An item is progression when any rule names it.
- **Items and fill:** each boon `count` times, then the filler; a seeded assumed fill over the derived rules. The fill draws one open check at random for each progression copy, so on a graph with few checks open at the start one draw can leave no place for the last copies while another does not. It is tried up to `fillAttempts` times (`DEFAULT_FILL_ATTEMPTS`, 32; the compile script's `--fill-attempts`). Attempt 1 uses the seed itself, so a graph that fills first time compiles to exactly the bytes it did before retries existed (the example does); attempts 2 and on take their seeds from a separate stream derived from it (`fillAttemptSeeds`). A world that needed a retry records `action_logic.fill` (`attempt`, `seed`); one that did not carries no such key. Measured on the omsi town (`graphs/omsi-first-town.json`, 20 nodes, 18 checks; see [The omsi town](#the-omsi-town)), seeds 1–20: attempt 1 alone fills 6, the retry fills all 20, the worst needing 6 attempts; over seeds 1–200, attempt 1 fills 120 and every seed fills by attempt 6.
- **Ids:** the `action-nodes` row of `procgenCore/apIdNamespaces.js` (base 40000000), allocated by sorted name.
- **Blocks:** `preset_sidecars[p]` (one per node, below), `action_nodes[p]` (`actionNodesBlockOf`: loop, stats, resources, `boosts` by item name, `mana_per_item_default`, start, goal, `action: 'act'`, settings), `procgen_metadata[p]` (`driver: 'action-graph-compiler'`, the graph id and path, `action_logic`), `provenance[p]` (the pack ids given as `exists`, else the graph's own provenance block: a world looks its sources up through its packs), `exporter[p].assume_bidirectional_exits: false` (the world LISTS its back-exits; `true` would let a reader construct one for every exit, `start -> Menu` included), `discovery_mode[p]: {enabled: true, bundle: 'actionNodes'}` (below) and `loop_costs[p]`: every node `{moveCost: 0, xpEffect, xpGainScale, actions: {act: <time>}}`. These costs are authored, not generated; `rules.schema.json` declares `actions` and `xpGainScale` on a region entry for them.
- **Sphere log:** `generateSphereLog` over the compiled rules, embedded as `sphere_log`.

**The proof.** In each loop at least one location check can be earned (when the player is not waiting on another world). The compiler refuses by name when a check or the goal has no item combination that earns it (`check-never-earnable`), when a node is never reached (`node-never-reached`), when the sphere log over the derived rules does not reach the goal (`goal-not-in-logic`), or when no fill attempt finds a place for every progression item (`fill-failed`, naming how many attempts were made). A check is in logic exactly when a one-loop plan earns it, and the fill guarantees an unchecked in-logic check whenever the game is not waiting, so some loop earns one. `action_logic.a6.spheres` reports how many checks are open at once in each sphere; that is reported, not enforced. Every target also records a witness plan per minimal combination.

**The payload.** `playable_payload` is the node with names resolved: `node_id`, `name`, `kind`, `time`, `limit`, `requires` and `results` as `{<id>: {name, amount}}` (results also `mana`), `after`, `location` (only on a node that carries one), optional `position`, and the envelope's `exits` (each `{exit_id, exitName, targetRegion}`, a reverse exit also `reverse: true`, with no `side`: a node has none). The entry's `sidecarFields` declare every key.

## The runtime

`actionNodesRuntime.js` holds the loaded world; `index.js` wires it to the app and `actionNodesPanel.js` shows the node the player is at. The runtime's model has `buildActionModel`'s shape, built from `action_nodes[p]` and the node payloads (`runtimeModelOf`), so "can this node be performed" is `actionModel.whyNot`, the same rule the search and the bot use.

- **What it keeps.** Per loop: each node's performances. Through the host ledger (`resourceChannels/resourceLedger.js`): the stats and resources. Across loops, until the next world load: the checks it has sent and the nodes whose exits it has revealed.
- **The `act` verb.** A Loops queue entry `{type: 'customAction', actionName: 'act', params: {nodeId, label}, sourceRegion}`. The named-action table (`shared/procgen/loopCustomActions.js`) prices it at the node's `loop_costs[p].regions[<node>].actions.act` (then the region-XP discount, as every cost), labels it by the node's name, and on completion publishes `loop:actionCompleted` on the event bus; the runtime then performs the node. There is no explore in ActionNodes (below).
- **The start gate** (`loopSupport.actionGate`). Before the generic executor starts an entry of an ActionNodes region it asks the runtime. An `act` is refused when its node is not reached this loop, its limit is used up, a requirement is not met, or a result would take a resource below 0; a move is governed by the MULTI-ENTRY RULE (AN-3a): every exit, forward or reverse, is open iff its TARGET is reached this loop — the start, or a node one of whose `after` sets is fully cleared. On a one-member set that is "the source is cleared" (code `not-cleared`, with the count); on `after: [[A, B]]` both A→N and B→N stay shut until A and B are cleared (refused with A cleared: `target-not-reached`, naming B); on `after: [[A], [B]]` either cleared opens both. A move that names no exit of the node keeps "the source is cleared". The compiler's forward-exit rule is already the target's reach rule, so the example preset is unchanged. So a multi-hop move between reached nodes is never refused and costs 0; reachability resets with the loop. Any custom action but `act` and `wait` is refused (`action-not-offered`). An early `act` is refused (`too-early`): its `wait` goes first (above). The refusal stops the queue at that entry and the Loops panel names the entry and the reason ([Loop Recording](./loop-recording.md#the-start-gate)). Mana is not part of the gate: a node started short of mana drains what is left into region XP and the loop ends, as every Loops action does.
- **One performance.** The results go to the ledger (all or nothing), `results.mana` to the pool. The first time a node is cleared, its forward exits are revealed (below); discovery is never reset by a loop. A check or goal node sends its location once (`user:locationCheck`); in later loops the action repeats without it.
- **Outside Loop mode** the panel's **Act** performs at once: the runtime charges the shared pool the XP-adjusted price (`chargeMana`), and at zero fires the loop-reset teleport. Short of mana, what is left is spent and the action does not complete. In Loop mode the button is **Queue act**: it appends an `act` entry when the queue ends at the node.
- **Boosts (A4).** An item named in `boosts` adds its stats and resources to the ledger at once when received and again at every loop's start. Its `mana` is that item's starting mana, through the per-item table in `gameState` (an item with no row adds `mana_per_item_default`); a received boost's mana is also gained at once. The first state snapshot after a load is the baseline, so items already held are not gained twice. A baseline that arrives after the loop's first performance (nothing guarantees a snapshot between a load and a check) does not restart the loop: what it holds was received during the loop and applies at once (AN-3a; before, it wiped the loop's counts mid-loop).
- **Both resets.** `gameState:loopReset` and `loopState:loopReset` each start a new loop: counts to zero, the ledger to its base plus every held boost.
- **Cross-substrate items.** The resources are also declared under `sharing.items`, so a grant to `action_nodes/<resource>` lands in the ledger.
- **Costs are authored.** The entry declares `loopSupport.authoredCosts`, the cost class `authored`: the Loops panel's Generate Costs and the pipeline's cost pass copy each node's entry as compiled. `xpGainScale` on a region entry scales the region XP earned there (default 1, so every other world is unchanged).

### No explore

The user, 2026-11-16: *"I don't want explore actions to be available in ActionNodes."* The entry's `loopSupport.queueActions` (`regionMove`, `act`, and AN-TIME-2's `wait`) is ENFORCED: it declares `strictQueueActions` (`loops/strictQueueActions.js`). An explore — from any control, an undiscovered exit or location click included — is refused at queue time (gameState's custom-action guard, installed by the loops module: nothing is appended, `gameState.lastQueueRefusal` names it) and, if it got into the queue some other way, by the start gate. The Loops block builder draws no explore button for a region whose entry lists no explore. No other substrate opts in.

### Discovery

The user, 2026-11-16: the start node starts fully discovered; the nodes connected to it start showing all their contents; a node that is visible but not completed on any loop shows how many exits it has and which way they lead, not their names nor their targets' names; discovery stays on loop reset; no random explore effect. The compiled world names the discovery module's `actionNodes` bundle (`discovery/worldDiscoveryMode.js`: Loop mode's overrides with `autoDiscoverLocations` on, forced with Loop mode on AND off).

- **At load** the discovery module reveals the start's neighbourhood (`discovery/revealCore.js` `revealStartNeighbourhood`): the start node's exits, the nodes they lead to with their locations, and each of those nodes' exit back.
- **A node's first clear** calls the discovery module's public `revealExits(node, its forward exits)`: each exit, its target and the target's locations, and the target's exit back. It makes no random pick (until AN-1b the runtime published `loop:exploreCompleted`, whose receiver also ran explore's random pick).
- **A reverse exit is revealed with its node**, so it never shows as `???` and never adds to the visible exit count. A visible node's forward exits stay `???` edges to `???` nodes at their layout position (what the Region Graph already draws; the Regions panel lists them as `??? → ???`).
- **The order trap.** The override applier writes `regionDiscoveryTrigger` before `autoDiscoverLocations`, so the start cascade runs with locations off; `settingsChangeSteps` re-runs its location step when they turn on.
- **Loop reset.** Nothing clears discovery: no module publishes `loop:reset` (`revealCore.test.js` holds that).

### The node states and the node card

`nodeStates.js` gives every node exactly one state, by one pure function over the node data and a loop state, in this precedence:

| State | Meaning |
|---|---|
| `undiscovered` | the discovery module has not discovered its region: the card shows the discovery placeholder |
| `not-reached` | no `after` set is cleared this loop |
| `done` | its limit is used up this loop (the start, cleared from the beginning, is always `done`) |
| `blocked` | reached, performances left, a requirement unmet (named). Short ONLY of mana: `blocked`, "not enough mana" (it can still be queued) |
| `ready` | reached, performances left, every requirement met, the mana covers its live price |

While the Loops queue is being planned the states are for its END (`queueEndState` applies every uncompleted `act` entry and stops where the queue would); while it runs they follow the live state (`viewStateOf`; `runtime.nodeStates({running, queue, isDiscovered})`).

**The card** (`nodeCard.js`) is a Region Graph node overlay. `nodeCardOverlay.js` registers it (`regionGraph` public `registerNodeOverlayProvider`) while an ActionNodes world is loaded and removes it on unload (`unregisterNodeOverlayProvider`, added for this in AN-3a), so no other world sees it; it refreshes on the queue, the ledger, mana, discovery and checks. It shows the name, a check mark once its location is checked (a goal mark on the goal), `used/limit`, the live mana price, needs and gives with the unmet line marked, and takes its state's border. An undiscovered node shows `???` only; one with no way in from a discovered node is not drawn (the view model's rule). A Region Graph panel created while the card is registered (a closed panel reopened, or a second one) gets it too: `regionGraph/index.js` publishes `regionGraph:panelMounted` when a panel registers, and `nodeCardOverlay.js` registers the card again on it (AN-3b; before, the overlay API's one pending slot served only the first panel, so a reopened panel had no card until the next world load).

**The click** (AN-3b; the user, 2026-11-17: *"The default click action should be to perform once. I don't want to add a right click action."*). `actionNodes.act` is a registered click action (`regionView/clickActions.js`; owner `actionNodes`, region target, a toggle, panel order 300, after the built-in route and checks), registered only while an ActionNodes world is loaded (`nodeClickAction.js` `syncClickAction`); both the Region Graph and the Region Map run it from their **On click** strip. A click on a node card's body is the node's click: the overlay manager forwards it to the Region Graph's `handleRegionNodeClick` (planner ruling 2026-11-20). What a click does is `nodePerformPlan.js` `planPerform`, computed for the END of the Loops queue (the state the cards show):

| The node at the queue's end | Loop mode on | Loop mode off |
|---|---|---|
| `ready`, the queue ends on it | queues one `act` | performs once at once (`runtime.actNow`, the pool pays) |
| `ready`, the queue ends elsewhere (unreached by the queue) | queues the free hops to it (`actionLoopBot.hopsBetween`; from `Menu`, `Menu → start` first), then one `act` | the same moves, then performs once |
| `blocked` (a requirement, or short only of mana) | refused by name, with the unmet requirement (`Eat Bread: needs Bread 1 (has 0)`, `… : not enough mana`); nothing queued | the same |
| `done` (its limit used up at the queue's end) | refused by name, with the count | the same |
| `not-reached` | refused, naming what is still to clear | the same |
| `undiscovered` | refused, naming nothing about the node | the same |

A queue that already stops early (an entry the gate would refuse) is refused too: nothing after its stop would run. The hops are queued as `user:regionMove` under the planning source `actionNodes-plan-<panel>` (`loops/loopModeExemptions.js`). A click never starts a performance it cannot finish (⚖ Q1 still lets the node panel's **Queue act** do that on purpose). There is no right click.

**The "perform all remaining" button** (AN-3b; the user: *"a separate button on the repeatable nodes to perform all remaining"*). A node whose limit is greater than 1 gets one **Perform all remaining** button in the card's `.an-card__actions[data-slot="perform-all-remaining"]`. It does what the click does with every performance left at the queue's end (`limit − count`), CAPPED by what the end state allows: each performance must pass the gate with the mana left after the ones before it (the live, XP-discounted price) and every requirement. When the mana runs short it queues (or performs) as many as the pool finishes and says so on the card (`.an-card__message`, e.g. `1 hop(s), then Do Chores ×1 of the 2 left (stopped: short by 4 mana)`); a node with none left, or not ready, is refused by name there. The button is not a node click (it publishes no `regionView:regionClicked`).

The Resources panel (`resourceChannels/resourcesPanel.js`) shows the mana line, the ledger's stats and resources, and the boosts in effect, for every substrate of the loaded world that declares a sharing category.

## The bot planner

`actionPlanner.js` `planLoop(model, {items, checked, xp, start})` plans one loop (or the rest of one) with the live items and region-XP prices (`livePrices`, the shared `xpFormulas.js`). Its aim: the goal as soon as it is reachable, with the fewest performances; otherwise the most new checks (ties: most mana left); otherwise the target short of mana by the least, run as far as it goes and ended by attempting the node it cannot afford, which drains the rest into region XP; otherwise, when every target needs an item, the most mana it can spend, and it says it is waiting for an item. Every decision is a line naming the choice and why each unchosen check was not taken, for example *Move the Boulder: short by 5 mana after Guard's Locker*. **The relevance cone** (AN-OMSI-1). The question "short of mana by how much" is a search with mana ignored, and over a whole town-sized graph it has too many states: on the omsi town with every item held, 911,712 against the budget of 200,000, so the bot was refused. `relevantNodes(model, state, target)` keeps only the nodes that can matter: the target; for each kept node, the members of its `after` sets, the producers of each stat it requires that the state does not already meet, and the producers of each resource it requires or spends; and every node whose mana result is at least its price. `leastShortPlan` and the "needs an item" line walk only those (`enumerateLoop`'s `allowed`). Dropping a node outside the cone from a plan leaves the plan legal and short by no more, so the least shortfall is the same; when it is above 0 the whole answer is the same, plan included, because the cone's states come in the whole walk's order. When it is 0 the whole walk would have preferred a plan padded with any affordable node, which no caller reads. On the town the largest cone walk is 19,164 states, and the bot's plays of the example and of the town are byte-identical to the whole-graph walk's (the town's measured with the budget raised).

`playToGoal(model, {placements, xpGainScale})` plays a compiled world with it: an item arrives the moment its check is performed and the bot plans the rest of the loop again from there. A knowledge flag learned in a loop is held from the next.

**Time and knowledge in the planner** (AN-TIME-1).
- When no check can be earned this loop but a flag some open target needs can be learned, the loop learns the most of them (kind `learn`; ties: most mana left). Otherwise the XP and waiting fallbacks follow as before.
- The relevance cone also keeps every node that teaches a flag a kept node needs and the state does not know. Dropping a node only makes later steps start earlier, which an `until` allows, and an early node waits to the same `from`. So the cone stays exact (pinned in the slow test).
- The shortfall and "runs furthest" sums add each wait.
- `orderForMana` checks the target after a reorder and keeps the BFS order when the reorder would bring a windowed target too late.
- A reasoning line names the waits along its plan (`Watch the Ferry Come In waits 2 (opens 12:00)`); a windowless graph's lines are unchanged.

**The live bot** (AN-3a). The registry entry declares `loopBot.planLoop(context)` (`actionLoopBot.js` `planLiveLoop`): `planLoop` over the runtime's model with the live inventory, checks, region XP and pool, written as a Loops path — `Menu → start`, then for each performance the free hops from where the player is (a shortest path over exits whose target is reached at that point of the plan, so the start gate never refuses one), then the `act` entry; an attempt is the last act. The Playback Bot's loop runner asks it for the whole loop when every region of the world is an ActionNodes node ([Playback and Debugging](./playback-and-debugging.md#the-playback-bot-frontendmodulesplaybackbot)); its reasoning lines go to the bot's log and the console behind the bot's **Log the loop plan's reasoning** setting. `actionLiveSim.js` `playLiveToGoal(rules)` plays those paths headless through the real runtime gate, pool and checks. **The mid-loop replan** (AN-3b). When a loop's queue has run to its end with mana left and the state DIVERGED from the plan — an item arrived during the loop (applied at once, A4), the one thing the plan could not foresee — the runner asks `planLoop` again with `context.continueFrom = {region, mana}`: the rest of the loop from the runtime's live counts, routed from the player's node (no `Menu → start` hop). Its path is APPENDED to the queue, which resumes where it stopped (no reset, no refill); its lines are logged as `loop N (replan): …`. Without a divergence the loop ends as before: the plan already was the planner's answer for that state. `playLiveToGoal` plays the same continuation, so the live path reaches the example's goal in the pure planner's 2 loops (AN-3a: 3) with its reasoning lines.

## The scripts

- `scripts/procgen/action-nodes-compile.mjs [<graph>] [-o out] [--seed N] [--exists id,id] [--fill-attempts N] [--check]` compiles a graph; `--exists` names the packs the graph is the resolved structure of (recorded in `provenance[p]`). With no graph it recompiles **every committed ActionNodes preset** by the recipe that preset records: the roster is derived from `preset_files.json` (each folder whose game is Action Nodes) and the rules file's own `procgen_metadata[p].graph_path`, `generation_seed` and `provenance[p].exists`, so a new preset enrols itself once it is registered. With `--check` that is a byte-identity gate over all of them, and it runs in CI as a row of the Producer --checks job (`ci-producer-checks.mjs`). A new preset is written once with its recipe spelled out (`<graph> -o <out> --seed N`), then registered.
- `scripts/procgen/action-nodes-play.mjs [<rules.json>] [--live-only]` plays a compiled world to its goal with the planner and prints every loop with its reasoning, at the graph's XP scale and at 0; then the live bot's path (`playLiveToGoal`), where a refused hop or act fails the run.

## The example

`graphs/example-village.json` is the ten-node village: Start; Do Chores (5 mana, Gold +3, twice); Train; Read the Notice; Eat Bread (a use node, off the start); Buy Bread and Bribe the Guard (after Do Chores); Guard's Locker and Move the Boulder (the two checks); Leave the Village (the goal, Strength 2 and Knowledge 1). Its two boons, Strength Boost and Pocket Money, state `gives.mana: 0`: under the default of 10 the goal would no longer need the bread. Its numbers are hand-made content in the content-sets sense of *use the table as written*: nothing reassigns them, and the compiler reads them exactly as written (the other value of that per-world switch, *assign by playthrough*, belongs to generated worlds and is not built here). It compiles to the committed preset `frontend/presets/action_nodes_example/AP_1/` (4 item combinations, at most 64 states each): both checks `True`, the goal `Has(Strength Boost)`.

## The omsi town

`graphs/omsi-first-town.json` is omsi-loops' first town, Beginnersville, as 20 nodes: the start, 18 checks and the goal **Start Journey**. It uses 19 of town 0's 25 actions, under their omsi names, with no story text. Its numbers are the AN-OMSI-D design's mapping as Robert ruled it (2026-11-24):

- **Time**: omsi's level-0 mana ÷ 20, with a 100-mana loop; every item adds 10 starting mana (the default). Multipart actions are one performance per segment (Fight Monsters and Heal The Sick 3, Small Dungeon 7, each segment the same price).
- **Progress bars** (Wander, Met, Secrets): the first step is an `after` edge ("done this loop": Pick Locks, Buy Glasses and Buy Mana after Wander; Train Strength and Short Quest after Meet People; Long Quest after Investigate). Each later step is a boost item: Wander Progress ×1, Met Progress ×1, Secrets Progress ×2.
- **Skills**: omsi's Combat + Magic ≥ 35 is Combat 2 and Magic 2. A Training item gives +1 every loop (Combat ×2, Magic ×2); a Lesson gives +1 within the loop, and needs Reputation 2 held, so a loop that spends its reputation first loses the Lessons.
- **Checks**: every action but the start and the goal (18), with 10 Soulstones as filler.
- **Gold** ÷ 10, every-Nth rewards given every time; growing limits flattened (Smash Pots 3, Pick Locks 2, Short Quest 2, Long Quest 2). **Buy Supplies costs 6 gold**, not 30: one loop holds at most 12 gold with every item, and the goal is refused at 10. Haggle's discount on Buy Supplies is folded into Gold +2 per Haggle.

**Left out**, recorded in the graph's own provenance (`left-out`): Open Rift and AssassinZ0 (later towns' skills), SurveyZ0, Hitch Ride and Map (explore progress, whose first map comes from town 7), and Found Glasses (never startable). Also dropped: trained stats and talents (they only make omsi's actions faster, and the graph has no speed), the glasses' Wander multiplier, Throw Party's Met reward, Small Dungeon's soulstones and the multiparts' skill exp. No format addition was needed.

It compiles to the committed preset `frontend/presets/action_nodes_omsi_town/AP_3/` at seed 3, whose fill succeeds on the first attempt (so `action_logic.fill` is absent): 1,188 item combinations, at most 10,554 states each, 8 spheres ending Buy Supplies → Start Journey. The bot plays it to the goal in 7 loops at XP scale 1 and 8 at XP scale 0 (`action-nodes-play.mjs`). The town-scale pins (`actionNodesTownScale.slow.test.js`, the relevance cone and the fill retry) load this same file: there is no second copy to drift.

## The registry entry

`actionNodesLibrary.js` registers identity, `deserializeWorld` / `serializeWorld` (exits as a `Map`), `sidecarFields`, `apLocationNamesOf`, `apExitNamesOf`, `regionGeometry: sides` and `SIDE_AGNOSTIC_EXIT_SIDES`. It declares no realiser hook, because the compiler writes its regions.

- `fillRules`: the content-pack fill rules it applies (`procgenCore/fillRules.js` `fillRulesOf`).
- `loopSupport`: `queueActions: ['regionMove', 'act', 'wait']`, `strictQueueActions: true`, `actionGate`, `authoredCosts: true`, `manual: false`, and (AN-TIME-2) `pool()` and `clockLine(mana)`, the pool's name and the Time line, read by the Loops and Resources panels. Not `manual`: a Manual block parks the queue for live play, and in Loop mode every performance is a queue entry, so a park would wait for nothing. Not `record` / `playback` (the strict action gate's pair: the start gate does that job), and no `executeVia` until the playback controller exists.
- `sharing`: `mana`, `items` (its resources), `stats` and `resources`, each list read from the loaded world.
- `loopBot.planLoop`: the live bot's loop plan (above).

It declares no playback controller (the live bot plays through the Loops queue), so the capability chart shows ✗ for a Bot block.

Unit tests: `frontend/modules/actionNodes/*.test.js`; in the browser, the category "ActionNodes" of the substrates test mode (batch `fast`), and `an-bot-plays-to-goal` in the category "Playback Bot" (batch `playback-bot`). The omsi town has two rows of its own (AN-OMSI-3): `an-omsi-town-load-and-act` (category "ActionNodes", batch `fast`: the preset loads, the start's neighbours' cards show the preset's prices and needs, the goal's supplier is blocked with its unmet line, one performance sends its check) and `an-omsi-bot-plays-to-goal` (category "Playback Bot", batch `playback-bot`: the bot reaches Start Journey in exactly 7 loops, equal to the pure planner and the headless live path).
