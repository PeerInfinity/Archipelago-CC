# The Seedling Real-Game Bot

How the repo drives the real recompiled Seedling with a scripted input tape and checks a JavaScript transcription of its physics against what the game actually did, tick by tick. The chronological build history (the R1–R9 rungs and the `watch.html` arcs) is in [seedling-bot-log.md](./seedling-bot-log.md).

The maze bot ([maze.md](./maze.md)) proves generated worlds beatable on the projected map. This bot answers questions about the original game, which is the only oracle that can say "beatable in the actual game". The plan it belongs to is `CC/docs/plans/region-atlas-plan.md` (Phase 8, the real-game surface).

The ladder that built it was subtractive (`CC/docs/plans/seedling-bot-subtractive-plan.md`): disable collision, damage and hazards so the whole map is walkable, walk the whole game, then re-arm one obstacle type per rung. Each tape still says which relaxations it runs under, which is why the tape format carries them.

## The shape: two implementations, one tape, compared

```
        tape (JSON: tick-indexed hold spans)
         │                              │
         ▼                              ▼
  seedlingDemo (JS)              Bot.as (compiled into the game)
  playerPhysicsV1/V2             dispatches KeyboardEvents at FP.stage
         │                              │
         ▼                              ▼
   observation stream  ==EXACT==  observation stream   ← the differential
```

Both sides consume the same tape and emit the same observation-stream shape, so a disagreement is about physics rather than bookkeeping. The game's streams are recorded and committed as fixtures (`fixtures/expectations/<name>.json`, `{ticks, transitions}`). Vitest then checks the JS model against the real game on every CI run without a browser, and the browser differential only has to answer "are the recordings still current?".

Exactness is deliberate. AS3 `Number`, JS numbers and the recompiled runtime are all IEEE-754 doubles, so a mismatch is a transcription defect to investigate, not a tolerance to configure.

## The tape format

A tape is JSON. Inputs are tick-indexed hold spans, `from` inclusive and `to` exclusive:

```json
{ "tape_version": 3, "game": "seedling",
  "boot": { "level": 0, "x": 80, "y": 128 },
  "noclip": false, "noDamage": true, "noHazards": [], "grants": [],
  "persistence": [], "tick_count": 40,
  "inputs": [ { "key": "right", "from": 0, "to": 30 } ] }
```

Spans rather than per-tick key states, because Seedling reads input three ways and the tape must express all of them. Movement is `Input.check` (held), item use is `Input.pressed` (down edge), and dialogue, NPCs and the seal read `Input.released` (a full down-then-up). A length-1 span yields a press edge on tick `from` and a release edge on tick `to`, so it covers all three.

Key names map to AS3 keycodes through one table, `KEY_CODES`, asserted by both consumers. The source is `Player.as`'s `keys = [RIGHT, UP, LEFT, DOWN, X, C, X, V, I]`; the names are `right`, `up`, `left`, `down`, `primary` (X), `secondary` (C), `inventory` (V) and `inventory2` (I). `M`, `R`, `Esc` and `W` are rejected by name (`FORBIDDEN_KEYS`): `Game.update` reads the first three before entities and some branches call `Input.clear()` or rebuild the world, and `W` opens an external URL.

Validation is loud everywhere. `noclip` has no default, unknown keys throw, and overlapping spans on one key are rejected: FlashPunk's `_key[code]` guard makes a second KEY_DOWN a no-op and the first KEY_UP clears the hold, so overlapping holds do not compose.

`name`, `description` and `note` are free-text audit fields that neither consumer reads.

### Versions

`tapeFormat.SUPPORTED_TAPE_VERSIONS` accepts versions 1 to 13. A field is legal only at or above the version that introduced it; a lower-version tape that declares it is a named error. **Note:** check the version by value, never by presence: `parseTape` is idempotent and fills every later field with its empty value, and the harness sends the parsed object, so a presence check rejects every tape.

| Version | Adds | Reaches the game? |
|---|---|---|
| 1 | Hold spans, `boot`, `noclip`. `boot` must equal `BUILD_SPAWN` (`{level: 0, x: 80, y: 128}`), the spawn the early build had baked in | yes |
| 2 | `noDamage` (boolean), `noHazards` (a set of names from `HAZARD_NAMES`: water, pit, lava, ice, waterfall), `grants` (`[{level, items}]`); `boot` may name any level | yes |
| 3 | `persistence`: `[{level, tag, note}]` persistence flags cleared before the first live tick. Clears only, never sets | yes |
| 4 | `equips`: `[{t, slot}]`, a write to `Main.primary` at observation tick `t` | yes |
| 5 | `pins`: determinism pins from `PIN_NAMES` (`sound`, `dead_frames`) | yes |
| 6 | `save`: the boot save arrays `totem_parts`, `keys`, `seal_parts` (`SAVE_SLOTS`) | yes |
| 7 | `rng: {seed, split}`: the gameplay RNG state and the cosmetic split | yes |
| 8 | `rng.cosmetic`, `rng.fp` (the other two generators), and the `seam` block (`SEAM_BOOT_SPEC`) | yes |
| 9 | `at` on a persistence clear: the clear is applied at that tick, witnessing a clear the game makes by play | no (model only) |
| 10 | `despawn`: `[{level, id, at, note}]`, a body the game removes on its own at tick `at` | no (model only) |
| 11 | `tick0: {rng, seam}`: the measured state at tick 0 of a fresh boot | no (model only) |
| 12 | `hold: true`: freeze the room at the seam latch until the next `botStart` | yes, on builds declaring `hold` |
| 13 | `profile: {id, md5}`: the physics profile the tape was recorded against (the tape-envelope document in this directory) | no (model only) |

Live in `fixtures/tapes/` today: versions 3 to 11 (no committed tape is at 1, 2 or 12). To tally them, read `tape_version` across `fixtures/tapes/*.json`, skipping `index.json`.

**Model-only fields never cross to the game.** `gameVisibleTape()`, the tape handed to `botLoadTape`, drops `GAME_VISIBLE_DROPS` (clears with `at`, `despawn`, `tick0`, `profile`) and reports the newest version whose features survive; `Bot.as` accepts 1–8 and 12. A v9 `at` or v10 `despawn` states what the game does by itself, and a game that consumed it would no longer be checked. `tapeFormat.test.js` pins the projection, so a new field fails until it is classified.

### The relaxations (v2)

`noDamage`, `noHazards` and `grants` are required from v2 because each selects which experiment both consumers run.

- `noHazards` is a set, not a boolean, so hazards can be re-armed one at a time. Names rather than tile-type ints, so a fixture says what it disables. A coerced hazard becomes Ground (`COERCED_TERRAIN_STATE = 0`).
- **The coerce applies to what the physics consumes, never to what the resolver stores.** `Player._state` keeps the raw tile type, so the `_s != _state` change gate, `lastState` and the splash comparison are identical with the flags on or off; only the effect sites read through `Bot.coerceState`. **Note:** one effect site is the per-tick `moveSpeed = moveSpeeds[...]` assignment in `Player.update`, which a "guard the setter" patch misses.
- **A grant fires on the first observation tick whose level matches** (in JS: at construction and right after a world swap; in `Bot.as`: right after pushing the observation), first entry only, since `health` adds to `hitsMax`.
- **Grants are property writes only.** `Game.setPersistence` is not called: persistence tags are a cross-level namespace the endgame reads (`Scenery/FinalDoor.as` reads level 114's tag 0), and an arrival-tick grant is too late to despawn that visit's pickup anyway.
- With `noDamage: false` the JS run prices enemy contact; with it on, `Player.hit()` returns before sound, shake, knockback or death. **Note:** `noDamage` does not make every enemy harmless; see *Roles* below.

### Persistence clears, equips and save arrays (v3, v4, v6)

- A clear is `{level, tag, note}`. There is no way to set a flag true from a tape, because a crutch that could write either way could forge an ending. A negative tag is refused: entities use -1 for untagged and every reader guards `tag >= 0`, so the clear would do nothing.
- `equips` is applied right after grants. The slot bound is checked against the mirror by the engine and against the game's `inventory_slots` by the differential. Slot order follows `Inventory.addItemsFromSave` (sword, fire, wand, spear; `inventorySlotsFor`), not item-id order.
- `save` is a boot presentation, not a grant: `Bot.botStart` applies it before the first world is built, because `BossTotemPart.check()` and `BossKey.check()` remove themselves when the player already holds their index. **Warning:** `seal_parts` is an ordered log, not a set of flags. `SealController.getSealPart` writes into the first slot still holding -1, and `hasAllSealParts()` tests only the last slot, so the array's slot is the ordinal and its value is the seal identity.

### Determinism pins (v5)

A pin selects which vanilla-reachable execution a run gets and creates no unreachable one, so a recording made under it is still a real-game run.

- `sound` makes `Music.soundPosition`, `soundIsPlaying` and `soundPercentage` read a frame clock (one step per engine update at `PIN_FRAME_RATE = 60`) instead of the live Web Audio mixer. Water and lava couple swim speed to `soundPosition("Swim")`, so an unpinned wet tick is not reproducible; `playerPhysicsV2.step` refuses a wet tick on a tape without the pin. `swimSoundClock.js` is the JS half of the same arithmetic.
- `dead_frames` makes `Game.blackCover` decay per update rather than per render, so a room fade costs a fixed number of dead frames.

### The RNG state (v7, v8)

`Math.random()` in the recompiled build is one global 31-bit XOR-shift LFSR whose state is a single uint32 (`SWFModernRuntime/src/avm2/avm2_number.c`). A page is reproducible, but the stream position is the whole page's history (three draws per `Tile`, one per `Enemy`, and so on), and some rooms' gameplay reads a draw (the Owl's `FinalBoss`, `RockFall`).

- **`seed`** is written into the generator by `botStart` after the boot world is built, so the tape owes only the draws its own window makes. 0 means "inherit the page's stream" and is not a reachable state.
- **`split`** routes cosmetic draws (sprite frames, particles, sound indices, the camera jiggle) to a second generator: the fork calls `Rng.cos()` instead of `Math.random()` at those sites. With `split` false, `Rng.cos()` is `Math.random()`.
- **The bound is `0..2147483647` (`RNG_SEED_MAX`)** for two reasons: the n = 31 tap `0x48000000` keeps every reachable state in `[1, 2^31)`, and the runtime's `JSON.parse` coerces an integral Number to int32, so 2147483648 would arrive in `Bot.as` as -2147483648.
- v8's `cosmetic` declares the second generator (meaningful only while `split` is on), and `fp` FlashPunk's own LCG (`FP._seed`), which no gameplay reads; it is declared and compared, bounded at `RNG_FP_SEED_MAX = 2147483646` because the `FP.randomSeed` setter clamps there. The fork reads it through `FP.randomSeedLive`, since the `FP.randomSeed` getter is a stale mirror.

**Warning:** classifying a draw as cosmetic is the risky half, and errors are silent. `Tile.addGrass`'s blade positions look decorative but are gameplay (`Grass` has a hitbox and `cut()` increments `Main.grassCut`), and the camera jiggle gates `Enemy.update`'s `onScreen()`. Route a site to `Rng.cos()` only when the drawn value's only readers are `render()`, a `Draw` call, an audio channel, or nothing.

The runtime hooks are `swfmodern.Rng` (`state`/`setState`, `cosmeticState`/`setCosmeticState`, `cosmetic`), looked up with `getDefinitionByName` so a build without them throws. `botRngProbe(seed, count, cosmetic)` samples the stream and restores it; it is `rng.js`'s oracle, via `scripts/procgen/probe-seedling-rng.mjs`.

### The seam block and continuations (v8, v11, v12)

A playthrough is recorded as a chain of segments, and the director (`director.js`) plays them as windows on one page. The seam claim is that segment N+1's boot equals segment N's latch.

- **`seam`** carries boot state no earlier block could express (item flags applied before the first world builds; counters such as `hits_max`, `time`, `grass_cut`, `menu_state`). Its schema is `SEAM_BOOT_SPEC`; `Bot.botLoadTape` states the same bounds. `modelled: false` entries are compared at the seam but not simulated.
- **`tick0`** is the state at tick 0 of a fresh boot, measured by a zero-tick run. A continuation window never rebuilds its world, so the page writes this measured state rather than the pre-build declaration.
- **`hold: true`** freezes the room at the seam latch until the next `botStart` (no body steps, `Game.time` and the mixer stop), so the frames between windows do not step it. It needs a build declaring the `hold` capability in `builds.json`, and the director stamps it only on a window with a successor (`holdingWindowTape`).

**Warning:** a tape that is too large kills the game with `heap_alloc(...) failed - out of memory` before the first tick. Span count and JSON bytes are independent ceilings (`scripts/procgen/probe-seedling-span-ceiling.mjs`), so `TAPE_BUDGET` limits both and `assertTapeWithinRuntimeBudget` throws at synthesis time.

## How the game is driven

`Bot.as` is a generic, data-driven tape interpreter: one AS3 edit costs the whole build pipeline, so behaviour lives in tapes and JS and the interpreter changes rarely, in batches. Input needs no patch: `Input.enable()` registers FlashPunk's listeners on `FP.stage`, so a `KeyboardEvent` dispatched there drives input on the hardware path.

The hook is `Bot.update()` at the top of `Main.update()`, above `super.update()`: after the previous frame's `Input.update()` cleared the edge queues and before `World.update()` reaches `Player.input()`. An injected event is live for exactly one frame.

The control surface is registered by the bot as ExternalInterface callbacks and auto-wrapped by the page shim as `__swfBridge.game.*`:

| Verb | Does |
|---|---|
| `botLoadTape` | validate and load a tape; returns `ok` or `error:<reason>` |
| `botStart` | apply the boot block (re-booting only when the construction args differ) and arm the bot |
| `botStatus` | the live readout: tick, position, items, flags, counters |
| `botDrain` | the buffered observation stream (drains on read) |
| `botReset` | forget the tape (it cannot rewind the game) |
| `botMobiles` | enemies, pods and other movers |
| `botRngProbe` | sample the RNG stream and restore it |
| `botSeam` | the seam signature readout |
| `botLoadLevels`, `botLevelSet` | deliver a level set in chunks; read the mounted set back |
| `botForgeSaveStamp` | overwrite the level-set stamp on the save (a test lever) |

None of this needs a change to `BridgeGeneric` or to `games/seedling.json`.

## The bookkeeping contracts

Each of these is a place where a tidy-looking implementation turns every differential red for a reason that has nothing to do with physics.

**Record, then act.** The only hook is before the movement, so the bot records the state it can see (the result of the previous tick) and then dispatches this tick's edges. Observation `t` is the state after exactly `t` completed movement ticks: index 0 is the boot position under no input, and an N-tick tape yields N+1 observations. `tapeRunner.js` mirrors this.

**Dead frames do not consume tape.** `Game.update` skips `super.update()` while `blackCover > 0` (about 18–20 frames after every world load), and `Mobile.mobileUpdate` skips movement while `Game.freezeObjects`. The tick counter gates on both, so a fade that varies by a frame run to run is harmless.

### The transitions contract

`transitions` is `[{ t, from_level, to_level }]`, where `t` is the first observation tick whose `level` is the new level. The arrival position is already `ticks[t]`. Teleporter identity is excluded because the AS3 bot cannot observe which teleporter fired, and a field only one side knows cannot be checked.

Within one tick (transcribed in `tapeFormat.js`'s docblock, as a contract both consumers share):

1. **Teleporters update before the player.** `World.addUpdate` prepends, and `Game.loadlevel` adds the player before the teleporters, so a trigger tests the position the previous tick left.
2. If one fires, the old player still runs this tick's full movement in the old level: `FP.world = new Game(...)` only records a `_goto`, and `Engine.checkWorld` defers the swap to end of tick.
3. The swap lands at end of tick: a new `Game` whose `Player` is constructed at `(playerx + 8, playery + 8)` with zero velocity and a fresh terrain state, while held keys carry over (FlashPunk's `Input` is static and no teleport path calls `Input.clear()`).
4. The `blackCover` frames that follow are dead frames.

So there is no intermediate observation on a crossing tick: in `transition-west-return`, tick 60 is level 0 and tick 61 is already (296, 168) in level 94. The old player's last step is never observed but is modelled, because the game runs it.

**The game's side of the field is derived, in one place.** `botDrain` returns `transitions: []` unconditionally. The harness derives the game's entries from the tick stream with `tapeFormat.deriveTransitions` (via `gameStreamFromDrain`), on both the record and compare paths. The JS engine derives its own entries from its world swap, never from the level field; if both sides read the level field, the transitions diff would compare the tick stream with itself. The harness also checks that `botDrain`'s own field is still empty, so a future build that reports transitions is a named failure rather than something the derivation overwrites.

Derivation happens at record time, so a committed expectation states its crossings in reviewable form. The differ compares entries exactly, not by count.

## The level is injected, never loaded

Nothing in the engine reads the atlas. The caller passes `levelSource(level) -> record`: `levelSource.js` holds the node-only `atlasLevelSource()`, and `levelSourceFromAtlas(atlas)` is the browser-usable one. `buildLevelWorld` transcribes the `loadlevel` subset over that record, and the runner memoises what it builds.

A record source rather than a prebuilt world, because the runner must build worlds for levels nobody named at call time (a teleporter's destination), and `buildLevelWorld`'s throws should fire when a run walks into a level, naming it, rather than eagerly for all 116.

`opts.levelSource` also selects the engine. Without it you get the v1 engine (stub terrain, no collision), which refuses a `noclip: false` tape. With it you get v2, whose sweep is on or off as the tape says.

Two facts about the record: tile rows are tile-space while entity x/y are pixel-space (in a `[x, y, tx, ty]` row, `tx` is a pixel offset into the tileset strip, so `tx/16` is the column), and the extract has already applied `loadlevel`'s out-of-bounds guard, recording what it dropped in `tiles_outside_level`. Do not re-filter, and do not un-filter.

## The physics, and the things the source will mislead you about

`playerPhysicsV1.js` and `playerPhysicsV2.js` are a transcription, not a model. Per tick: teleporter triggers → `getState()` → friction and speed selection → `friction(); input(); moveX(); moveY()` → world clamp → the end-of-tick swap, if one fired.

1. **`input()` overshoots; it is not a clamp.** The branch is `if (v.x < moveSpeed) v.x += accel` with `accel === moveSpeed`: a threshold test followed by a full-magnitude add. Velocity settles into a roughly 3-tick limit cycle peaking near twice the "cap". Holding right from the spawn, the game reports x = 88, 92.09999999999998, 99.15 at ticks 0, 4 and 10, and the JS engine emits the same doubles.
2. **Friction is vector-length, not per-axis.** `v.normalize(max(v.length - f, 0))`, then components under 0.05 snap to zero. Both axes accelerate independently but only one friction quantum leaves the combined length, so a diagonal covers about √2 the ground of an axis-aligned run.
3. **`Player` overrides `Mobile.moveX`/`moveY`.** The base-class movers are dead for the player, so the noclip flag lives in the `Player` overrides; patching `Mobile` is a silent no-op.
4. **The clamp reads the level size, not the screen size.** `Game.loadlevel` overwrites `FP.width`/`FP.height` from the level file on every load, so level 0 (320×320) clamps to x ∈ [2, 318], not the [2, 158] that `Main.as`'s 160×160 screen implies.
5. **The player does not spawn at the constructor's coordinates.** The `Player` constructor re-centres onto the tile (`+Tile.w/2, +Tile.h/2`), so `new Game(0, 80, 128)` puts the entity at (88, 136). A tape's `boot` block carries the constructor args and the offset is applied on top.

### Collision: solid geometry is entities, not a grid

FlashPunk's `Grid`/`Tilemap` masks have zero call sites. `loadlevel` builds one `Tile` entity per 16×16 cell from the `tiles` layer via a switch on the tileset column; the entity position is the cell centre and the hitbox covers the cell. Solidity is a deferred type flip: every Tile is constructed with `type = "Tile"` and its first update sets `type = Tile.types[t]`, marking t ∈ {2, 9, 11, 14, 15, 19, 20, 23, 24, 27, 34, 35, 36} `"Solid"`. The player's solid list is `["Solid", "Tree", "Rock", "Rope", "ShieldBoss"]` plus `"LavaBoss"`, pushed unconditionally in the constructor.

The sweep is 1-px steps, `collideTypes(solids, x + d, y)` per step, X fully resolved before Y. Facts only the running game settled:

- **On a hit the loop returns and the caller discards the entity.** Position stays at the last free step and velocity is not zeroed; it decays through `friction()`, so in `collide-up-rock` the player later creeps from y = 130.5 to 130.05.
- **The stop is mid-pixel.** `d = min(1, |rel|) * sign`, so resolving to a tile edge or an integer is wrong by half a pixel.
- **Sub-pixel moves do sweep.** `for (i = 0; i < Math.abs(_xrel); i++)` executes for `_xrel = 0.8`.
- **The first-tick type flip is modelled** (`beforeTypeFlip`), and only tiles are late: every object class assigns its type in its constructor. The tick is per world, not per run, so the tick after an arrival is the destination world's first live tick.
- **`Rectangle.intersects` is positive-area only** (`SWFModernRuntime/src/avm2/avm2_text.c`, behind an isEmpty guard on both rects, the same comparison `Entity.collide` makes). One `rectsOverlap` predicate serves both the sweep and the terrain gate.
- **Pixelmask colliders** (Building, TreeLarge, SnowHill, TentacleBeast, OpenTree, Statue, CliffSide) collide by bitmap, from `seedlingPixelMasks.js`. The planner still uses the mask's bounding rect, a conservative over-approximation, while the physics uses the bitmap. An `ENTITY_CLASSES` entry with `collider: 'pixelmask'` and no `mask` throws by name rather than silently becoming a rect.

### The terrain resolver

`Player.getState()` is not a pure function of position. Four properties, all transcribed:

- **Sticky.** `state` is assigned only when the candidate tile's rect intersects the player's probe rect; otherwise the previous state persists. Only a world swap resets it.
- **Nearest walkable tile, by centre distance.** `nearestToPoint` with the default `useHitboxes = false` measures to entity x/y, i.e. tile centres. Solid tiles have left the `"Tile"` list after their type flip, so `state` can never become a wall type.
- **Strict intersect.** Touching edges with zero overlap area do not intersect.
- **`checkOffsetY = 1`** (`height - originY - 2` for the 4×5 box). The probe point is `(x, y + checkOffsetY)` and the probe rect is the player's box shifted down by the same pixel.

Terrain typing runs every tick independently of collision, so `noclip` does not bypass it. The tile types the resolver accepts are `levelWorld.MODELLED_TILE_TYPES`; anything else throws when the player stands on it. Water, pit, lava, ice and waterfall are modelled; water and lava additionally need the `sound` pin. Bridge (29) is walkable only while the run's `openBridges` set holds it.

`getStatePos` is a different function: no intersect gate, returns -1. Do not conflate it with `getState`.

**Note:** level 0's spawn tile is Brick (t = 3), not Ground. The observation stream cannot tell, because both walk at 0.8, so the test asserts the resolver's own answer. "The streams match" is a weaker claim than it reads.

## The pit transport

A pit is not a floor with a speed. Standing on one starts a three-phase transport the game drives and the player cannot steer, and every frame of it is a live observed tick: `receiveInput = false` stops input, not the tick counter.

Pits are the only way into the underworld cluster that holds `darkshield` (L74) and `darksuit` (L79). `pit-fall-83` (pit live) and `hazard-boot-pit` (pit coerced) are a contrast pair.

**The edge** fires inside the `state` setter, so only on a raw change (`_s != _state`), only while `onGround`, and it reads the coerced value. `fallInPitPos` is the pit tile's position, the cell centre. **Warning:** the edge fires before the movement, and `receiveInput = false` is set after it, in `checkFallingInPit`, which runs after `super.update()`. The edge tick still accepts input; refusal starts on the next tick. A transcription that kills input on the edge tick diverges on tick 1 of every fall.

**The fall-out is exactly 20 ticks.** `alpha` starts at 1 and does `-= 0.05` per tick; twenty repeated double subtractions land just below zero, while `1/0.05` gives 21, so transcribe the subtraction. The lerp moves one tenth of the remaining offset per tick toward `fallInPitPos`.

**The swap** is the same deferred end-of-tick swap as a teleporter, a new arrival kind in `levelRun` rather than a second implementation. The destination comes from the level's `control` parameter block.

**The descent is always 83 px and 41 ticks, in every level.** `Player.check()` runs on the new world's first frame, above the `blackCover` gate, and reads the camera `loadlevel` just set from the player's own position, unclamped: 160/2 + (5 − 2) = 83.

**The landing polarity is inverted from the obvious reading:**

```as3
if (bouncedFromCeiling || getStatePos(x, yStart) == 6 || == 1 || == 17) land;
else { y = yStart; v.y = -2; bouncedFromCeiling = true; }   // BOUNCE
```

You cannot bounce on a hole or a liquid, so ordinary floor is the case that bounces, once, at `v.y = -2`, for 39 ticks. `getStatePos` is not routed through the coerce, so the landing check reads the raw tile type while the physics reads the coerced one: a fall that lands on coerced Ice bounces.

**L84 is a pass-through.** The `83 ⇓ 84` arrival lands in a 3×3 block of pit tiles and falls again on the next tick. It has no walkable neighbour, so a router that demanded one would call darkshield and darksuit unreachable; a pass-through leg has zero targets, zero input spans and an automatic exit.

**Pit tiles are forbidden floor to the planner.** In levels with no `control` block (Dungeon 6 and most of Dungeon 8), `checkFallingInPit` calls `die()`, and `playerPhysicsV2` throws. `exit: {pit: {tx, ty}}` is the driver's single exemption. The driver emits no input inside a transport window, and the harness reads `saw_input_refused` two-sidedly: a transport requires refusal, and no transport means refusal is a defect.

These throw rather than being transcribed: a teleporter trigger overlapping the player during fall-out or descent, a second pit edge while a fall is pending, and a trigger tile that is also a pit tile (which fires wins is FlashPunk bookkeeping; the planners refuse the two in the extract, L43 → L37 and L100 → L101).

**A `Pull` current can carry the player into a pit** (U12-swim). `Pull.update` writes `e.x += force·cos(dir); e.y -= force·sin(dir)` on every overlapping Player, Enemy and Solid, every frame. It does not call `moveBy`, test solids, call `hit()` or check a freeze gate. `loadlevel` adds the pulls after the Player and the chasers, so they update before both, in reverse `.oel` order, and each pull tests the box the previous one moved. A box straddling two cells of one current is therefore pushed twice in a frame. `levelRun.stepPullsNow` is that step, placed between the pulsers and the arrow traps; `previewStepper` applies the same push. L12's 14 pulls ring its one pit (36,43). Every push points into another pull cell or the pit, and every current drains into it. In `u12-pull-carry` a standing player rides 1 px/tick (2 px on t7–8 and t21–22), the edge fires on t35, the push still lands in the fall-out while the box touches `pull@576,672`, and the swap comes on t55. `u12-pull-cross` is the perpendicular walk. Refused by name: a stepped body on a pull, a room with pulls and pushables or spinners, and a push that leaves the box in a solid.

## Roles: what the entity census answers

`buildLevelWorld` classifies each entity tag per role and throws only for a role the caller says it consults:

| Role | The question | Who consults it |
|---|---|---|
| `blocking` | does it stop the sweep? | a `noclip: false` run |
| `trigger` | does it swap the world? | everything |
| `pickup` | is it a walk-over item? | a relaxed walk's planner |
| `proximity-hazard` | does approaching it freeze the game, move the player, or consume gameplay RNG, with no key pressed? | a relaxed walk's planner |
| `combat` | hit points, aggro reach, what kills it (from `combat.js`) | runs that ask for it by name |

`RELAXED_ROLES` is the three a noclip walk consults, `PRE_R5_ROLES` the four-role default, `ROLES` all five. Classification is an affirmative act: an `ENTITY_CLASSES` entry lists the roles it answers for, with a source citation, and an absent tag throws for every role. The census covers all 137 tags in all 116 levels, because a missed trigger is an exit that silently does not exist and a missed proximity hazard reads as "the physics diverged". A hazard's disposition (`hazardDisposition`) is `'unpriced'` (the builder throws), `entry`, `inert`, or a volume.

Facts the census rests on:

- **`lightalpha`, `snow`, `blur`, `blur2`, `control` and `droplet` are not entities.** `loadlevel` reads them with `hasOwnProperty` or as parameter blocks.
- **Every placed `Pickup` subclass is `special` with text.** Walking over one sets `Game.freezeObjects` and spawns an NPC dismissed only by `Input.released`. Unless the run models the ceremony, a pickup is an avoid volume, not something a route may clip.
- **`keyNeeded` is assigned in exactly one place**, `NPCs/Watcher.as` (`keyNeeded = !Game.checkPersistence(tag)`). A fresh boot fills `levelPersistence` with `true`, so a Watcher with `tag >= 0` auto-talks within 24 px, and all eleven watchers in the extract carry `tag >= 0`.
- **A tagged, non-inverted teleporter is deactivated on a fresh boot** (`tag >= 0 && (!checkPersistence(tag) == invert)`).
- **`Bot.noDamage` does not make enemies harmless.** It guards `Player.hit()`, the whole damage path, but `LavaTrap`, `Whirlpool`, `Pull`, `IceTurretBlast`, `ShieldLock`, `Pod` and `BossTotem` write the player's position or input state directly. They are classified as proximity hazards and routed around; no flag covers them. `Pull` is the one of them the model now steps (U12-swim, below).

**Note:** the route planners pin the levels their rung could not build by name (`FROZEN_UNBUILDABLE`), so widening the census cannot make `--write` re-author a committed route.

## The acceptance signal

A run without a terminal assertion is a demo, not a result. `botStatus` reports live off the game's statics, and the differential checks every tape against it (`checkReadout` in `check-seedling-bot-differential.mjs`):

- `items`: the 14 item properties (`ITEM_PROPERTIES`), 13 booleans plus `hitsMax`, an int that `health` adds 1 to over `Player.hitsMaxDef` = 3. All 14 are checked, positives and negatives; a check that asserted only the granted item would pass a build that granted all fourteen.
- `grants`: a sticky list of `{t, level, items}`, compared tick for tick with what the tape asked for.
- the inventory slot array and `Main.primary`, against the mirror.
- `cutscene` and `menu`: the win statics, which must stay false unless the run takes the ending.
- the persistence flags (bosses, watchers, touch-locks, the FinalDoor): every one the run earned is written, every other one untouched.
- `saw_auto_advance`, the freeze arrivals the bot's auto-advance dismissed, must equal the model's count (`autoAdvanceArrivals`). Higher means the proximity census missed a dialogue freeze.
- the dead frames the game spent must be the ones the model accounts for, which catches freezes the auto-advance cannot see.

The readout itself must be present, or every other assertion would compare undefined with undefined.

**The JS mirror supplies the expectation; the game supplies the answer.** Reading the mirror for both would be the mirror agreeing with itself.

**Note:** the talk key is X (88), not V. `NPC.talk()` reads `Input.released(p.keys[6])`, and index 6 of `[RIGHT, UP, LEFT, DOWN, X, C, X, V, I]` is the second X. V is index 7 and opens the inventory, which would freeze the game rather than unfreeze it.

Across tapes, `checkAcceptance` adds the rung findings (`r2Acceptance` to `r5Acceptance`) and the chain findings from `playthroughAcceptance` (every seam: boot of N+1 equals latch of N).

## The seams that are loud on purpose

Each of these is a throw, not a fallback. An over-throw is a loud "move the fixture"; the quiet alternative is a divergence nobody sees, or a model that agrees with the game only where the fixtures happen to look.

- **Two teleporters firing on one tick.** `FP.world =` only records a `_goto`, so the winner is whichever updates last, in FlashPunk's prepend order, which is not transcribed. This is live: level 0's west pair sits at (0, 128) and (0, 144), and a player whose y lies in (141, 146) overlaps both.
- **A teleporter targeting its own level.** The game side derives transitions from the level field, so a same-level teleport is invisible there. None of the 280 triggers in the extract (228 `teleporter`, 26 `stairsdown`, 26 `stairsup`) self-targets.
- **An unclassified entity tag.** Add it to `ENTITY_CLASSES` with its `Game.as` construction site and `setHitbox` args rather than assuming it does not collide.
- **An unknown layer name.** `loadlevel` builds `tiles`, `objects` and `cliffsides` only.
- **Terrain outside `MODELLED_TILE_TYPES`**, and a wet tick without the `sound` pin. (Drowning and a fall into a pit with no `control` block used to throw here; since R3-swim they are deaths the run reboots, below. A PREVIEW still refuses them with the old words.)
- **Enemy contact the run does not price** (`levelRun`'s contact refusal names the body as `type@x,y`).

**Deaths are the game's.** Every death is `Player.die()`: `dying = true; restartLevel()`, and `restartLevel()` is `FP.world = new Game(level, playerPosition.x, playerPosition.y)`, the current world's ctor args, swapped at the end of the tick, with no transition record. `levelRun` runs all four through one reboot (`pendingDeath`, `playerDeaths`): a hit that reaches `hitsMax` (the death tick has no physics); a fall into a pit with no `control` block (`checkFallingInPit`'s `else die()`, after the tick's move; `r3-pit-death`); drowning, water without the conch or lava without the dark suit (`r3-drown`, `r3-lava`). The drown spiral starts the tick AFTER the latch, and `drown()` sets `dying`, which skips `super.update()`: the player stands still for the twenty spins and the twentieth is the death. Lava also calls `hit(null, 0, null, 0)` every tick before the latch, so its first tick opens the 20-tick i-frame (no steering) and adds 5 to the shake. A death inside the BobBoss fight reboots the fight (`r3-bobboss-death`): the rock's flag is a `Game` static, so the new `Game` builds it fallen, its first live frame re-adds the boss, and the respawn is the rock's own `playerPosition` write, (72,104). The respawn's `Player` draws `fallSpinSpeed` from FlashPunk's Lehmer generator, which only a graphic's angle reads, and the model consumes no RNG stream outside L112, so no death owes the model a draw.

**A static body's arrow death is the game's too** (fidelity F4, `enemyDamage.STATIC_ARROW_DEATH`). An arrow calls `Enemy.hit(5, p)` on every `"Enemy"` it overlaps, a static census body included. For `SandTrap`, the one class read off the game (`f4-l8-sandtraps`), `levelRun` keeps the body's damage state (`staticBodyStates`): one damage per landed arrow, 30 i-frames that only the body's own update (behind `onScreen`) runs down, and no knockback. The third hit plays "die" (19 updates, the first on the killing tick), and `endAnim` removes the body. The removal edits the level record at the top of the next tick, and `removed()`'s write of the tag goes through the declaration if the tape owns the slot, through the scratch layer in a scratch run, or into the next build's earned clears otherwise (`run.staticBodyDeaths`). L8 kills `sandtrap@96,80` on t230 and removes it on t248; the solver plans the room from any boot state, because a cleared tag builds the room without its body. Every other static class still stops the arrow and takes nothing, and the solver refuses its death by name (§11.4).

The rule this keeps re-teaching: **do not let the JS clean up the game.** The first-tick type flip, the sticky state, the discarded collision return and the strict `Rectangle.intersects` are all transcribed verbatim, and the oracle arbitrates. Every divergence so far came from a description tidier than the code.

## The driver

`botDriverV2` plans A\* over the walkable tiles of the current level, smooths the waypoint chain, and executes each waypoint with a bang-bang controller driving the real `step()` with collision on. Two rules keep it short: **simulate, don't solve** (velocity is not proportional to anything convenient, so a closed form would be a second model of the physics), and **the tape is the artifact** (tests re-run the emitted tape through `runTape` rather than trusting the planner's running state).

**The controller is 45°-then-axis, not straight-line.** Both axes accelerate by the same quantum under vector friction, so while both are held they advance at the same rate: the player leaves a waypoint at 45° and straightens out once the shorter axis arrives. Smoothing greedily while the straight segment stays clear puts the player in the lake. `controllerPathClear` models the two legs actually traversed. It stays approximate in two bounded ways (the X-first intra-tick corner, and up to one accel quantum of overshoot, absorbed by the 6 px between a tile centre and its edges), and the executor's throw makes the approximation safe.

**The geometry has two faces.** The physics uses `collidesSolid`, which throws; the planner uses `levelWorld.plannerBlockerAt`, the same geometry without the throw and strictly wider (it also reports unmodelled terrain). Teleporter volumes and pit tiles are planning policy in `botDriverV2.plannerObstacleAt`; a leg's own `exit` is exempt.

**It refuses rather than recovers.** A wall hit en route to a waypoint is a planner bug and throws; it never re-plans quietly, because silent re-planning is how a geometry disagreement with the game stays hidden. The same goes for an unrequested transition, a leg that starts in the wrong level, and an `exit` whose teleporter does not go where the next leg says.

`contacts` lets a leg declare the volume its arrival already stands in, and the planner exempts exactly that. `extraVolumes` adds a volume the static census cannot know because the route created it (a `buttonroom` in L38 arms L37's `FallRock`).

**Cross-level legs:** a task is `[{ level, targets: [...], exit?: {x, y} }]`. The driver walks the targets, then into the teleporter at `exit`, and asserts it arrived in the next leg's level. The caller names the teleporter; the driver never searches the teleporter graph.

**`levelRun.js` is the one swap** (arrival offset, zeroed velocity, reset terrain, pre-armed latch, the destination's `beforeTypeFlip` tick), shared by driver and runner. Two copies could be wrong together and still reconcile against the game.

For a synthesized fixture, "the driver still emits this tape" turns any geometry error into a red, because the plan depends on the geometry.

**The solver above the driver** (`solverBot.js`; the as-built record is the log's per-slice sections, R3-swim the latest). ## Running it

```bash
# 1. dev server at the repo root (check first; do not double-start)
ss -ltn | grep ":8000" || python3 -m http.server 8000

# 2. the staleness gate: the live game against the committed recordings (headless)
node scripts/procgen/check-seedling-bot-differential.mjs --tier=fast

# 3. re-record after a deliberate physics or fixture change
node scripts/procgen/check-seedling-bot-differential.mjs --record \
    --only=collide-up-rock,transition-west-return
```

| Flag | Does |
|---|---|
| (none) | replay the default tier (`full`, the whole roster) and compare |
| `--tier=<t>` | `fast` (tapes of 600 ticks or fewer), `gate` (everything but `LEGACY_TAPES`), `full`, or a comma list of the categories `campaign`, `map-walk`, `mechanic` (`fixtures/tiers.js`). `legacy` is deprecated. An unknown name is refused before the box lock |
| `--only=a,b` | restrict the sweep to these tapes; a misspelled name is a named failure |
| `--record` | write the streams as oracle recordings (`expectations/<name>.json`) |
| `--resume` | reuse a stored PASS from `test-results/seedling-differential/checkpoint.jsonl` when its fingerprint still matches |
| `--shard=i/n` | replay shard i of the tier's n-way partition; refused with `--only=` |
| `--shard-plan=n` | print the partition and exit (no browser, no lock); add `--json` for CI |
| `--win` | drive real-GPU Windows Chrome instead of headless Chromium |
| `--wait-for-box=<sec>` | queue for the box lock instead of refusing |

It drives the build `builds.json` marks `default` (`seedling_bot_ap_p4f`); `SEEDLING_PAGE=<build directory>` drives another pinned build, such as the `control` one. The payload filename is read from `game.html`'s `<script src>`, because it does not always match the directory name. Without the `frontend/modules/flashPanel/wasm/` submodule checked out it prints `SKIP` and exits 0.

**Always pass `--only=` when recording.** `--record` does not compare before it writes, so without it a genuine drift in an old fixture would be baked in instead of reported.

**Every tape gets a fresh page.** `botReset` forgets the tape but cannot rewind the game, so a second tape on the same page starts from the wrong position and records plausible garbage.

**The checkpoint fingerprint is deliberately blunt.** It hashes the script, the Windows driver, every `.js` under `seedlingDemo/` (fixtures included), the tape and expectation, the atlas, the wasm and `game.html` bytes, and the channel, so any model edit invalidates every stored PASS. A stored FAIL and anything under `--record` are never reused.

**Replay deadlines scale with tape length** (`SECONDS_PER_FRAME`, plus `LOAD_ALLOWANCE_SEC` per world load, because a heavy room's load is one long frame of CPU work). A fixed deadline looks exactly like a dead bot.

### Headless is the default; `--win` is opt-in

Headless runs this machine's Chromium with `HEADLESS_LOGIC_ONLY_ARGS` (`scripts/procgen/headlessChromium.js`): the WebGPU device is lost on purpose at the first present, so there are no pixels and the game ticks at roughly 30 per second. The differential reads state, never pixels. `assertLogicOnlyChannel` (`scripts/procgen/seedlingChannel.js`) proves the device is lost before the first tape and refuses otherwise; the run prints `CHANNEL: headless logic-only`.

Gates whose claims assert zero page errors (`check-seedling-wasm-pages.mjs`, `check-seedling-wasm-ship.mjs`) use `HEADLESS_WEBGPU_ARGS` instead, which keep the device alive. Its Vulkan pair must stay in one `--enable-features=` switch, because Chromium keeps only the last one; `headlessChromium.js`'s docblock says what each flag is for.

`--win` drives real-GPU Windows Chrome from WSL through `/mnt/c/Windows/py.exe -3.12` and `scripts/procgen/seedling-bot-replay-win.py`; use it for pixel questions. The physics is identical on both channels, but neither reuses the other's checkpoint.

Windows Python cannot take Linux paths, so the driver and its files are staged under `C:\playwright\` (`/mnt/c/playwright/`); all fixture and diff logic stays on the Linux side. Each replay prints `WEBGPU_ADAPTER:`, writes the whole `botStatus` every second to `C:\playwright\progress-<tape>.json` (so a frozen game is distinguishable from a slow one), and on failure prints `REPLAY_FAIL` with the last 25 page log lines. The general recipe is SWFRecomp-CC's `tools/divergence/perf/WINDOWS_PLAYWRIGHT_FROM_WSL.md`.

### The full tier in CI

The whole roster runs in CI only on demand: `.github/workflows/seedling-full-tier.yml` (*Seedling full tier (manual)*), triggered from the Actions tab or with `gh workflow run seedling-full-tier.yml -f tier=full -f shards=10`. Inputs: `tier` (default `full`), `shards` (default 10) and `page` (a `SEEDLING_PAGE` override).

- **plan** runs `--tier=<t> --shard-plan=<n> --json`, which prices each tape (`fullTierEstimate.js`) and packs the roster longest-first into `n` shards (`fullTierShards.js`).
- **shard** runs `--tier=<t> --shard=i/n`, asserts the `CHANNEL: headless logic-only` line and uploads its checkpoint; the cross-tape findings and the live driver task wait for the merge.
- **merge** runs `--tier=<t> --resume` over all checkpoints and goes red unless every tape is reused (`RESUME: 0 tape(s) to replay`). It prints the one verdict line.

Per push, CI runs only the bounded smoke face `--tier=fast --only=friction-stop`. `scripts/procgen/check-seedling-full-tier-owed.mjs` prints what a tier run owes and what it costs on the box and in CI.

## Rebuilding the game after an AS3 change

`build_bot.sh` (in the seedling bot build directory, outside this repo) builds the SWF; its header documents the rest (inject → SWFRecomp → `build_wasm_avm2.sh` → `deploy_wasm_avm2.sh` → copy into `frontend/modules/flashPanel/wasm/`). That directory is the submodule `PeerInfinity/seedling-wasm`: a rebuilt build is committed and pushed there, then the pointer is bumped here in its own commit. A build belongs in the submodule if and only if a tracked file of this repo names it; `scripts/procgen/check-seedling-wasm-pins.mjs` gates the agreement between the manifest, the whitelist, what the submodule tracks and what this repo names. `frontend/modules/flashPanel/README.md` has the add and retire steps.

Budget roughly ten minutes per build and **batch AS3 edits**; that cost is why `Bot.as` is a generic interpreter.

- **A control build comes first.** mxmlc is not reproducible and SWFModernRuntime moves independently, so an edited build's behaviour change cannot be attributed unless the same toolchain, run at unchanged source with `FRESH=1`, has been through the same rows first. The control is a throwaway directory, never committed.
- **The tracked reference and the gitlink bump are one commit.** A tracked file naming a build the submodule does not carry fails the pins gate, and a build nothing names is cleared for retirement. The reference must be in one of the gate's recognised spellings; a path assembled with `join(...)` from a name held in a separate `const` is not recognised. Write it as one literal path.
- **"Flags off must be byte-inert" is a gate.** Before recording anything against a fresh build, re-verify every committed fixture against it. The live driver task passing while the fixtures fail is itself a diagnostic: the driver's tape comes straight from `buildTape` and never goes through `parseTape`.
- `Bot.botStart` sets `Inventory.help = false`, as the game's own debug warps do. Otherwise `Inventory.update` raises a tutorial that freezes the game once the player holds two items, and no tape span can reach the key that dismisses it, because frozen frames are dead frames.

Build traps:

- The `.o` cache keys on mtime, not flags. Use `FRESH=1` after any define change, and after an ABC change: an incremental build can produce a page that dies with `heap_alloc(...) failed - out of memory` before the bot callbacks register, which looks like a harness problem.
- Use `run-SWFRecomp.sh` rather than raw SWFRecomp, or risk a WSL2 VM `bad_alloc`.
- `deploy_wasm_avm2.sh` stages the teleport SWF as `test.swf` unless you pass `DEMO_SWF`.
- mxmlc strips `trace()` without `-omit-trace-statements=false`, and its flow analysis does not credit returns inside `try`/`catch`, so such functions need a terminal return.

## Gates, and what would make them vacuous

- **Vitest (CI):** every tape's JS stream equals its committed oracle recording exactly, `transitions` included. The hand-derived physics and geometry cases are a second, independent stratum, since their values come from reading the AS3.
- **The browser differential:** the live game replays match the recordings, the readout checks above hold, and the live driver task (thread-the-gap plus a cross-level leg, planned at run time) lands the real game on both targets with the crossing at the tick the driver named, asserted from the game's own drained observations.

Both pin observation and transition counts per tape, because a positional assertion alone is satisfiable by a bot that teleports.

The two census gates stay vitest rows in the default tier: the constants census (`seedlingConstantsCensus.test.js`) and the solver-surface census (`seedlingSolverSurface.test.js`). They are not enrolled as `check-*.mjs` roster rows. The user decided this on 2026-09-30 (⚖ Q17). A roster row would be a second instrument for the same claim, and it would owe a standing row of its own.

The fixture leg means something only while the expectations are oracle recordings. `fixtures/regenerate.mjs` writes `*.provisional.json` from our own engine, a bootstrap for a not-yet-recorded fixture; a verifier sharing the generator's assumptions verifies nothing. A test pins that no committed fixture rides that path.

### The bounded vacuities

Some model properties turn no fixture red when mutated away, because the roster never reaches the situation that would show them. Each row names the witness that would close it.

| Property | Why no fixture sees it | The witness that would |
|---|---|---|
| sticky terrain state | a route must reach a tile gap with a previous state whose speed differs from the nearest tile's; the obvious candidate cells in L83 land on an equidistant `nearestToPoint` tie | a tape through a hole cell with a speed-differing previous state |
| terrain state reset on a swap | arrival tiles on both sides of the committed crossings walk at the same speed | a transition whose two sides differ in speed |
| the driver's teleporter policy | the only trigger a committed route approaches is the leg's own exit, which is exempt | a target beyond a trigger tile, forcing a detour |
| the executor's hit-throw | a diagnostic, not a detector | none; keep it, because the alternative is a silent re-plan |
| the executor's avoid-volume throw | the planner's own policy keeps routes clear | a smoothed segment clipping an off-centre volume the tile-centre test cleared |
| the A\* tie-break | the committed routes have no equal-f tie that survives the smoother | a route with one |

The synthetic hand-built grids in `playerPhysicsV2.test.js` are the stratum that sees stickiness today, and they share the generator's assumptions. Saying so is the point.

## Three transcription lessons worth generalising

**A tag missing from a table while its twin is present.** `ENTITY_CLASSES` once carried `stairsdown` but not `stairsup`, the same class and trigger (`Stairs`' third argument only picks a sprite, a sound and a render flag). The guard is a census wider than the fixture levels: every `teleporter`/`stairs*` tag in all 116 levels must be a classified trigger, because a missing one is an exit that silently does not exist.

**An offset applied at one level of a constructor chain but not the next.** `Statue` adds its own offset (+16, −8) before `NPC`'s constructor adds (+8, +8). Applying only the first put level 0's statue collider 8 px off, unnoticed until a better driver routed next to it. "Unobservable" decays as soon as the driver improves; `statue-press` (a planned approach plus a hand-authored press into the edge) now pins it.

**A blocker whose trigger reads only one side.** `BossLock.update` tests the key only against a player on the one-pixel row below the lock (`BossLock.as:62`), so a `kind: 'gated'` row, which the analyzer pays both ways, let the rules v1 playthrough cross 11 of the 14 bosslocks from the side the game refuses (`census-seedling-bosslocks.mjs`; `REFUTATION_LOG` entry 3). The semantics row now carries `probe: 'S'`, and the playthrough generator reads it as the analyzer's `enter` gates (swim T4).

## Dead ends

- **A black canvas means nothing here.** The differential runs logic-only, and pixel readback under headless WebGPU is black even for an untouched page.
- **`A valid external Instance reference no longer exists`**, repeated every frame, is Chromium's WebGPU device-lost message. It is expected on the logic-only channel. Never key a check on that text; detect a live device by behaviour (`__swfPerf`'s frame wall, or `device.lost` still pending).
- **The world clamp is unreachable in level 0.** Walking far enough left loads an adjacent level, so a "clamp" fixture silently tests transitions; the clamp keeps a hand-derived unit case.
- **Cutscenes are already skipped.** The intro fires only from `Game`'s `level < 0` branch, and the boot passes an explicit level; a cutscene that did fire would show in `botStatus`'s `receive_input`.

### The stage machine

Every stage is a named state the readout prints and `__watch.wasm` carries (`WASM_STAGES`); every refusal is a named reason:

```
probe    the build is served (HEAD)          ⇒ wasm-build-missing
runtime  __runtimeReady in the frame          ⇒ runtime-never-ready
start    the user pressed ▶ Start             ⇒ start-never-pressed
levels   (a level set only) botLoadLevels per chunk, then botLevelSet read
         back and diffed field by field       ⇒ set-readback-disagrees
tape     botLoadTape returned 'ok'            ⇒ botLoadTape:<what it said>
running  botStart returned 'ok'               ⇒ botStart:<what it said>
finished botStatus.finished
drain    botDrain, read once: the game's whole observation stream
verdict  the end-state comparison, then the per-tick differential
```

A payload that will not build refuses at a `payload` stage before any of this. A sequence of windows repeats `tape`, `running`, `finished` and `drain` per window, with a `boundary k/n` stage between them (`stagesOf`).

- **`botDrain` is a buffered stream, not a sample**, read once after `finished`. The 250 ms `botStatus` poll sees only a fraction of the ticks, so the per-tick verdict never uses it. The readback is the proof a set mounted, not merely arrived.
- **`"pending"` is the success answer for every chunk but the last.** `botLoadLevels` answers `pending` (accepted, more owed, nothing mounted), `ok` (this chunk completed the set, which is now mounted) or `error:…` (refused; the staged delivery is dropped). A sender must expect `pending` up to the final chunk and `ok` on it; an early `ok` is itself a refusal. The protocol is `deliverChunks` in `flashPanel/seedlingLevelSetDelivery.js`.
- **Consecutive boots on one page are not independent.** `botStart` reuses the world unless the next tape's boot names other construction args, so a second room booted on the same page can read the previous room's roster. A ship is always a fresh iframe, and the button is disabled while a ship is in flight.

### The end-state verdict

`end state: agrees` says the real game ended where the JS model ended: same level, position within the tolerance, and an item set that is a superset of the model's. It is printed with its bound: *end state only — two runs can meet on the last frame having disagreed on every tick between.* It is not a certification.

The other answers are answers, not absences: `disagrees (…)` with every difference named; `no expectation (manual)`; and `not finished (<the refusal's reason>)`.

**The tolerance is 0 px** (`END_STATE_TOLERANCE`), because committed tapes agree exactly, floats included. A live `botStatus` read coasts past the last frame of a run that ends moving, so the comparison reads the drained final frame (`verdictOf`'s `finalFrame`). A non-zero delta is a finding, not a reason to widen the tolerance.

### The per-tick verdict

After `finished`, the page diffs the drained stream (plus derived transitions, `tapeFormat.gameStreamFromDrain`) against the JS model's stream with the node differential's comparator, `tapeFormat.diffObservationStreams`. The model's stream is the walk the page already made for its overlays (`watchOverlays.test.js` pins that it equals `runTapeToStream`); for a generated room, `remapStreamRooms` maps levels at every observation.

The headline is one of:

- `agrees per tick (N observations)`;
- `diverges — tick T differs: expected (…), got (…)`: the comparator's own sentence at the first divergence, with both stream lengths;
- `no per-tick comparison (<reason>)`: MANUAL's zero-input tape has no run to reproduce;
- `end-state only (no drain on this build)`: an older build without the verb;
- `verdict-internally-inconsistent`.

**The end-state check runs first and always runs.** A per-tick `agrees` beside an end state that disagrees about the same frame is a defect in the comparison, so the page prints `verdict-internally-inconsistent` and keeps both lines. An items-only disagreement is not an inconsistency: an observation is `{t, x, y, level}`, so the per-tick line owns position and level and the end-state line owns the item set.

The printed scope names its two limits: it compares against the JS model of the same tape, not a recorded expectation, and both sides share this repo's tape and observation code, so a defect in that shared code is invisible. The instrument that compares against recorded oracles is `check-seedling-bot-differential.mjs`. There is no count of divergences after the first; counting would need a second copy of the comparison.
