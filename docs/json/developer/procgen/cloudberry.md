# Cloudberry Substrate

Cloudberry (substrate id `cloudberry`, in `frontend/modules/cloudberryDemo/`) plays each region as a Cloudberry Kingdom level. The game, its level generator and its embedded page live in the Cloudberry repository (`PeerInfinity/cloudberry-kingdom-wasm`); this repository holds only the substrate: the registry entry, the panel, the rules and pre-generated region payloads. No Cloudberry code, build output or game data is committed here.

A level is generated by the game's own generator from a request (`ck-level/2`), and the page regenerates it from the same request when a region loads. The payload carries the request and the sha256 of the document it makes, and the page refuses to play a level whose document hash differs.

## Setting up the game page

The flash bridge is injected into the game's iframe by the host panel, so the page must be served from the same origin as the frontend.

- **On GitHub Pages** both sites are on `peerinfinity.github.io`: the panel iframes `/cloudberry-kingdom-wasm/`.
- **Locally**, run this once (and again after the Cloudberry site is redeployed):

  ```bash
  node scripts/setup/fetch-cloudberry-site.mjs           # the live site → frontend/external/cloudberry/
  node scripts/setup/fetch-cloudberry-site.mjs --check   # is the copy there and the live build?
  node scripts/setup/fetch-cloudberry-site.mjs --link <site dir>   # use a local build instead
  ```

  The script finds the file list from what the build publishes about itself (`index.html` and the scripts it references, `content-manifest.json`, `_framework/blazor.boot.json`) and records the build id it fetched in `.cloudberry-site.json`.

Nothing is fetched until the first Cloudberry region is entered: until then the panel shows a small waiting page (`waiting.html`), because the game is about 26 MB and most worlds have no Cloudberry region. Then the panel uses the local copy when its `build-info.json` answers, and `/cloudberry-kingdom-wasm/` otherwise. The module setting **Cloudberry site URL** (`moduleSettings.cloudberryDemo.siteUrl`) overrides both.

The iframe URL is the page with `?embed=1` (the page's embedded mode, which implements the game side of `__swfBridge`), the bridge's `loadRegionEvent` and `playbackControlEvent`, and `packs=` pointing at this frontend's own `packs/` folder. The page draws check coins with the Archipelago logo from that art library, falling back to a purple coin when it cannot read it.

## The contract

The page side is documented in the Cloudberry repository (its README and `build/web/embed.js`). In short, the bridge's `world.params` is the page's region payload, version `cloudberry-region/1`:

- `generate`: the resolved generator request (the reroll search's result, never `reroll: true`).
- `docSha256`: the document's canonical sha256, with the build id blanked.
- `checks`: check name → coin id.
- `items`: AP item name → game item.
- `knobs` (P5d, ⚖ *"Save it"*): the generation knobs the request does not spell (`CLOUDBERRY_RECORDED_KNOBS`: checks per piece, the minimum pieces, hazards, the ability chances, the Jump level, retries), only those that differ from the defaults, so a default world's payload is unchanged. The panel's read-back (`cloudberryProcgenParamsFromPayload`) returns them, so a Regenerate rebuilds a region with what it was built with. The hero variation is not recorded: its draw is already in the request's physics. The committed sphere world records `cloudberryChecksPerPiece: 2`, and the two Double Jump worlds `cloudberryDoubleJumpChance: 1` as well.
- `exits`, `sidePortals`, `entrySide`: derived when the world loads (`deserializeWorld` → `pageParamsForWorld`) and stripped when it is saved, so a stored payload never carries them. Each exit carries its `exitId` and `targetRegion`, which the start door matches the arrival against.

Exits are offered at the level's end door, as a menu of the region's exits by side. The page names sides `north`, `east`, `south`, `west`; the grid's `N`/`E`/`S`/`W` are translated by `PAGE_SIDE`. Each exit is labelled with the region it leads to.

The **start door** offers the way back. It offers two sides, each once:

- `entrySide`: the region's own way back, the engine's `backExitSide`. This is the side the logic counts on: a sphere region's back exit is free (`backPortalGated` is false).
- The side the player **arrived by**. The bridge passes procgenPlayer's arrival to `configure` as `arrivedFrom` (`{exit_id, source_region}`). The page matches it against the exits by `exitId`, and in a world whose exits are not linked both ways, by the exit whose `targetRegion` is `source_region`.

A page without `arrivedFrom` (an older host) offers `entrySide` alone, as before; an older page ignores `arrivedFrom`.

The substrate uses two optional bridge methods from [Flash](./flash.md)'s bridge (`frontend/modules/flashSubstrate/bridge.js`):

- `setCheckedLocations(names)` is called on every snapshot change, so a collected check coin is redrawn as an outline.
- A `loadRegion` that arrives before the page has created `configure` (the .NET runtime takes seconds to boot) is held until it exists.
- `configure`'s `checkedLocations` comes from the iframe's cached snapshot. Right after a world is loaded that cache can still hold the previous world's checks, so a coin of the new world would be handed to the page as collected, and the page would never report it. The cause is subscriber order: procgenPlayer publishes the new world's loadRegion from its `stateManager:rulesLoaded` subscriber, ahead of the iframe adapter forwarding that same rulesLoaded with the new snapshot. Host messages arrive in the order they were posted, so the FIRST snapshot the bridge hears after a configure is the new world's, and it alone decides: if it lacks a check the configure was given, the bridge configures the region again, once (it logs `configured with checks the host does not have`); later host changes never reconfigure. No clock is involved. The rule is `frontend/modules/flashSubstrate/checkedSeedVerifier.js`, pinned by `frontend/modules/flashSubstrate/checkedSeedVerifier.test.js`.

| Game item | AP item | Obstacle id |
|---|---|---|
| `MovingBlock` | Moving Blocks | `cloudberry_gate_MovingBlock` |
| `FallingBlock` | Falling Blocks | `cloudberry_gate_FallingBlock` |
| `BouncyBlock` | Bouncy Blocks | `cloudberry_gate_BouncyBlock` |
| `GhostBlock` | Ghost Blocks | `cloudberry_gate_GhostBlock` |
| `Cloud` | Clouds | `cloudberry_gate_Cloud` |
| `Elevator` | Elevators | `cloudberry_gate_Elevator` |
| `Pendulum` | Pendulums | `cloudberry_gate_Pendulum` |
| `Conveyor` | Conveyors | `cloudberry_gate_Conveyor` |
| `FlyBlob` | Fly Blobs | `cloudberry_gate_FlyBlob` |
| `Jetpack` | Jetpack | `cloudberry_gate_Jetpack` |
| `DoubleJump` | Double Jump | `cloudberry_gate_DoubleJump` |

The nine platform items are platform types. The same level is generated whether or not an item is held; without it, that type's platforms are drawn dashed and cannot be landed on. `Jetpack` and `DoubleJump` are movement abilities. A level generated with the Jetpack hero needs Jetpack. A level generated with the Double hero (two jumps) needs Double Jump: without the item the page gives that hero one jump.

**Double Jump needs a page that has it.** The page reports it as `__cloudberryEmbed.features.doubleJump`, which arrived with the Cloudberry repo's commit `cdc77c9`. Before that commit, a 2-jump hero's level replayed from its inputs in only 13 of 30 levels: the generating computer toggles a jump-ready flag (`AutoAllowComputerToJumpOnLand`) that is not input, and the replay did not restore it. The page now records that flag with the inputs and restores it: 230 of 230 levels replay, and with the second jump taken away 0 of 30 do. On a page without the feature, a Double Jump level is refused by name before anything is generated (`CloudberryFeatureMissing`, [below](#generating-it-cloudberrygenerationjs)), because it could neither be replayed nor gated.

A payload's `items` map names Double Jump only for a Double-hero level. The `doubleJump` fact is likewise recorded only when it is true. Payloads written before Double Jump existed therefore keep their bytes.

`Victory` is the substrate's victory item.

`Cloudberry Gem` opens nothing and does nothing in the game; it is not a platform item, so a Cloudberry exit never gates on it. It exists to give a tiny world fill slack ([below](#fill-slack-for-tiny-worlds)). It is classified progression, not filler, because the sphere plan, its oracle and AP's sphere log count only progression items, so a filler item in the plan never matches them.

## The bot

The bot is the page's own: the computer's recording of the level, replayed. The host drives it through the substrate's playback proxy (the surface the Playback Bot and loop mode use), which the bridge turns into `botWalkTo` calls on the page:

- **A location** (`{kind: 'pickup', id: <check>}`): the player respawns at the start of the coin's piece and plays that piece's recording to the coin. Without the piece's items it falls through the dashed platforms (`died`), or the recording runs out short of the coin (`timeout`).
- **An exit** (`{kind: 'portal', id: <side>}`): the player walks to the door and leaves by that side, without the menu.
  - A side the **start door** offers (`startDoorSides`: the way back, and the side the player arrived by) is left by the start door. The player respawns at the level's start, where the start door is, so it needs no item.
  - Every other side is left by the end door. The player respawns at the start of the last piece and plays its recording to the door, so it needs the last piece's items.
  - `options.door` (`'start'` or `'end'`) forces one door.

The start door's walk is a Cloudberry page feature: the page says it has it with `__cloudberryEmbed.features.botStartDoor`. A page without it leaves every side by the end door.

**A walk sent before the game page is up.** Until the first Cloudberry region the panel shows its waiting page, which runs the flash bridge too; then it swaps in the game page. A `walkTo` sent in that window reaches the waiting page and would be lost with it, leaving the Playback Bot waiting on its first target. The panel's proxy therefore remembers the latest `walkTo` sent while the game page is not up (a `stop` or `reset` forgets it), and sends it again when the game page's bridge announces `iframe:appReady`. This is the bot channel's twin of procgenPlayer's re-publish of the active region on the same event. The rule is `cloudberryDemo/heldWalkTo.js` (unit-tested). Measured: the tutorial walk run on a cold page failed 2/2 before (Play pressed 0.1 s after the load) and passed 3/3 after, on the local copy and on the Pages path.

## The status strip

Above the game, the panel shows a slim **status strip** (P7a, ⚖ Robert 2026-11-06: *"Strip in the panel"*, *"All five"*). It is the generic flash-panel strip ([Flash: the status strip](./flash.md#the-status-strip)): everything on it is host state, and the game page is not changed. One line shows the level's items, the checks and the exits, with ▾ for details. A second line shows the latest activity and the bot.

| Section | What it shows | Where it comes from |
|---|---|---|
| This level's items | Each platform type the level uses, plus its ability hero (Jetpack or Double Jump), as ✓ HELD or 🔒 LOCKED, with where it starts ("from checkpoint 1"; an ability is "whole level"). It changes as soon as an item arrives. | `describeCloudberryLevel` (`cloudberryStatus.js`) reads the payload's request. The generated document realises exactly the request's piece upgrades (`readCloudberryDocument` refuses one that does not), so the request's platform upgrades are the level's `pieceItems`. The hero is `heroCustom.move`. A payload that carries `facts` (a library entry's) is read first. Held = the inventory. |
| Recent activity | A rolling log of up to 8 entries, newest first: "You found X (loc)", "Sent X to <player> (loc)", "Received X from <player>", and offline "Received X". | See [Flash: the activity log](./flash.md#the-activity-log). |
| Checks | Collected k of n, and each check coin's state: collected, reachable, or locked with what it needs. | The payload's `ap_locations`, the checked snapshot, and each location's own `access_rule` from static data. |
| Exits | Each side: open, or locked with what it still needs ("needs Clouds"). | Each exit's `access_rule` from static data, so the authored locks (`gate_rules`) count too. |
| Bot | When the Playback Bot walks: "Bot → loc_0", then "reached" or "stopped", plus the page's own notes ("ladder: skipped to checkpoint 1"). | The playback proxy's `walkTo`/`stop`, and the page's `__swfBridge.botStatus` reports relayed as `substrate:botStatus` ([P7b](#the-bot)). A page without them (`cdc77c9`) shows the walk only, and a walk to a coin ends when its location is checked. |

The details also show the number of checkpoints and the hero's physics where they are not the game's own, for example "hero: gravity 1.3, jumps 3" (P5b: only the sliders that act on that level's kind).

**Checkpoints are numbered by piece.** Piece 0 begins at the start door ("the start"), and piece k ≥ 1 begins at checkpoint k. The page's notes and the strip use the same numbers, as agreed with P7b.

**What is available offline and what needs a connection:**

| | Offline (a rules file) | Connected to a room |
|---|---|---|
| Who owns a location's item | the rules file's `locations[].item.player` | the connect-time scout (`getScoutedLocations`: item, slot and room name) |
| Player names | `player_names` of the rules file | the room's slot info |
| Received items | an inventory gain that no find explains: "Received X", with no sender claimed (a starting item, a spoiler sync or a grant) | the server's ReceivedItems, with the sender (`game:itemsReceived` `items`): "Received X from <player>"; the player's own items are not logged twice, and a full resync is one "Synced N items" line |

A name the client does not have is shown as "player <slot>". None is ever made up.

It does not take focus from the game: its one control (▾/▴) is not in the tab order and cancels the pointer's focus change. The expanded state is remembered per browser. Measured at 1280×800 (the panel 571 px wide): one line high, 25 px, until the first activity, then 43 px. At a phone's 390×844 it is 51 px, then 69 px.

## Loop mode

Cloudberry is a **summary** substrate, like bounce and Noiz2sa (`loopSupport`: `summaryRecording`, `record`, `playback`, `instant`, `playClock`, `executeVia: 'solver'`, queue actions `regionMove` and `locationCheck`). The mechanics are loops' own; see [Loop Recording and Block Modes](./loop-recording.md#summary-substrates). What is Cloudberry's:

- **Manual / Record.** The queue parks and the player plays the level. Record keeps the visit's net result: the check coins collected, the exit taken, and the play time (`summary.durationSeconds`, with the page's last report as `playStats: {gameSeconds}`). A loop reset during the visit discards it.
- **Playback** applies the summary at once: loops spends its price, refires the checks and crosses the recorded exit. The page plays nothing.
- **Bot.** The page's bot ([above](#the-bot)) walks each queued target: a check coin by name, an exit by side. The way back is the start door, which needs no item.

### The cost: the page's game clock

Every mode is priced by **game time**. The page calls `setPlayClock(running, {gameSeconds})` every second and on every change, where `gameSeconds` is physics steps / 60 since the configure. Loops charges the region `timeDrainPerSecond` (from `loop_costs`, 1 by default, discounted by region XP) for each whole game second played. This is the summary substrates' time-drain formula ([Loop Recording](./loop-recording.md)), except that the seconds come from the game, not the wall clock. So:

- Boot, the level's regeneration on a configure, an open exit menu and a hidden tab cost nothing: the game does not step, and the page reports its clock stopped.
- Live play and the Bot cost the same per second of play.
- Playback costs `durationSeconds` × the current rate.

The page settles the clock at the door: just before `sendExit` it reports the clock stopped, with the game seconds up to the door. A visit then costs exactly `floor(its game seconds)`. This is Cloudberry branch `p3b-exit-clock`; the test surface is `app.exitClockSettles`. A page without it bills each visit up to its last periodic report, which can be up to one second before the door.

The Bot respawns at the goal's piece rather than walking there, so a Bot visit costs the pieces it plays, not the whole level from the start.

**Measured** on the committed `cloudberry_sphere_worldgen` preset, with a `loop_costs` generated from its sphere log (rate 1 everywhere):

| Visit | Game seconds | Charged |
|---|---|---|
| Record, region_2_2: coin then end door | 9.38 (wall clock parked 9.36 s) | 9, and Playback 9 |
| Bot block, region_2_2: coin then end door (bot steps 165 + 346) | 8.60 | 8 (live page without the settle: last report 7.78, charged 7) |
| Running play, then 2.5 s hidden | — | 3 for 2.5 s running, 0 for 2.5 s hidden; no physics step while hidden |
| Instant Playback of the Record summary | — | 9, in 81–161 ms |

### Resets

A loop reset puts the region back through the existing chain. The reset sends the queue back to index 0. The queue's re-drive moves into its first region again, even when the player is already there. procgenPlayer publishes `cloudberry:loadRegion`, and the page is configured again: the player is back at the level's start door, the uncollected coins are re-armed, and checked coins are drawn checked from the host's state (the bridge's checked-seed rule, `checkedSeedVerifier.js`). A Bot walk in flight is stopped (`result: 'stopped'`). Nothing in `cloudberryDemo` handles resets itself.

The rows: `cloudberry-loop-record-then-instant-playback` (a reset before the Record completes, and the Loops Restart after it) and `cloudberry-loop-bot-blocks-reset-victory` (a reset in the middle of a Bot walk). See [Testing](#testing).

### Mixed worlds

Nothing in the loop code is per world: each region's class (`classifyRegion`) and solver come from its own substrate. The row `cloudberry-mixed-loop-bot-victory` shows it on the committed `cloudberry_maze_mix_worldgen` (two maze rooms, the start among them, and three Cloudberry levels; see [Presets](#presets)). The world is loaded with a `loop_costs` sidecar generated from its sphere log, and the Playback Bot plays it in loop mode: the maze blocks are walked by Loops' maze delegation, the Cloudberry blocks by the page's bot (solver `walkTo`, priced by the game clock), all from one mana pool, until every sphere-log location is checked.

## Rules

Rules come from the generated document's facts, not from a simulation here (`documentFacts`):

- A level is a sequence of nested pieces. Piece k is generated with the platform items S_k, the union of the items of pieces 0 to k. The generator's reroll search makes sure each piece's new items are really needed.
- A **check coin** in piece k needs S_k.
- **Every exit** (the end door) needs the last piece's set.
- A level generated with the Jetpack hero needs `Jetpack` everywhere.
- A level generated with the Double hero (`level.heroAbility.NumJumps` > 1) needs `Double Jump` everywhere.

These are sufficient sets (what the computer's own run used), not minimal ones. That is the safe direction: the logic never claims a coin the player cannot reach.

Check coins are a subset of the coins the computer collects. `chooseCheckCoins` takes a number per piece (default 1), spread through the piece by the tick at which the computer collects them.

Emission uses the shared [paths-and-obstacles](./paths-and-obstacles.md) vocabulary, like [bounce](./bounce.md): one path per goal, holding one physics obstacle per required item. Authored terms the level cannot realise (foreign items, counts above 1) become `logic_gate` obstacles ANDed onto the path, and ride the payload as `gate_rules` for the bridge to evaluate at run time.

## Build-time generation (sphere growth)

Sphere growth realises a Cloudberry node by generating a new level for it with the game's own generator. The registry entry declares `generateZoneForSpecsGen` (and its synchronous form), `buildZoneSpecs`, the gate hooks below and `generationCost: 'heavy'`.

### Planning a level (`cloudberryZonePlan.js`)

`planCloudberryLevel` turns a node's specs into a `ck-level/2` request, synchronously and deterministically:

- Requirements are split by `splitCloudberryRequirement`. Platform items with count 1 are **physics**: pieces realise them. Everything else is **authored**: `Jetpack`, `Double Jump`, items of other games, and counts above 1. An authored term becomes a `logic_gate` obstacle on the path and a `gate_rules` entry. The page's exit menu greys out a locked exit.
- The requirements form one nested chain S_0 ⊆ S_1 ⊆ … ⊆ S_last (the shape the deleted runner substrate's strip planner used). Each set gets pieces. Item-free pieces come first and hold the check coins, `cloudberryChecksPerPiece` per piece (⚖ R19). Then come the pieces that bring in the exits' platform items. A piece's new items are at upgrade level 5 and its carried items at 3. Item-free pieces are added at the start up to `cloudberryMinPieces`.
- Every **forward** exit leaves by the end door, after the last piece, so it needs S_last. Because they share one door, the forward exits' platform requirements must be **equal**: a smaller one would be over-required. `canHostCloudberryExitGates` (also `exitGateVeto`) declines unequal gates the way bounce declines non-nested ones, and `gateHostingHint` says why. Incomparable location requirements are refused by name.
- The **back** exit (the entrance side) is free. The start door offers it, so `backPortalGated` is false. The engine's zone context (`ctx.entrance`) says which side it is and what the entry gate holds. A back exit that still arrives with platform items (a caller could not show that every player inside holds them; P5d, ⚖ *"lock as fallback"*) is an **authored lock** on the start door, like Jetpack in an exit gate: `gate_rules.portals` greys that side of the start door until the player holds them, and a `logic_gate` says the same. The APWorld Editor's Regenerate recovers the entry gate first ([the editor's entry gate](../../modules/apworldEditor.md#region-generation---generate-in-a-worker-under-a-time-limit-substrate-change-r2)), so a sphere-grown region's way back is free again, as it was generated.
- **Jetpack levels.** A region whose entry gate holds `Jetpack` is generated with the Jetpack hero with probability `cloudberryJetpackChance`. Everything in it then needs Jetpack, which every player inside already holds. Jetpack in an exit gate is a lock, since the hero is level-wide.
- **Double Jump levels.** These work the same way. A region whose entry gate holds `Double Jump` is generated with the Double hero (`{move: 'Double', phsx: {numjumps: 2}}`) with probability `cloudberryDoubleJumpChance`. Everything in it then needs Double Jump. Double Jump in an exit gate is a lock.
- **Jetpack and Double Jump in one entry gate:** a level gets at most ONE ability hero. The Hero Factory's movement is a single choice, and a hero with both abilities has never been measured to replay. The Jetpack draw comes first. A level that draws the Jetpack hero makes no Double Jump draw, so a Jetpack level is never also a Double Jump level.
- **The hero's physics (P5b).** The Hero Factory's sliders are world settings (`CLOUDBERRY_HERO_PHYSICS`, keys `cloudberryHero…`; defaults = the game's own hero). The general sliders act on every level. The Double Jump sliders (jumps, double jump length and acceleration) act only on a Double Jump level, and the Jetpack sliders (acceleration, fuel) only on a Jetpack level. The request carries them as `heroCustom.phsx`. A slider at its default is left out, so a default world's requests are unchanged: a plain level has no `heroCustom`, and the ability levels keep `{jetpackfuel: 1}` / `{numjumps: 2}` first. With `cloudberryHeroVariation` above 0, each region draws its own hero (draw 5 below): every slider moves from the world's value toward a uniform point of its range by that fraction. A value outside its ruled range is refused by name. Physics changes no rule: every item gate of a level is verified under that level's own hero (the reroll search), and the page plays the same hero, because it regenerates the same request and checks its hash.
- `hostsSurplusExitsNatively` is true: every exit is listed in the end door's menu.

**Randomness.** The level's seed is the engine's region seed, drawn from the pipeline's stream (`shared/rng.js`). A per-region stream `createRng(seed)` then draws, in order:

1. The tileset, only when `cloudberryTileset` is `random`.
2. The hazard kinds, only when hazards are on.
3. The Jetpack draw, only when the entry gate holds Jetpack and the chance is strictly between 0 and 1.
4. The Double Jump draw, only when the entry gate holds Double Jump, the level is not a Jetpack level, and the chance is strictly between 0 and 1.
5. The hero variation, only when `cloudberryHeroVariation` is above 0: one number per physics slider that acts on the level, in `CLOUDBERRY_HERO_PHYSICS` order.

Draws 3 to 5 come last. A world without these gates and without variation draws exactly what it drew before them. With variation on, a retry also redraws the hero: attempt a > 0 draws draw 5 alone from `createRng(<attempt a's seed>)`, so an unlucky hero cannot refuse every attempt. The draw (the kind of level, the world's values and the variation) is part of the cache key.

### Generating it (`cloudberryGeneration.js`)

The generator lives in the game page, so nothing in this repository can generate a level synchronously:

1. The hook plans the request and looks the result up in the cache.
2. On a miss it **yields** an event carrying `await`: a promise from `ensureCloudberryLevel`.
3. The pipeline's asynchronous drivers wait on it before resuming. These are `growSpheresAsync`, `growSpheresBatchedAsync`, the stepped `runSphereToStep`, top-down's realise step and `growMazeAsync`, all through the engine's `yieldedWait`.
4. A synchronous drain does not wait: the hook refuses by name. The generation it started keeps running and is cached, so the same call made again once it is done succeeds. If the generation FAILED, that call names the failure, once (`takeSettledCloudberryFailure`).
5. The APWorld Editor's region regenerate takes ONE press (P5c). The engine's synchronous drain records the yielded promise (`collectPendingGenerations`). The editor's worker has no game page, so it flags the refusal, and the page finishes the job: it awaits that promise and asks once more. See [the editor's Region generation](../../modules/apworldEditor.md#region-generation---generate-in-a-worker-under-a-time-limit-substrate-change-r2). *Initialise procgen data* takes the same road for a whole slot (P5d): each ask builds one more region, bounded by the slot's region count.

Each level is generated with `reroll: true`, the generator's own gate search (⚖ R14). Its document is read against the plan (`readCloudberryDocument`): each piece realises its planned items, the Jetpack and Double heroes match the plan, the hero's physics are the attempt's request (the document's `level.heroPhsx` holds every slider and nothing was clamped; otherwise `CloudberryHeroMismatch`), a start door exists when there is a way back, and each piece has enough witnessed coins for its checks. A refusal moves to the next attempt, which has a derived seed (`cloudberryAttemptSeed`). Refusals are `RerollExhausted:` or a failed read. After `cloudberryRetries` retries, the hook throws `CloudberryLevelRefused`, naming the region and every attempt's reason.

**Page features.** A generator may offer `features()`, which returns the page's `__cloudberryEmbed.features`. A plan that needs a feature the page lacks is refused before any generation, as `CloudberryFeatureMissing: cloudberry zone '<id>' is a Double Jump level, but the Cloudberry page (build …) has no doubleJump …`. The refusal names the fix: a page that has the feature, or `cloudberryDoubleJumpChance` 0. Today the only such feature is `doubleJump`, which every Double Jump plan needs. The refusal is not cached, because another page may have the feature. A plan without Double Jump never asks for features.

The result is cached in memory by the request and its needs (`cloudberryLevelKey`), and in a persistent store. The browser uses `localStorage`; headless runs use a file per key under `frontend/external/cloudberry-level-cache/<build>/`. A re-run, a stepped replay or a second Generate regenerates nothing. The payload stores only the resolved request (`generate`, with explicit `rerolls`), the document hash and the check coins, and the page regenerates the level itself.

**Where the generator comes from.** In the app, `index.js` installs `cloudberryGenFrame.js`'s generator. It is a hidden same-origin game page (`?embed=1`), created on the first generation from the same site the panel plays. It is a 2×2 transparent frame, not `display:none`, so the browser does not throttle its boot, and it is removed after two idle minutes. Headless, an instrument calls `installHeadlessCloudberryGenerator(browser)` from `scripts/procgen/cloudberrySite.mjs`. Both need the same-origin site (see [Setting up the game page](#setting-up-the-game-page)).

**Determinism.** The same seed and params give the same `rules.json` bytes. `check-cloudberry-sphere.mjs` measures it with two generations from scratch, the cache cleared between them. The Procgen Pipeline panel's world equals the headless one: `check-procgen-presets.mjs` checks this for `shipped:cloudberry-sphere-demo`.

**Cost.** Measured on the box: the page is ready in 4–11 s headless, then each level takes 0.3–1.4 s, all three demo levels rerolling 0 times. In the browser panel, the demo preset took 42 s including the hidden page's boot.

### World settings

Prefixed so they survive mixed-substrate merging; defaults in `DEFAULT_CLOUDBERRY_PROCGEN_PARAMS`, drawn in the Procgen Pipeline panel's Parameters section. The generator's own settings are a whitelist: its reflection lists engine state fields too.

| Param | Meaning |
|---|---|
| `cloudberryDifficulty` | The generator's difficulty, 0 (Easy) to 4 (Masochistic). |
| `cloudberryPieceLength` | Each piece's length in world units (the generator's `pieceLength`). |
| `cloudberryMinPieces` | The fewest pieces a level has. |
| `cloudberryChecksPerPiece` | Check coins per piece (⚖ R19), chosen among the coins the computer collects there. |
| `cloudberryHazards` | Hazard upgrades on every piece. |
| `cloudberryHazardLevel` | The level of each hazard upgrade (0–10). |
| `cloudberryHazardKinds` | How many hazard kinds a level draws. |
| `cloudberryJetpackChance` | The chance that a region entered through a Jetpack gate is a Jetpack-hero level. |
| `cloudberryDoubleJumpChance` | The chance that a region entered through a Double Jump gate is a Double-hero level (not when it is already a Jetpack level). |
| `cloudberryTileset` | A tileset, or `random` (drawn per region). |
| `cloudberryJumpLevel` | The generator's Jump upgrade on every piece. |
| `cloudberryRetries` | Retries with a derived seed before the named refusal. |
| `cloudberryHeroGravity` | The hero's gravity (0.5–1.5; default 1). |
| `cloudberryHeroAccel` | The hero's acceleration (0.5–2). |
| `cloudberryHeroMaxSpeed` | The hero's top speed (0.5–2). |
| `cloudberryHeroMaxFall` | The hero's top fall speed (0.33–3). |
| `cloudberryHeroJumpLength` | How long a held jump keeps rising (0.85–1.65). |
| `cloudberryHeroJumpAccel` | The jump's acceleration (0.9–1.65). |
| `cloudberryHeroFriction` | Ground friction (0.5–3). |
| `cloudberryHeroSize` | The hero's size (0.8–2.1). |
| `cloudberryHeroNumJumps` | Jumps on a Double Jump level (2–4, whole; default 2). |
| `cloudberryHeroJumpLength2` | The double jump's length, Double Jump levels only (0.5–1.35). |
| `cloudberryHeroJumpAccel2` | The double jump's acceleration, Double Jump levels only (0.5–1.65). |
| `cloudberryHeroJetpackAccel` | The jetpack's thrust, Jetpack levels only (0.75–2). |
| `cloudberryHeroJetpackFuel` | The jetpack's fuel, Jetpack levels only (0.5–4; default 1). |
| `cloudberryHeroVariation` | 0–1. How far each region's hero is drawn from the values above toward a random point of each range (0 = every level has the same hero). |

The ranges are narrower than the game's own slider bounds where P5b measured trouble (⚖ Robert, 2026-11-04):

- **Size below 0.5**: the computer passes coins without touching them, so 3–13% of levels fail the replay check and are rerolled.
- **More than 4 jumps**: the hero no longer needs the platform items, so the reroll search refuses more levels.
- **Double jump length above 1.35**: rerolls climb, and the bot died more often in combined settings.
- **Gravity above 1.5, jump length below 0.85, jump acceleration below 0.9, friction below 0.5 and size below 0.8**: the hero crossed the fixed elevator ladder between pieces less often than the default hero (a scripted crossing on the same levels, paired per seed; ⚖ rulings A, then A3).

Every other slider keeps the game's full range.

### Fill slack for tiny worlds

Archipelago's unit test `TestTwoPlayerMulti` fills two copies of every world, with full accessibility and the restrictive fill. A tiny sphere-grown world whose start region holds **one** free location fails that fill on some seeds (`FillError: No more spots to place N items`). Each world has exactly one item that leaves its start, and the fill can spend a world's only start slot on another item, such as Victory. Before P4c (2026-11-03, 2 players, 5,000 random seeds): `cloudberry_sphere_worldgen` failed on 10, `cloudberry_maze_mix_worldgen` on 3. `procgen_maze_worldgen` failed on none: it also has one start slot, but two `key_red`s, either of which opens it.

What fixes it is a **second free location in the start region**; slack anywhere else does not. Measured by adding one location (and one item) to the old worlds, 5,003 seeds each:

| Variant | Sphere world | Mixed world |
|---|---|---|
| As committed before P4c | 18 | 5 |
| + a free location in the start region | 0 | 0 |
| + a location in the last region | 13 | 9 |

So both committed worlds carry the Cloudberry Gem in sphere 1, which puts a second free location in the start region (afterwards: 0 failures in 5,013 seeds each, including the seeds that failed before). The sphere demo also sets `cloudberryChecksPerPiece: 2`, so its start level keeps one item-free piece. The gem gets into sphere 1 through the **key order of the scenario pool**: the planner shuffles the pool in insertion order, and at seed 1 the committed order puts the gem in sphere 1, after Moving Blocks in the mixed world. The order also decides which item the maze gates its start exit on: Moving Blocks, not the gem. `check-cloudberry-sphere.mjs` checks the result on every run: the start region has two free locations, the gem is one of them, and no rule names the gem. Measure a world with `setup_multiworld([w, w], (), seed=s)`, accessibility full, each of `gen_steps`, then `distribute_items_restrictive`; it takes about 1 ms per seed. A new tiny world needs the same slack.

## Regions from a library

Cloudberry regions can also come from region-library packs: the substrate declares `instantiateLibraryEntry`, `instantiateLibraryEntryForSpecs`, `captureLibraryEntry` and `validateLibraryEntry`, and no zone table.

A pack entry's `payload` holds the original arguments, the resolved request, the document hash, the facts (`pieceItems`, `jetpack`) and the check coins (`checks`: name, coin id, piece). Its `carried_rules` are the rules those facts emit; `validateLibraryEntry` re-emits them and refuses any drift.

- **Spiral** (`instantiateLibraryEntry`): the entry on the slot's sides (any subset of its four, since every exit leaves by the end door), keeping its captured slot items.
- **Sphere growth** (`instantiateLibraryEntryForSpecs`): a library level is real geometry, so a pack entry is used only where it is sound. Its `libraryEntryRefusal`, which the engine's sphere source consults before it picks an entry, refuses a slot in two cases:
  - Fewer of the entry's check coins are reachable with the slot's entry gate than the node has locations. A coin in piece k needs S_k.
  - A forward exit's gate, together with the entry gate, does not hold S_last.

  The node's items go on the reachable coins, in piece order, with the engine's filler on the rest. The hook returns the end door's real requirement as the forward exits' paths, and the engine ANDs its own gate onto each of them as a `logic_gate` obstacle (`buildSphereLibraryRegion`), so neither requirement is lost. The entrance side is the start door's way back and is free.

  A world whose only content source is a library takes its goal from the library's substrate: Cloudberry declares `Victory`. `check-cloudberry-embed.mjs` plays a sphere world built from the demo pack to Victory with the Playback Bot.

The demo pack has seven levels: nested pieces over every platform item, two Jetpack levels, one check coin per piece, all four exit sides. One captured slot holds `Victory`, so a world made from the pack alone has a goal.

The entry declares `regionGeometry: SIDES` and its own `exitSides` declaration, which keys the stored payload's `params.backExitSide` and `gate_rules.portals`.

**The demo-pack row's silent bridge (P3b's 1-in-7, fixed in P4a).** The row plays a demo-pack region the host is not in (`cb_demo_inapp`; the host stays in `region_2_2`).
