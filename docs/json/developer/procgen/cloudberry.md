# Cloudberry Substrate

Cloudberry (substrate id `cloudberry`, in `frontend/modules/cloudberryDemo/`) plays each region as a Cloudberry Kingdom level. The game, its level generator and its embedded page live in the Cloudberry repository (`PeerInfinity/cloudberry-kingdom-wasm`); this repository holds only the substrate: the registry entry, the panel, the rules and pre-generated region payloads. No Cloudberry code, build output or game data is committed here.

A level is generated by the game's own generator from a request (`ck-level/2`), and the page regenerates it from the same request when a region loads. The payload carries the request and the sha256 of the document it makes, and the page refuses to play a level whose document hash differs.

## Setting up the game page

The flash bridge is injected into the game's iframe by the host panel, so the page must be served from the same origin as the frontend.

- **On GitHub Pages** both sites are on `peerinfinity.github.io`: the panel iframes `/cloudberry-kingdom-wasm/`.
- **Locally**, run this once (and again after the Cloudberry site is redeployed):

  ```bash
  node scripts/setup/fetch-cloudberry-site.mjs           # the live site → frontend/external/cloudberry/
  node scripts/setup/fetch-cloudberry-site.mjs --check   # is the copy there and the live build?
  node scripts/setup/fetch-cloudberry-site.mjs --link <site dir>   # use a local build instead
  ```

  The script finds the file list from what the build publishes about itself (`index.html` and the scripts it references, `content-manifest.json`, `_framework/blazor.boot.json`) and records the build id it fetched in `.cloudberry-site.json`.

The panel uses the local copy when its `build-info.json` answers, and `/cloudberry-kingdom-wasm/` otherwise. The module setting **Cloudberry site URL** (`moduleSettings.cloudberryDemo.siteUrl`) overrides both.

The iframe URL is the page with `?embed=1` (the page's embedded mode, which implements the game side of `__swfBridge`), the bridge's `loadRegionEvent` and `playbackControlEvent`, and `packs=` pointing at this frontend's own `packs/` folder. The page draws check coins with the Archipelago logo from that art library, falling back to a purple coin when it cannot read it.

## The contract

The page side is documented in the Cloudberry repository (its README and `build/web/embed.js`). In short, the bridge's `world.params` is the page's region payload, version `cloudberry-region/1`:

- `generate`: the resolved generator request (the reroll search's result, never `reroll: true`).
- `docSha256`: the document's canonical sha256, with the build id blanked.
- `checks`: check name → coin id.
- `items`: AP item name → game item.
- `exits`, `sidePortals`, `entrySide`: derived when the world loads (`deserializeWorld` → `pageParamsForWorld`) and stripped when it is saved, so a stored payload never carries them.

Exits are offered at the level's end door, as a menu of the region's exits by side. The page names sides `north`, `east`, `south`, `west`; the grid's `N`/`E`/`S`/`W` are translated by `PAGE_SIDE`. Each exit is labelled with the region it leads to. `entrySide` (the start door's way back) comes from the engine's `backExitSide` when the region has one.

The substrate uses two optional bridge methods from [Flash](./flash.md)'s bridge (`frontend/modules/flashSubstrate/bridge.js`):

- `setCheckedLocations(names)` is called on every snapshot change, so a collected check coin is redrawn as an outline.
- A `loadRegion` that arrives before the page has created `configure` (the .NET runtime takes seconds to boot) is held until it exists.

## Items

| Game item | AP item | Obstacle id |
|---|---|---|
| `MovingBlock` | Moving Blocks | `cloudberry_gate_MovingBlock` |
| `FallingBlock` | Falling Blocks | `cloudberry_gate_FallingBlock` |

| `GhostBlock` | Ghost Blocks | `cloudberry_gate_GhostBlock` |
| `Cloud` | Clouds | `cloudberry_gate_Cloud` |
| `Elevator` | Elevators | `cloudberry_gate_Elevator` |
| `Pendulum` | Pendulums | `cloudberry_gate_Pendulum` |
| `Conveyor` | Conveyors | `cloudberry_gate_Conveyor` |
| `FlyBlob` | Fly Blobs | `cloudberry_gate_FlyBlob` |
| `Jetpack` | Jetpack | `cloudberry_gate_Jetpack` |

The nine platform items are platform types. The same level is generated whether or not an item is held; without it, that type's platforms are drawn dashed and cannot be landed on. `Jetpack` is a movement ability: a level generated with the Jetpack hero needs it.

`Victory` is the substrate's victory item.

## Rules

Rules come from the generated document's facts, not from a simulation here (`documentFacts`):

- A level is a sequence of nested pieces. Piece k is generated with the platform items S_k, the union of the items of pieces 0 to k. The generator's reroll search makes sure each piece's new items are really needed.
- A **check coin** in piece k needs S_k.
- **Every exit** (the end door) needs the last piece's set.
- A level generated with the Jetpack hero needs `Jetpack` everywhere.

These are sufficient sets (what the computer's own run used), not minimal ones. That is the safe direction: the logic never claims a coin the player cannot reach.

Check coins are a subset of the coins the computer collects. `chooseCheckCoins` takes a number per piece (default 1), spread through the piece by the tick at which the computer collects them.

Emission uses the shared [paths-and-obstacles](./paths-and-obstacles.md) vocabulary, like [runner](./runner.md): one path per goal, holding one physics obstacle per required item. Authored terms the level cannot realise (foreign items, counts above 1) become `logic_gate` obstacles ANDed onto the path, and ride the payload as `gate_rules` for the bridge to evaluate at run time.

## Regions from a library

Until build-time generation lands, Cloudberry regions come from region-library packs: the substrate declares `instantiateLibraryEntry`, `instantiateLibraryEntryForSpecs`, `captureLibraryEntry` and `validateLibraryEntry`, and no zone table.

A pack entry's `payload` holds the original arguments, the resolved request, the document hash, the facts (`pieceItems`, `jetpack`) and the check coins (`checks`: name, coin id, piece). Its `carried_rules` are the rules those facts emit; `validateLibraryEntry` re-emits them and refuses any drift.

- **Spiral** (`instantiateLibraryEntry`): the entry on the slot's sides (any subset of its four, since every exit leaves by the end door), keeping its captured slot items.
- **Sphere growth** (`instantiateLibraryEntryForSpecs`): the node's items on the check slots in order, with the engine's filler on the rest. The hook returns the end door's real requirement as exit paths, and the engine ANDs its own gate onto each of them as a `logic_gate` obstacle (`buildSphereLibraryRegion`), so neither requirement is lost.

The demo pack has seven levels: nested pieces over every platform item, two Jetpack levels, one check coin per piece, all four exit sides. One captured slot holds `Victory`, so a world made from the pack alone has a goal.

The entry declares `regionGeometry: SIDES` and its own `exitSides` declaration, which keys the stored payload's `params.backExitSide` and `gate_rules.portals`.

## CLI tools

| Script | Purpose |
|---|---|
| `scripts/setup/fetch-cloudberry-site.mjs` | The same-origin copy of the game page (see [Setting up the game page](#setting-up-the-game-page)). |
| `scripts/procgen/make-demo-cloudberry-pack.mjs` | Generates the demo pack through the game's own generator (headless, from the local copy). Each payload is configured in the page once, and a refusal fails the run; a region whose reroll search is exhausted is named. `--check` compares a fresh generation with the committed pack byte for byte. |
| `scripts/procgen/check-cloudberry-embed.mjs` | A spiral world from the demo pack, through `world_generator` (`--canonical-seed 1`) and `Generate.py`, played in the real frontend. The start region configures. The bot dies short of a coin behind an unheld item. The bot collects the free coin, which is checked in the tracker, drawn as an outline, and gives the item. The bot then reaches the gated coin. Up at the end door opens the exit menu, and choosing a side moves to the next region. Needs a dev server (`--port`) and takes the box lock. |
