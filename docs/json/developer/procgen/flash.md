# Flash Substrate

The flash substrate (`frontend/modules/flashSubstrate/`, id `flash`) hosts recompiled Flash games — SWF → C → WASM via SWFRecomp-CC — in a same-origin iframe as procgen regions. The module ships a placeholder game page, so it is testable independently of any real recompiled game; its real significance is as the **shared iframe-substrate machinery** other substrates build on.

## The `__swfBridge` contract

The game page owns `window.__swfBridge.configure` / `pollItems` (the game side of the contract); the host-injected `bridge.js` completes the iframeAdapter handshake, configures the game from the region payload, applies received items via `pollItems`, and dispatches `user:locationCheck` when the game's ActionScript cooperatively calls `__swfBridge.sendLocation`. The host module (`index.js`) brokers `flash:loadRegion` activation and brings the panel forward.

## Per-game entries (one panel, many ids)

`createFlashSubstrateEntry` (`flashSubstrateLibrary.js`) is a factory: each Flash game can register its **own substrate id** with its own `supportedFeatures`, while every entry resolves to the same panel component and `flash:loadRegion` event. The module itself registers only the generic `flash` entry (a region whose game is identified purely by the payload's `gameId`). The factory also supplies the runtime plumbing — the exits-Map `deserializeWorld`/`serializeWorld` round-trip and a null playback stub — which is exactly what **bounce** builds its entry on top of, overriding the panel identity and adding build-time hooks ([Bounce Substrate](./bounce.md)).

The `iframeId` field on flash-family entries closes an init race: procgenPlayer re-publishes the active region's load event when that iframe announces `appReady`, covering both the initial load-before-subscribe window and iframe reloads.

## Capabilities

Flash regions are opaque minigames by default: `arbitrary_ap_locations` only, no build-time generation hooks (procgen just records `gameId` + params in the sidecar), no playback controller, and loop support of queueable `regionMove` plus manual play. Full contract: [Substrate Registry Reference](./substrate-registry.md).

## `flash_seedling` — a real game's map as procgen regions

`flash_seedling` (`frontend/modules/flashPanel/flashSeedlingLibrary.js`) is the region atlas's play-time substrate: a region is a **real Seedling level**, marked out in the atlas and compiled into `preset_sidecars` by `procgenPipeline/regionAtlasCompiler.js` (plan: `CC/docs/plans/region-atlas-plan.md`, Phase 4). It is built on `createFlashSubstrateEntry` but differs from every other flash-family entry in two ways, both deliberate:

- **It renders in `flashPanel`, not `flashSubstratePanel`,** and therefore owns its own `flashSeedling:loadRegion` event (the bounce precedent). The game is driven by flashPanel's shipped `WasmBridgeAdapter` — teleports, item writes, progressive/fusion expansion, location checks. Building a second AP↔game translation inside flashSubstrate's in-iframe bridge would duplicate solved work, and the dialects differ anyway: the SWFRecomp wasm shim speaks `game.configure(json)` + `queueItems`, the substrate bridge speaks `__swfBridge.configure(obj)` + `pollItems`.
- **It declares no `iframeId`.** flashPanel's embed is a plain `<iframe>` that never announces `iframe:appReady`, so procgenPlayer's re-publish race-closer has nothing to fire on. The equivalent is handled inside the glue instead (below).

### The host-side glue

`seedlingRegionBinding.js` is a pure state machine (region load + property reports in, effects out); `seedlingRegionGlue.js` applies the effects. Detection is **level-granular**: an atlas region binds to a whole level, so a boundary crossing is the game's own `Main.level` change, tie-broken on the reported spawn coordinates when two exits of one region reach the same level. Sub-level physical boundaries (live player x/y against a marked tile line) are deferred — they need BridgeGeneric changes, re-injection and a wasm rebuild. Logical sub-regions are unaffected: they carry rules and are never physically triggered, so every sub-region of a region shares its level.

The signals are three `Main` statics declared in `games/seedling.json` — `playerPositionX`, `playerPositionY`, `level`, in that order, so a `new Game(level, x, y)` reports its tie-break coordinates before the level change. They ride the **one** configure at boot: `BridgeGeneric.doConfigure` refuses a second configure for the life of a game instance, so widening the set later needs a page reload.

Three behaviours are worth knowing before touching this:

| | |
|---|---|
| **Teleport echo** | The glue's own arrival teleport changes `level`, and that report is indistinguishable from the player walking through a door. An arrival is marked in flight and its matching report swallowed, clearing on match or after 15 s. A teleport to the level the game is *already* on arms nothing — arming would eat the next real crossing. |
| **First-read baseline** | BridgeGeneric reports the whole declared set at boot, so the first `level` report is where the game already is, not a crossing. It doubles as the "game is alive" signal that releases an arrival queued while the wasm page was still waiting on its own ▶ Start gesture (which can take minutes). |
| **Unmapped levels** | The starter atlas covers 3 of Seedling's 116 levels, by design. A level change the current region has no exit to **warns loudly** on both the console and the panel log and does *not* move the AP region. A silent no-op would read as a complete map; a crash would make a partial atlas unusable. |
| **The park** | While ANOTHER substrate owns the region, the game keeps running — flashPanel has no inactive overlay, deliberately (below) — so the binding is PARKED instead: the glue subscribes `procgen:activeSubstrateChanged` and every property report is dropped, position included, no crossing published, no warn, no echo armed, and an in-flight echo cleared. An arrival that lands meanwhile (procgenPlayer publishes the target's `loadRegion` **before** the broadcast, so the return leg always does) is queued on the same slot the not-yet-booted case uses and released exactly once. Default is ACTIVE, so a preset that never broadcasts is unaffected. |

`arrivedFrom` is consumed **host-side** here — flashSubstrate's own bridge drops it — which is what makes "arrive at the exit you came through" work. With no arrivedFrom (the synthesized `Menu → start-region` hop, or a move whose source region is outside the warehouse) the region's first declared exit stands in; that is an info line, not a warning.

No `SubstrateInactiveOverlay` in v1: the flashPanel panel predates the overlay and is not procgen-only (it still serves the Stage-1 direct-client presets), so wiring the overlay would mean teaching it a panel that is legitimately active with no procgen substrate at all. Deliberately skipped rather than half-wired. That ruling stands — what changed is the BINDING, not the panel: parking is about which reports may be read as AP movement, and `flashPanelUI.js` is untouched.

### AP's item placement — the room is rewritten, the host owns every grant

The randomizer does not write item flags into a running game: it puts AP's item **in the room**. `seedlingDemo/apPlacementRewriter.js` takes the AP placement (`stateManager.getLocationItem`, injected — `seedlingDemo/` never imports the host's state manager) and the vanilla 116 as a `record`-sourced set, and replaces exactly the pickup entity at each randomized location with an `<apitem>` carrying two attributes: `@tag`, the persistence slot that is the location's address, and `@look`, the graphic. Every other byte of every room is identical, measured on the emitted OEL rather than on a substitution count. `flashPanel/seedlingLevelSetDelivery.js` then delivers that set — `botLoadLevels` per chunk, `botLevelSet` read back and diffed — and `seedlingRegionGlue` gates the first `flashSeedling:loadRegion` on it, because a region load teleports the player into a room and replacing the room under the player afterwards is a different game.

**The `look` vocabulary is 21 names and every one is derived** — `ITEM_FOR_TAG`'s 14 keys, `bosskey0`…`bosskey4`, `seed`, and `ap` (the Archipelago logo, for a foreign player's item or an item this world names no graphic for). Three facts shape it:

- **`ITEM_FOR_TAG` is not injective.** 14 tags carry 12 item names: `Progressive Shield` is both `shield` and `darkshield`, `Progressive Swim` both `conch` and `feather`. So "the inverse" is not a function, and the tie-break is ruled: the destination's own vanilla graphic when the item wears it too, otherwise the first in `ITEM_FOR_TAG`'s own key order. The book is BUILT from the goal ledger's rows, never typed, so a new tag is followed automatically.
- **A `look` must determine one sprite alone.** `BossKey` picks its graphic with `Game.bossKeys[_t]`, so a bare `bosskey` would leave the game guessing and a Green Key placed where the Red one sat would render red. The index comes from `ITEM_FOR_KEY` and is cross-checked against the element's own `@keyType`.
- **`Fire` renders as `ap`.** It is an encounter grant with no pickup entity anywhere, so no table in this repository names a graphic for it. Stated rather than patched.

**11 of the 39 rewritable locations have no vanilla `@tag`.** `bosskey`, `totempart` and `seed` take none in `Game.as`'s XML loop, so their address is ALLOCATED through `procgenSeedling.placementTagId` — the repo's one writer of that rule — composing per level, which matters because level 40 needs three and already spends 23 of the game's 30 slots. The two `encounter` rows (the BobBoss drop, the Witch trade) are **not** rewritten: their entities are a falling rock and an NPC, and they are reported by name for the check binding to serve through the existing property path.

**A rewrite moves none of the 24 vanilla AP references and falsifies eleven.** It adds no room, removes none, reorders none and repaints no tile, so every level id and coordinate in `region_coords`, `location_coords` and the atlas's `map_ref`s still resolves to the same room at the same tile. But `location_coords`' whole content is *"the Sword is at level 10, (48, 64)"*, and each of those tiles now holds an `apitem`. So `apMappingInvalidation`'s companion is a **precondition**: the delivery refuses a set that arrives without its own stamped one.

⛔ **Wasm-only, and the reason is not a policy.** Real Flash's `seedling_injected.swf` carries no `bot*` verb at all, so `botLoadLevels` cannot exist there. The Ruffle arm keeps doing what it does today — BridgeGeneric property writes, `readState`, teleport — it simply cannot be handed a rewritten level set.

**`seedling_bot_ap_p4d` is the build the placement can actually be PLAYED on**, and it is the only build carrying the two report seams. Five AS3 files, ~11 substantive lines plus one class: `Pickups/APItem.as` is built from the `<apitem>` element, **grants nothing**, and calls `Game.setPersistence(tag, false)` on collection — the engine's own collected marker, since `buildLevelPersistence` fills the table with `true` meaning *"nothing cleared"*. Its sprite comes from a `look → [PNG, frameW, frameH]` table of sixteen re-embedded graphics plus the shared `Game.bossKeys[N]`; the graphics are re-embedded rather than borrowed from a throwaway vanilla instance because `Chest`'s own field initialiser calls `Rng.cos()`, so constructing one to steal its graphic would move the RNG stream every tape is recorded against. `look == "ap"` binds a plain `Image` where every Seedling look binds a `Spritemap`, which is what makes the placeholder observable without a single pixel: `botMobiles` reports `frame` as `graphic as Spritemap`, i.e. **null for the logo and a number for a Seedling sprite**.

**The two seams are BridgeGeneric state properties, and they cost the bridge nothing.** `Game.pendingExit` is `"<seq>|<from>|<type>|<x>|<y>|<to>"`, written by `Teleporter.update()` before the world swap; `Game.pendingCheck` is `"<seq>|<level>|<tag>|<0|1>"`, written inside `setPersistence`. Both are declared in `games/seedling.json` **before `level`**, because BridgeGeneric builds its property list in declaration order and reports in it — measured on p4c against an existing String static, 18 declarations produced 18 first-burst reports in that order. Three facts about the channel shaped the payloads:

- **A property is reported only when its value CHANGED.** Two fires of one door, or two clears of one slot, would otherwise be reported once. Hence the `<seq>` prefix, which the host strips and never compares.
- **The level is the one the CALL names, not `Main.level`.** `ButtonRoom` writes another room's slot, and a report saying `Main.level` would address the wrong room.
- **The fourth field is the value written, and it is a filter.** `setPersistence` has ~50 callers — every door taken, every boss killed, every lock opened — and six of them RESTORE a slot with `true`. The host requires a clear, so a restore of a slot that happens to be an AP location's tag cannot send a check.

`keyMask` and `totemCount` are two static getters that close the ten key/totem locations `pendingCheck` cannot see: `BossKey.removed()` writes `Player.hasKeySet` and `BossTotemPart` its own count, neither touches persistence, and neither could be declared as it stood because `Main.hasKey(i)` is a FUNCTION and BridgeGeneric reads a property.

**Host side, `flashPanel/seedlingCheckBinding.js` turns a check report into `user:locationCheck`** — the same event and dialect the adapter's own location path publishes — plus a `{location, item, player}` readout the panel renders as *"found X for Player Y"*, answered off the placement table rather than after the server's `PrintJSON`. ⛔ Its filter is the **placement TABLE**, never a vanilla tag list: eleven of the 39 addresses are allocated tags the vanilla data never used, and `Lock.turnOff()` clears slots exactly the way a pickup does. The glue FANS the adapter's single `onStateReport` hook out to both bindings — a second consumer that assigned it would silently replace the region binding, and every crossing would stop working while every check kept working. And the adapter **stands down** on the locations the table covers: with an `APItem` in the room the game grants nothing, so the only writer of that `Main.*` flag is the bridge, and an echo the suppression missed would check the location twice and queue an undo that revokes the granted item. It is a SET and not a delete, because the two encounter locations must keep that path.

⚠ **On p4c the rewritten room shows NOTHING at an AP location**, because `Game.as`'s XML loop enumerates known element names and an unknown `<apitem>` is ignored. That absence is the transport gate's discriminator, not a defect: the `APItem` class that will stand there rides the next build. Gate: `scripts/procgen/verify-seedling-ap-placement.mjs` — a fresh page per arm, the shipped delivery module driven inside it, and the claim is the DIFFERENCE of the two arms' `botMobiles` rosters, which must be exactly the rewritten entities. Chest locations are reported NOT OBSERVABLE by name: `Chest` is Scenery and `botMobiles` walks `Mobile`.

### The panel wires it, and it DETECTS whether to — no opt-in flag

⚖ **USER, 2026-08-29: every frontend feature decides from the loaded preset's DATA whether it applies, and the build-side half of that decision is a `capabilities` list per build in `flashPanel/wasm/builds.json`.** So there is no setting, no query parameter and no per-preset boolean: at bridge-ready — the host's first moment of control, with the game already live in level 0 — `flashPanel/seedlingRandomizerEligibility.js` answers four questions in order and names the FIRST one that is false.

1. **The transport is wasm and the preset names a page.** Under real Flash the answer is one log line saying "wasm-only" (see above; `botLoadLevels` does not exist there).
2. **The build that preset names DECLARES `apitem`.** The panel fetches `wasm/builds.json` and looks up the entry whose `name` is the page's own directory — never a literal, so nothing here hardcodes a default. An entry with `capabilities: []` says *"measured, this build has none"*; an entry with NO `capabilities` field says nothing at all, and the two are kept distinct so a stale manifest reads as stale rather than as a build that lost a feature. `check-seedling-wasm-pins.mjs` makes the array mandatory and refuses any name outside the vocabulary — which it **imports** from the predicate rather than restating, because a gate spelled differently from its consumer tests itself.
3. **At least one goal-ledger location resolves against the loaded placement**, and the count is reported either way. Zero means these rules are not a Seedling seed; some-but-not-all is ordinary, and the remainder simply stay on the adapter's property path, which is what `hostOwnedLocations()` being a SET is for.
⛓ **AN INELIGIBLE-AT-(iii) PRESET STILL PAYS THE LAZY IMPORT, AND THAT IS BY DESIGN.** (iii) needs the goal ledger resolved against the room map, so the map has to be fetched before the question can be asked — which means a preset that turns out not to be a Seedling placement has already paid the 87-file import and the 976 KB document. MEASURED on the real page: `seedling_atlas` created its overlay 5.1 s after the panel came up and removed it at 12.4 s, i.e. **~7 s** for the import and the two fetches, then refused. The cost is bounded by (i) and (ii), which are cheap and run first: only a wasm preset naming a build that DECLARES `apitem` ever gets that far — today, exactly the three seedling presets.

4. **The vanilla record set and the room map are reachable**, and the answer says which map — a preset's own `region_atlas.map_document` when it names one, else the atlases default. ⛔ `region_atlas` is NOT in the panel's static-data surface (`statePersistence.js` enumerates the keys the worker posts and it is not among them), so it is read from `getLastRawJsonData()`, the documented catch-up path for raw-rules-only fields.

⛔ **THE THREE SEEDLING PRESETS ARE NOT WRITTEN IN ONE VOCABULARY, AND THE JOIN IS THE AP ID.** `seedling_playthrough` names its locations the way the goal ledger derives them (`"Level 010 - Sword"`) — 41 of 41 resolve directly. The stage-1 `seedling` preset carries the upstream Seedling APWorld's names (`"Penguin's Feather"`, `"Chest (Waterfall)"`) and **none** of them match. What does match is the id: its location records carry `"id": 20000000…`, which is `games/seedling.json`'s `ap_id_offset + ap_locations[k].id`. So the second path is exact rather than a spelling heuristic — ledger row → `flash_name` → AP id → the loaded location — and it resolves **40 of 41**. `seedling_atlas` has one location and resolves none, so it is refused at (iii) by its own data.

The `flash_name` step is derived four ways and **no alias table is typed**: a key names itself out of the ledger row's own id (`bosskey<N>` → `key<N>`, cross-checked against the entity's `@keyType`); a chest names its LEVEL (measured — the ledger's 16 chest levels are exactly the 16 `chestNN` entries); a totem part names the entity's own `@totempart` attribute, which is the one arm the ledger id cannot answer because it addresses by pixel position; and everything else is the tag, or — needed exactly once — the `locations[]` row whose `ap_name` is `ITEM_FOR_TAG[tag]`, which is how `torchpickup` reaches `torch` through `"Light"`.

⛓ **The one row that does not resolve is REPORTED and the ledger is FILTERED, never the preset refused.** `buildPlacementTable` throws by name when a rewritable row has no placement — deliberately, because that is an item nobody could find. The stage-1 preset has no location for `seed@L115` (upstream the goal is an event, not a check), and refusing 38 good placements over one absent goal row is the wrong trade. The ledger is already an injected parameter, so it is filtered to the rows that resolve and the dropped ones are named in the panel log; a dropped location cannot be in the table and therefore cannot be host-owned, so it keeps the property path.

**The load sequence, as ruled: a loading indicator, then a reset to the set's own start.** Overlay on → `setDelivery` on the glue → `deliver()` → the reset → `setCheckBinding` → overlay off. A refusal shows why, does NOT reset and does NOT bind, because a vanilla room must keep the property path. Two things about it were measured rather than chosen:

- **Progress is by PHASE, not by chunk.** `deliver()` is synchronous and sends all nine chunks in one loop with no per-chunk hook, and a browser cannot paint inside a synchronous loop — a *"rooms k/N"* readout would be a number nobody ever sees. Each phase sets the text and awaits a frame.
- **The reset mode is decided by the SET.** `vanillaRecordSet(...).set.start` is `{"level": 0}` — level only, no position; `levelSetExporter` says in its own words that the arrival position then *"falls to the Game constructor's own (80, 128)"*, a constant that belongs to `Main.as` and which `region_coords` cannot derive (it has no level-0 row). So a start WITH a position takes the explicit `new_instance Game($level,$x,$y)` teleport, and a start with only a level takes the game's own new-game arm (`level < 0` → `LevelSet.applyStart`), which is the only thing that knows the spawn.

⚠ **What the host can see of a world swap is CONSTRUCTION, not the swap.** `Main.level` and `Main.playerPositionX/Y` are both written by `Game`'s constructor, which runs before `Engine.checkWorld()` swaps — so polling either declared property proves the object was built. `botMobiles()` enumerates whatever `FP.world` IS, so the confirmation is *"the expected level AND a roster"*, polled with a named timeout. Never slept: a wall-clock settle in a browser is a frame budget in disguise.

⛔⛔ **THE WHOLE HEAVY HALF IS BEHIND A SPECIFIER THE BUNDLER CANNOT SEE, AND A LITERAL `await import()` DOES NOT ACHIEVE THAT.** `scripts/build/bundle-frontend.js` runs esbuild with `bundle: true` and **`splitting: false`**, so it resolves a literal dynamic specifier at build time and inlines the module. Measured, four builds of `node scripts/build/bundle-frontend.js --no-minify`, which prints its own input count:

| what `flashPanel/` does | inputs | bundle bytes |
|---|---|---|
| baseline | 494 | 8,584,629 |
| `import {X} from '../seedlingDemo/apPlacementRewriter.js'` | 574 (+80) | 9,394,789 |
| `await import('../seedlingDemo/apPlacementRewriter.js')` | 581 (+87) | 9,481,672 |
| `await import(<a computed URL>)` | 494 (+0) | 8,584,894 |

The literal dynamic form costs **seven files more than the static one**, because a namespace object defeats tree-shaking. "Lazy" is a property of whether the bundler can see the string, not of the `await`. The base is `document.baseURI` and never `import.meta.url`: in the bundled build the module IS `frontend/dist/bundle.js`, so a module-relative resolve would look in `dist/`. As shipped, the panel's whole randomizer costs the bundle **+2 files and +14,577 B** — the eligibility predicate and the readout — and `dist/metafile.json` confirms that `apPlacementRewriter`, `levelSetExporter`, `levelSetValidator`, `r7Acceptance`, `seedlingAtlasDerivation` and the wiring module itself are all absent from its inputs.

**The readout.** The glue's *"found X for Player Y"* line still goes to `.flash-panel-log` — the log is the transcript — and beside it `seedlingRandomizerReadout.js` keeps the STATE: how many placements this session has found and the last three, `"you"` for this slot's own item. It is created beside the panel's `apItemFound` handler and dropped with it, one lifetime, because a remounted panel that kept either would count into a detached element.

### Crossing OUT of this substrate — `external`

A world can wire a Seedling room's door to a room another substrate plays. The compiled exit says so: `external: true` plus `target_substrate`, with **`target_level` and `target_spawn` null**.

Both halves are load-bearing. The null is not tidiness — before it, the compiler copied the target region's `map_ref` into `target_level`, and a maze region's `map_ref` is its *library entry index*. So a Seedling room with both a same-substrate and a cross-substrate door carried two exits claiming the same `target_level`, and `resolveCrossingExit`'s two-candidate tie-break could send an ordinary walk home through the maze door. Nulling it drops the exit from that filter by construction (`null !== 0`) with no change to the host.

The field is **present-or-absent**, never `external: false`: every committed flash sidecar is byte-pinned, and a boolean on every exit would move all of them. `report.external_exits` counts the crossings off the emitted sidecars.

**The DEPARTURE is host-driven, and it needs a report the `level` change cannot give.** `FP.world = x` only writes `FP._goto`, but `new Game(to,..)` sets `Main.level` in its own constructor — so by the time the level report moves, WHICH door fired is already unrecoverable. `pendingExit` lands one report earlier. `seedlingRegionBinding` rebuilds the atlas exit id as `out_<type>_<x>_<y>` (pinned against `seedlingAtlasDerivation.outExitId`, not respelt) and acts only when the matched exit carries `external`; the other three cases are silent, each for its own reason — the empty boot report is not a door, a door the region does not declare is the atlas being partial by design, and a same-substrate door is an ordinary crossing the `level` arm resolves better.

The game then swaps **anyway**, into a real room of its own set: design (c), so it never learns what a world is and `@to` needs no rewriting. That swap's own `level` report is a move already published as a crossing, so it is marked and swallowed — trap 1 pointed the other way. ⛔ The mark's AGE is checked before its level, and that is not cosmetic: a mark matches exactly one level, so testing equality first would make the timeout decorative and the player's genuine return through that door minutes later would still be swallowed.

An external door is **host-driven**. Seedling's only transition primitive is a one-way jump to a declared point, so a world link out of Seedling is authored `one_way: true` and the return leg is a second link from the other side; the game itself learns nothing about worlds. Today the host recognises such a door in the payload and parks while the other substrate plays — what it cannot yet do is notice the *departure* at the moment it happens, because the game's `level` report has already moved by the time the swap lands and carries no door identity. That was M1's work and it landed; the departure report is `pendingExit`, described above.

Gate: `scripts/procgen/verify-seedling-atlas-play.mjs` (skips when the wasm artifact is absent).

The same atlas also compiles to a **maze**-flavoured preset (`seedling_atlas_maze`) — the same geometry and the same computed item gating, playable with no wasm artifact, which is why the in-app suite can test that one and not this one. The two are separate presets — but *never merged* was always the narrower claim than it sounded. What holds is **one sidecar per AP region**: the player's warehouse has one slot per region and dispatches that region's load event by the sidecar's own substrate id, so two sidecars for one region would ask two substrates to own it. What does NOT hold, since the editor-integration arc, is one substrate per preset. An atlas region may name its own `substrate`, `compileRegionAtlas` dispatches the sidecar builder per region on it, and a single preset may therefore carry real flash rooms beside maze ones. The flavour is only what a region that names nothing falls back to. See [Maze Substrate](./maze.md#a-real-games-map-as-maze-regions).
