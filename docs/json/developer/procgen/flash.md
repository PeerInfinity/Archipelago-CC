# Flash Substrate

The flash substrate (`frontend/modules/flashSubstrate/`, id `flash`) hosts recompiled Flash games — SWF → C → WASM via SWFRecomp-CC — in a same-origin iframe as procgen regions. The module ships a placeholder game page, so it is testable independently of any real recompiled game; its real significance is as the **shared iframe-substrate machinery** other substrates build on.

## The `__swfBridge` contract

The game page owns `window.__swfBridge.configure` / `pollItems` (the game side of the contract); the host-injected `bridge.js` completes the iframeAdapter handshake, configures the game from the region payload, applies received items via `pollItems`, and dispatches `user:locationCheck` when the game's ActionScript cooperatively calls `__swfBridge.sendLocation`. The host module (`index.js`) brokers `flash:loadRegion` activation and brings the panel forward.

## Per-game entries (one panel, many ids)

`createFlashSubstrateEntry` (`flashSubstrateLibrary.js`) is a factory: each Flash game can register its **own substrate id** with its own `supportedFeatures`, while every entry resolves to the same panel component and `flash:loadRegion` event. The module itself registers only the generic `flash` entry (a region whose game is identified purely by the payload's `gameId`). The factory also supplies the runtime plumbing — the exits-Map `deserializeWorld`/`serializeWorld` round-trip and a null playback stub — which is exactly what **bounce** builds its entry on top of, overriding the panel identity and adding build-time hooks ([Bounce Substrate](./bounce.md)).

The `iframeId` field on flash-family entries closes an init race: procgenPlayer re-publishes the active region's load event when that iframe announces `appReady`, covering both the initial load-before-subscribe window and iframe reloads.

## Capabilities

Flash regions are opaque minigames by default: `arbitrary_ap_locations` only, no build-time generation hooks (procgen just records `gameId` + params in the sidecar), no playback controller, and loop support of queueable `regionMove` plus manual play. Full contract: [Substrate Registry Reference](./substrate-registry.md).

## `flash_seedling` — a real game's map as procgen regions

`flash_seedling` (`frontend/modules/flashPanel/flashSeedlingLibrary.js`) is the region atlas's play-time substrate: a region is a **real Seedling level**, marked out in the atlas and compiled into `preset_sidecars` by `procgenPipeline/regionAtlasCompiler.js` (plan: `CC/docs/plans/region-atlas-plan.md`, Phase 4). It is built on `createFlashSubstrateEntry` but differs from every other flash-family entry in two ways, both deliberate:

- **It renders in `flashPanel`, not `flashSubstratePanel`,** and therefore owns its own `flashSeedling:loadRegion` event (the bounce precedent). The game is driven by flashPanel's shipped `WasmBridgeAdapter` — teleports, item writes, progressive/fusion expansion, location checks. Building a second AP↔game translation inside flashSubstrate's in-iframe bridge would duplicate solved work, and the dialects differ anyway: the SWFRecomp wasm shim speaks `game.configure(json)` + `queueItems`, the substrate bridge speaks `__swfBridge.configure(obj)` + `pollItems`.
- **It declares no `iframeId`.** flashPanel's embed is a plain `<iframe>` that never announces `iframe:appReady`, so procgenPlayer's re-publish race-closer has nothing to fire on. The equivalent is handled inside the glue instead (below).

### The host-side glue

`seedlingRegionBinding.js` is a pure state machine (region load + property reports in, effects out); `seedlingRegionGlue.js` applies the effects. Detection is **level-granular**: an atlas region binds to a whole level, so a boundary crossing is the game's own `Main.level` change, tie-broken on the reported spawn coordinates when two exits of one region reach the same level. Sub-level physical boundaries (live player x/y against a marked tile line) are deferred — they need BridgeGeneric changes, re-injection and a wasm rebuild. Logical sub-regions are unaffected: they carry rules and are never physically triggered, so every sub-region of a region shares its level.

The signals are three `Main` statics declared in `games/seedling.json` — `playerPositionX`, `playerPositionY`, `level`, in that order, so a `new Game(level, x, y)` reports its tie-break coordinates before the level change. They ride the **one** configure at boot: `BridgeGeneric.doConfigure` refuses a second configure for the life of a game instance, so widening the set later needs a page reload.

Three behaviours are worth knowing before touching this:

| | |
|---|---|
| **Teleport echo** | The glue's own arrival teleport changes `level`, and that report is indistinguishable from the player walking through a door. An arrival is marked in flight and its matching report swallowed, clearing on match or after 15 s. A teleport to the level the game is *already* on arms nothing — arming would eat the next real crossing. |
| **First-read baseline** | BridgeGeneric reports the whole declared set at boot, so the first `level` report is where the game already is, not a crossing. It doubles as the "game is alive" signal that releases an arrival queued while the wasm page was still waiting on its own ▶ Start gesture (which can take minutes). |
| **Unmapped levels** | The starter atlas covers 3 of Seedling's 116 levels, by design. A level change the current region has no exit to **warns loudly** on both the console and the panel log and does *not* move the AP region. A silent no-op would read as a complete map; a crash would make a partial atlas unusable. |
| **The park** | While ANOTHER substrate owns the region, the game keeps running — flashPanel has no inactive overlay, deliberately (below) — so the binding is PARKED instead: the glue subscribes `procgen:activeSubstrateChanged` and every property report is dropped, position included, no crossing published, no warn, no echo armed, and an in-flight echo cleared. An arrival that lands meanwhile (procgenPlayer publishes the target's `loadRegion` **before** the broadcast, so the return leg always does) is queued on the same slot the not-yet-booted case uses and released exactly once. Default is ACTIVE, so a preset that never broadcasts is unaffected. |

`arrivedFrom` is consumed **host-side** here — flashSubstrate's own bridge drops it — which is what makes "arrive at the exit you came through" work. With no arrivedFrom (the synthesized `Menu → start-region` hop, or a move whose source region is outside the warehouse) the region's first declared exit stands in; that is an info line, not a warning.

No `SubstrateInactiveOverlay` in v1: the flashPanel panel predates the overlay and is not procgen-only (it still serves the Stage-1 direct-client presets), so wiring the overlay would mean teaching it a panel that is legitimately active with no procgen substrate at all. Deliberately skipped rather than half-wired. That ruling stands — what changed is the BINDING, not the panel: parking is about which reports may be read as AP movement. (Since T2b the panel does own the game's KEYBOARD: see *Playing a placed room* below.)

### AP's item placement — the room is rewritten, the host owns every grant

The randomizer does not write item flags into a running game: it puts AP's item **in the room**. `seedlingDemo/apPlacementRewriter.js` takes the AP placement (`stateManager.getLocationItem`, injected — `seedlingDemo/` never imports the host's state manager) and the vanilla 116 as a `record`-sourced set, and replaces exactly the pickup entity at each randomized location with an `<apitem>` carrying two attributes: `@tag`, the persistence slot that is the location's address, and `@look`, the graphic. Every other byte of every room is identical, measured on the emitted OEL rather than on a substitution count. `flashPanel/seedlingLevelSetDelivery.js` then delivers that set — `botLoadLevels` per chunk, `botLevelSet` read back and diffed — and `seedlingRegionGlue` gates the first `flashSeedling:loadRegion` on it, because a region load teleports the player into a room and replacing the room under the player afterwards is a different game.

**The `look` vocabulary is 21 names and every one is derived** — `ITEM_FOR_TAG`'s 14 keys, `bosskey0`…`bosskey4`, `seed`, and `ap` (the Archipelago logo, for a foreign player's item or an item this world names no graphic for). Three facts shape it:

- **`ITEM_FOR_TAG` is not injective.** 14 tags carry 12 item names: `Progressive Shield` is both `shield` and `darkshield`, `Progressive Swim` both `conch` and `feather`. So "the inverse" is not a function, and the tie-break is ruled: the destination's own vanilla graphic when the item wears it too, otherwise the first in `ITEM_FOR_TAG`'s own key order. The book is BUILT from the goal ledger's rows, never typed, so a new tag is followed automatically.
- **A `look` must determine one sprite alone.** `BossKey` picks its graphic with `Game.bossKeys[_t]`, so a bare `bosskey` would leave the game guessing and a Green Key placed where the Red one sat would render red. The index comes from `ITEM_FOR_KEY` and is cross-checked against the element's own `@keyType`.
- **`Fire` renders as `ap`.** It is an encounter grant with no pickup entity anywhere, so no table in this repository names a graphic for it. Stated rather than patched.

**11 of the 39 rewritable locations have no vanilla `@tag`.** `bosskey`, `totempart` and `seed` take none in `Game.as`'s XML loop, so their address is ALLOCATED through `procgenSeedling.placementTagId` — the repo's one writer of that rule — composing per level, which matters because level 40 needs three and already spends 23 of the game's 30 slots. The two `encounter` rows (the BobBoss drop, the Witch trade) are **not** rewritten: their entities are a falling rock and an NPC, and they are reported by name for the check binding to serve through the existing property path.

**A rewrite moves none of the 24 vanilla AP references and falsifies eleven.** It adds no room, removes none, reorders none and repaints no tile, so every level id and coordinate in `region_coords`, `location_coords` and the atlas's `map_ref`s still resolves to the same room at the same tile. But `location_coords`' whole content is *"the Sword is at level 10, (48, 64)"*, and each of those tiles now holds an `apitem`. So `apMappingInvalidation`'s companion is a **precondition**: the delivery refuses a set that arrives without its own stamped one.

⛔ **Wasm-only, and the reason is not a policy.** Real Flash's `seedling_injected.swf` carries no `bot*` verb at all, so `botLoadLevels` cannot exist there. The Ruffle arm keeps doing what it does today — BridgeGeneric property writes, `readState`, teleport — it simply cannot be handed a rewritten level set.

**`seedling_bot_ap_p4d` is the build the placement can actually be PLAYED on**, and it is the only build carrying the two report seams. Five AS3 files, ~11 substantive lines plus one class: `Pickups/APItem.as` is built from the `<apitem>` element, **grants nothing**, and calls `Game.setPersistence(tag, false)` on collection — the engine's own collected marker, since `buildLevelPersistence` fills the table with `true` meaning *"nothing cleared"*. Its sprite comes from a `look → [PNG, frameW, frameH]` table of sixteen re-embedded graphics plus the shared `Game.bossKeys[N]`; the graphics are re-embedded rather than borrowed from a throwaway vanilla instance because `Chest`'s own field initialiser calls `Rng.cos()`, so constructing one to steal its graphic would move the RNG stream every tape is recorded against. `look == "ap"` binds a plain `Image` where every Seedling look binds a `Spritemap`, which is what makes the placeholder observable without a single pixel: `botMobiles` reports `frame` as `graphic as Spritemap`, i.e. **null for the logo and a number for a Seedling sprite**.

**The two seams are BridgeGeneric state properties, and they cost the bridge nothing.** `Game.pendingExit` is `"<seq>|<from>|<type>|<x>|<y>|<to>"`, written by `Teleporter.update()` before the world swap; `Game.pendingCheck` is `"<seq>|<level>|<tag>|<0|1>"`, written inside `setPersistence`. Both are declared in `games/seedling.json` **before `level`**, because BridgeGeneric builds its property list in declaration order and reports in it — measured on p4c against an existing String static, 18 declarations produced 18 first-burst reports in that order. Three facts about the channel shaped the payloads:

- **A property is reported only when its value CHANGED.** Two fires of one door, or two clears of one slot, would otherwise be reported once. Hence the `<seq>` prefix, which the host strips and never compares.
- **The level is the one the CALL names, not `Main.level`.** `ButtonRoom` writes another room's slot, and a report saying `Main.level` would address the wrong room.
- **The fourth field is the value written, and it is a filter.** `setPersistence` has ~50 callers — every door taken, every boss killed, every lock opened — and six of them RESTORE a slot with `true`. The host requires a clear, so a restore of a slot that happens to be an AP location's tag cannot send a check.

`keyMask` and `totemCount` are two static getters that close the ten key/totem locations `pendingCheck` cannot see: `BossKey.removed()` writes `Player.hasKeySet` and `BossTotemPart` its own count, neither touches persistence, and neither could be declared as it stood because `Main.hasKey(i)` is a FUNCTION and BridgeGeneric reads a property.

**Host side, `flashPanel/seedlingCheckBinding.js` turns a check report into `user:locationCheck`** — the same event and dialect the adapter's own location path publishes — plus a `{location, item, player}` readout the panel renders as *"found X for Player Y"*, answered off the placement table rather than after the server's `PrintJSON`. ⛔ Its filter is the **placement TABLE**, never a vanilla tag list: eleven of the 39 addresses are allocated tags the vanilla data never used, and `Lock.turnOff()` clears slots exactly the way a pickup does. The glue FANS the adapter's single `onStateReport` hook out to both bindings — a second consumer that assigned it would silently replace the region binding, and every crossing would stop working while every check kept working. And the adapter **stands down** on the locations the table covers: with an `APItem` in the room the game grants nothing, so the only writer of that `Main.*` flag is the bridge, and an echo the suppression missed would check the location twice and queue an undo that revokes the granted item. It is a SET and not a delete, because the two encounter locations must keep that path.

⚠ **On p4c the rewritten room shows NOTHING at an AP location**, because `Game.as`'s XML loop enumerates known element names and an unknown `<apitem>` is ignored. That absence is the transport gate's discriminator, not a defect: the `APItem` class that stands there instead rides p4d. ⛓ **And that is why p4c is still pinned after slice P2 made p4d the default** — it is the only tracked build declaring no `apitem`, so it is the CONTROL arm of this pair and of P1-e's `panel-control-p4c`; `check-seedling-wasm-pins.mjs` row (f) requires this gate's `SEEDLING_PAGE` default to name an `apitem`-less build, and retiring p4c means MOVING that default rather than deleting it. Gate: `scripts/procgen/check-seedling-ap-placement.mjs` — a fresh page per arm, the shipped delivery module driven inside it, and the claim is the DIFFERENCE of the two arms' `botMobiles` rosters, which must be exactly the rewritten entities. Chest locations are reported NOT OBSERVABLE by name: `Chest` is Scenery and `botMobiles` walks `Mobile`.

### The panel wires it, and it DETECTS whether to — no opt-in flag

⚖ **USER, 2026-08-29: every frontend feature decides from the loaded preset's DATA whether it applies, and the build-side half of that decision is a `capabilities` list per build in `flashPanel/wasm/builds.json`.** So there is no setting, no query parameter and no per-preset boolean: at bridge-ready — the host's first moment of control, with the game already live in level 0 — `flashPanel/seedlingRandomizerEligibility.js` answers four questions in order and names the FIRST one that is false.

1. **The transport is wasm and the preset names a page.** Under real Flash the answer is one log line saying "wasm-only" (see above; `botLoadLevels` does not exist there).
2. **The build that preset names DECLARES `apitem`.** The panel fetches `wasm/builds.json` and looks up the entry whose `name` is the page's own directory — never a literal, so nothing here hardcodes a default. An entry with `capabilities: []` says *"measured, this build has none"*; an entry with NO `capabilities` field says nothing at all, and the two are kept distinct so a stale manifest reads as stale rather than as a build that lost a feature. `check-seedling-wasm-pins.mjs` makes the array mandatory and refuses any name outside the vocabulary — which it **imports** from the predicate rather than restating, because a gate spelled differently from its consumer tests itself.
3. **At least one goal-ledger location resolves against the loaded placement**, and the count is reported either way. Zero means these rules are not a Seedling seed; some-but-not-all is ordinary, and the remainder simply stay on the adapter's property path, which is what `hostOwnedLocations()` being a SET is for.
⛓ **AN INELIGIBLE-AT-(iii) PRESET STILL PAYS THE LAZY IMPORT, AND THAT IS BY DESIGN.** (iii) needs the goal ledger resolved against the room map, so the map has to be fetched before the question can be asked — which means a preset that turns out not to be a Seedling placement has already paid the 87-file import and the 976 KB document. MEASURED on the real page: `seedling_atlas` created its overlay 5.1 s after the panel came up and removed it at 12.4 s, i.e. **~7 s** for the import and the two fetches, then refused. The cost is bounded by (i) and (ii), which are cheap and run first: only a wasm preset naming a build that DECLARES `apitem` ever gets that far — today, exactly the three seedling presets.

4. **The vanilla record set and the room map are reachable**, and the answer says which map — a preset's own `region_atlas.map_document` when it names one, else the atlases default. ⛔ `region_atlas` is NOT in the panel's static-data surface (`statePersistence.js` enumerates the keys the worker posts and it is not among them), so it is read from `getLastRawJsonData()`, the documented catch-up path for raw-rules-only fields.

⛔ **THE THREE SEEDLING PRESETS ARE NOT WRITTEN IN ONE VOCABULARY, AND THE JOIN IS THE AP ID.** `seedling_playthrough` names its locations the way the goal ledger derives them (`"Level 010 - Sword"`) — 41 of 41 resolve directly. The stage-1 `seedling` preset carries the upstream Seedling APWorld's names (`"Penguin's Feather"`, `"Chest (Waterfall)"`) and **none** of them match. What does match is the id: its location records carry `"id": 20000000…`, which is `games/seedling.json`'s `ap_id_offset + ap_locations[k].id`. So the second path is exact rather than a spelling heuristic — ledger row → `flash_name` → AP id → the loaded location — and it resolves **40 of 41**. `seedling_atlas` has one location and resolves none, so it is refused at (iii) by its own data.

The `flash_name` step is derived four ways and **no alias table is typed**: a key names itself out of the ledger row's own id (`bosskey<N>` → `key<N>`, cross-checked against the entity's `@keyType`); a chest names its LEVEL (measured — the ledger's 16 chest levels are exactly the 16 `chestNN` entries); a totem part names the entity's own `@totempart` attribute, which is the one arm the ledger id cannot answer because it addresses by pixel position; and everything else is the tag, or — needed exactly once — the `locations[]` row whose `ap_name` is `ITEM_FOR_TAG[tag]`, which is how `torchpickup` reaches `torch` through `"Light"`.

⛓ **The one row that does not resolve is REPORTED and the ledger is FILTERED, never the preset refused.** `buildPlacementTable` throws by name when a rewritable row has no placement — deliberately, because that is an item nobody could find. The stage-1 preset has no location for `seed@L115` (upstream the goal is an event, not a check), and refusing 38 good placements over one absent goal row is the wrong trade. The ledger is already an injected parameter, so it is filtered to the rows that resolve and the dropped ones are named in the panel log; a dropped location cannot be in the table and therefore cannot be host-owned, so it keeps the property path.

**The load sequence, as ruled: a loading indicator, then a reset to the set's own start.** Overlay on → `setDelivery` on the glue → `deliver()` → the reset → `setCheckBinding` → overlay off. A refusal shows why, does NOT reset and does NOT bind, because a vanilla room must keep the property path. Two things about it were measured rather than chosen:

- **Progress is by PHASE, not by chunk.** `deliver()` is synchronous and sends all nine chunks in one loop with no per-chunk hook, and a browser cannot paint inside a synchronous loop — a *"rooms k/N"* readout would be a number nobody ever sees. Each phase sets the text and awaits a frame.
- **The reset mode is decided by the SET.** `vanillaRecordSet(...).set.start` is `{"level": 0}` — level only, no position; `levelSetExporter` says in its own words that the arrival position then *"falls to the Game constructor's own (80, 128)"*, a constant that belongs to `Main.as` and which `region_coords` cannot derive (it has no level-0 row). So a start WITH a position takes the explicit `new_instance Game($level,$x,$y)` teleport, and a start with only a level takes the game's own new-game arm (`level < 0` → `LevelSet.applyStart`), which is the only thing that knows the spawn.

⛓⛓ **AND WHERE THE RESET'S BOOT POSITION COMES FROM IS ITSELF A READOUT, because the fallback is silent** (slice P2 residue, ⚖ §17.4.8). `seedlingRandomizerWiring` prefers `SeedlingRegionBinding.lastSpawn`/`lastLevel` — `Main.playerPositionX/Y` and `level`, the CONSTRUCTOR'S OWN ARGUMENTS, which the binding already consumes off every declared report — so the happy path needs no half-tile arithmetic at all, and `lastLevel` is what arms the wrong-room guard. ⛔ **Read, never written: the wiring does not touch the binding's state**, so the two modules stay one-directional and a parked binding is not corrupted by a reset. The fallback derives the position from the ROSTER, less the map's own `tile_size / 2` — correct, but arithmetic on an entity position rather than the argument that produced it, and it fires whenever the binding has seen nothing (it drops every report while parked, and a preset with no sidecars may never have gone active). Those two answers look identical downstream. ⇒ the reset reports a **`source`** row — *"the binding's last declared playerPosition"* vs *"the roster, less the map's half-tile (N)"* — and that row is the only thing that catches a silent fall to the second: a guard armed off a derived level is a guard armed off arithmetic nobody checked.

⚠ **What the host can see of a world swap is CONSTRUCTION, not the swap.** `Main.level` and `Main.playerPositionX/Y` are both written by `Game`'s constructor, which runs before `Engine.checkWorld()` swaps — so polling either declared property proves the object was built. `botMobiles()` enumerates whatever `FP.world` IS, so the confirmation is *"the expected level AND a roster"*, polled with a named timeout. Never slept: a wall-clock settle in a browser is a frame budget in disguise.

⛔⛔ **THE WHOLE HEAVY HALF IS BEHIND A SPECIFIER THE BUNDLER CANNOT SEE, AND A LITERAL `await import()` DOES NOT ACHIEVE THAT.** `scripts/build/bundle-frontend.js` runs esbuild with `bundle: true` and **`splitting: false`**, so it resolves a literal dynamic specifier at build time and inlines the module. Measured, four builds of `node scripts/build/bundle-frontend.js --no-minify`, which prints its own input count:

| what `flashPanel/` does | inputs | bundle bytes |
|---|---|---|
| baseline | 494 | 8,584,629 |
| `import {X} from '../seedlingDemo/apPlacementRewriter.js'` | 574 (+80) | 9,394,789 |

"Lazy" is a property of whether the bundler can see the string, not of the `await`. The base is `document.baseURI` and never `import.meta.url`: in the bundled build the module IS `frontend/dist/bundle.js`, so a module-relative resolve would look in `dist/`. As shipped, the panel's whole randomizer costs the bundle **+2 files and +14,577 B** — the eligibility predicate and the readout — and `dist/metafile.json` confirms that `apPlacementRewriter`, `levelSetExporter`, `levelSetValidator`, `r7Acceptance`, `seedlingAtlasDerivation` and the wiring module itself are all absent from its inputs.

**The readout.** The glue's *"found X for Player Y"* line still goes to `.flash-panel-log` — the log is the transcript — and beside it `seedlingRandomizerReadout.js` keeps the STATE: how many placements this session has found and the last three, `"you"` for this slot's own item. It is created beside the panel's `apItemFound` handler and dropped with it, one lifetime, because a remounted panel that kept either would count into a detached element.

### Crossing OUT of this substrate — `external`

A world can wire a Seedling room's door to a room another substrate plays. The compiled exit says so: `external: true` plus `target_substrate`, with **`target_level` and `target_spawn` null**.

Both halves are load-bearing. The null is not tidiness — before it, the compiler copied the target region's `map_ref` into `target_level`, and a maze region's `map_ref` is its *library entry index*. So a Seedling room with both a same-substrate and a cross-substrate door carried two exits claiming the same `target_level`, and `resolveCrossingExit`'s two-candidate tie-break could send an ordinary walk home through the maze door. Nulling it drops the exit from that filter by construction (`null !== 0`) with no change to the host.

The field is **present-or-absent**, never `external: false`: every committed flash sidecar is byte-pinned, and a boolean on every exit would move all of them. `report.external_exits` counts the crossings off the emitted sidecars.

**The DEPARTURE is host-driven, and it needs a report the `level` change cannot give.** `FP.world = x` only writes `FP._goto`, but `new Game(to,..)` sets `Main.level` in its own constructor — so by the time the level report moves, WHICH door fired is already unrecoverable. `pendingExit` lands one report earlier. `seedlingRegionBinding` rebuilds the atlas exit id as `out_<type>_<x>_<y>` (pinned against `seedlingAtlasDerivation.outExitId`, not respelt) and acts only when the matched exit carries `external`; the other three cases are silent, each for its own reason — the empty boot report is not a door, a door the region does not declare is the atlas being partial by design, and a same-substrate door is an ordinary crossing the `level` arm resolves better.

The game then swaps **anyway**, into a real room of its own set: design (c), so it never learns what a world is and `@to` needs no rewriting. That swap's own `level` report is a move already published as a crossing, so it is marked and swallowed — trap 1 pointed the other way. ⛔ The mark's AGE is checked before its level, and that is not cosmetic: a mark matches exactly one level, so testing equality first would make the timeout decorative and the player's genuine return through that door minutes later would still be swallowed.

An external door is **host-driven**. Seedling's only transition primitive is a one-way jump to a declared point, so a world link out of Seedling is authored `one_way: true` and the return leg is a second link from the other side; the game itself learns nothing about worlds. Today the host recognises such a door in the payload and parks while the other substrate plays — what it cannot yet do is notice the *departure* at the moment it happens, because the game's `level` report has already moved by the time the swap lands and carries no door identity. That was M1's work and it landed; the departure report is `pendingExit`, described above.

Gates: `scripts/procgen/check-seedling-atlas-play.mjs` (the compiled atlas), `check-seedling-spiral-room-play.mjs` (a room the spiral placed: departures through `external` doors, fired by the game), and `check-seedling-sphere-room-play.mjs` (a room sphere growth placed as a leaf behind a maze gate); all skip when the wasm artifact is absent. The two room gates share their hands in `scripts/procgen/seedlingRoomPlay.js`.

The same atlas also compiles to a **maze**-flavoured preset (`seedling_atlas_maze`) — the same geometry and the same computed item gating, playable with no wasm artifact, which is why the in-app suite can test that one and not this one. The two are separate presets — but *never merged* was always the narrower claim than it sounded. What holds is **one sidecar per AP region**: the player's warehouse has one slot per region and dispatches that region's load event by the sidecar's own substrate id, so two sidecars for one region would ask two substrates to own it. What does NOT hold, since the editor-integration arc, is one substrate per preset. An atlas region may name its own `substrate`, `compileRegionAtlas` dispatches the sidecar builder per region on it, and a single preset may therefore carry real flash rooms beside maze ones. The flavour is only what a region that names nothing falls back to. See [Maze Substrate](./maze.md#a-real-games-map-as-maze-regions).

### As a content source in the pipeline

Since SEEDLING IN THE PIPELINE T1 (2026-09-23) the entry is also a **zone content source** ([Substrate Registry § *Build-time — content sources*](./substrate-registry.md#build-time--content-sources-zone-based-substrates)), so the shuffled spiral can place a real Seedling room beside generated rooms: `substrateQuotas: {maze: 3, flash_seedling: 1}` builds a world whose `flash_seedling` region plays the real level in the real game. It is the first procgen mode that builds *around* existing content rather than generating all of it.

- **The pool is one compile.** `applyPipelineConfig({atlasDoc})` installs a region atlas (default: the starter atlas `atlases/seedling.json`, a static JSON import, because a preset carries no `substrateConfig`). The pool is read off `compileRegionAtlas` of that atlas — the same payload `seedling_atlas` commits, byte for byte (a row pins it). An entry is one AP region: a sub-region where the atlas region has a subgraph.
- **Only rooms with a door are placeable.** A placed room is entered through a door (`resolveArrivalSpawn` lands the player at that door: on the game's own return spawn for it, see *Playing a placed room*), so a region whose compiled payload lists no exit cannot be placed. `zoneCount` counts the others, in the compile's order. On the starter atlas that is 4 of 10: `overworld_start__r8c0` (2 doors), `starting_house` (1), `owls_nest_entrance` (2), `dungeon1_room1__r0c4` (1). The payload lists only WIRED doors, so the five unwired teleporters stay out.
- **Doors are bound to sides by order.** A Seedling door has no side and the grid asks for sides, so the k-th side the driver asks for takes the k-th door in payload order (the maze atlas hook's relabel rule, ⚖ the user 2026-09-22 Q10). The door keeps its atlas `exit_id` (what a departure is matched against), the engine's `exit_<side>` rides `exitName`, and its `side` is the grid's. A surplus door is left out of the sidecar with a `pruned_exit` note (the spiral surfaces these on `stats.contentNotes`); it stays in the level and fires the real game's own transition. A cell that needs more sides than the room has doors is **refused by name**, with a sentence saying what to lower: the spiral's quota check cannot see a door count. A door's `exitRules` entry is its authored rule, read by the atlas pool's `boundaryRule`.
- **Every bound door is `external`** (§ *Crossing OUT of this substrate* above), with `target_level`/`target_spawn` null: its far side is whatever the grid put there, never the level the real game's door leads to. `target_substrate` is resolved after stitching, through the 5th argument `buildPresetSidecars` passes to `serializeWorld` (`{substrateOfRegion}`). ⚠ **No consumer reads `target_substrate` today.** It is provenance. The binding acts on `external` alone, so do not assume a reader exists.
- **Arrival and departure, as the binding resolves them.** An arrival tries `exit_id`, then `exitName` (worlds that link reverse exits), then the exit whose `targetRegion` is `arrivedFrom.source_region`. The shuffled spiral never sets `targetExitId`, so procgenPlayer hands over the SOURCE exit's own name, and only the source region identifies the door. A departure tries `out_<type>_<x>_<y>` first, then the door's tile (report pixels over the payload's `tile_size`) in `exit_tiles`: the starter atlas names its doors, so its ids cannot be rebuilt from a report.
- **The two top-level blocks.** A world that realised ≥1 `flash_seedling` region carries `region_atlas` and `flash_panel` exactly as the installed atlas's compile writes them. They come through the registry's `rulesJsonBlocks()`, which `buildRulesJson` asks only of substrates that realised a region, so every other world's bytes are unchanged. The flash panel engages on `flash_panel`.

The world above is pinned headless by `flashPanel/seedlingSpiralWorld.test.js`: one room, real doors, external to the maze, schema-valid, every region reachable, byte-identical twice. Sphere growth places one as a LEAF (below); top-down does not place these rooms.

### Playing a placed room

SEEDLING IN THE PIPELINE T2 (2026-09-23) committed that world as the `seedling_spiral_room` preset (`frontend/?game=seedling_spiral_room&seed=1`). It is written from `SEEDLING_SPIRAL_ROOM_STATE` in `procgenPipeline/presetDefs.js` by `make-seedling-spiral-room-preset.mjs --check`. The same state is the panel's *Seedling room in a maze spiral* preset. `scripts/procgen/check-seedling-spiral-room-play.mjs` plays the preset on the box, and these are the facts it measures:

- **Arrival — the game's OWN return spawn, not the door tile** (T2b U2b). The Seedling room is the start region, so Menu → GameStart lands the player inside the game. `GameStart` names no door and Menu is no neighbour, so the first bound door stands in: `new Game(0, 160, 288)`, one tile below `house_door`. Before T2b an arrival landed ON the door's own tile (`entrance_spawn`, the atlas's `entrance_tile`). The game does not draw the player on the house door's tile (measured: no sprite at (160,272), a visible one on the stairs and one step off), and vanilla never lands there. Leaving the house puts the player at (160,288), and coming up the owl's-nest stairs at (256,256), each the `playerx/playery` of the destination level's link back. `seedlingReturnSpawns.returnSpawnTable(mapDoc)` indexes that spawn per door. It takes the nearest reverse link within 2 tiles: over the 280 links, 265 have one within 1 tile, 6 within 2, and 8 are one-way. The panel fetches the map document the preset names (`region_atlas.map_document`) and hands the table to the binding. A door with no entry, or a table not yet in, lands on the door tile as before. Off the door, the game's `check()` latch is clear, so walking straight back in fires it.
- **Departure, fired by the game.** Walking back onto a bound door makes the game's own Teleporter write `pendingExit` (`<seq>|0|teleporter|160|272|86`). Its pixels over `tile_size` fall in the door's `exit_tiles`, and the tile arm publishes ONE `user:regionMove` to the maze neighbour. The game still swaps into the door's real destination (level 86 for the house, 2 for the stairs), and that report is swallowed. The flash panel parks, and the Maze Room tab comes forward by itself. The maze panel takes the keyboard once it is displayed ([Maze Substrate § Panel and runtime](./maze.md#panel-and-runtime)), and it puts the player ON its exit back to the room (below).
- **Return.** The spiral links no reverse exits, so the maze gets the room's own `exitName` and `source_region`. Its `source_region` arm (T2b F1) lands the player ON the maze exit leading back to the room: `region_0_1` `exit_0` (6,0), `region_1_0` `exit_1` (0,4). Before F1 it landed on the maze's `entrance`, and `region_1_0`'s entrance is a six-tile pocket whose only way out is `exit_0`, so the walk back took a trip through `region_1_1`. That pocket still exists; it touches the rest of the region only at `exit_0`'s tile. Entering the room, procgenPlayer hands over `source_region`, and the binding's third arm picks the door that leads to it: from `region_0_1` the house door, from `region_1_0` the owl's-nest stairs. The arrival is that door's return spawn. The second door is the proof, because the first is also the no-match fallback.
- **The panel comes forward and the game has the keyboard** (T2b U1, U2a). A `flashSeedling:loadRegion` publishes `ui:activatePanel` for the flash panel, as every other substrate panel's load does, unless loops' `isFocusLocked` pins another panel. The wasm game hears keys only while the page's focus is on its CANVAS. Focusing the iframe element alone lands the frame's focus on its BODY and leaves the game deaf (measured). So `FlashPanelUI.focusGame()` focuses the canvas inside the frame from the host. It retries briefly while the tab is still hidden. It runs when the bridge comes up after ▶ Start, on the container's `show` (the overlay's *Open the … panel* button, a tab click, the automatic activation), on a region-load activation, and when the AP loading overlay lets go. That overlay's `release()` used to focus the iframe element, which is why keys were dead ~1.75 s after ▶ Start.
- **A key held across a door is released into the game** (T2b F3). A door fired mid-hold brings the maze tab forward, and the key's `keyup` lands on the host page or on the frame's BODY, never on the canvas. The game keeps the key down, and the player walked on after the return with no key pressed. `gameInput.createHeldKeyRelease` tracks the keys the game heard go down. It dispatches a `keyup` with the key's own `key`/`code`/`keyCode` on the canvas when the canvas or the frame window blurs, when a `keyup` reaches the frame but not the canvas, and when the glue parks (`releaseHeldKeys`). The game has no blur callback and no bot release verb; a synthetic `keyup` on the canvas is what it honours (measured).
- **The level's other doors.** A placed sub-region is part of a level. `hut_door` and `gundernourd_stairs` are not bound; if the game changes level through one, the `level` arm warns and moves nothing. (The gate reaches `hut_door`'s level by a jump, because a breakablerock that needs a sword blocks the door itself.)
- **No AP level set.** The panel says `ap placement: not applicable — placement: 0 of 41 goal-ledger locations resolve against the loaded placement`. The room plays the vanilla level set with its vanilla pickups.
- A placed room's exits carry the engine's `isTeleporter`, as every stitched maze exit does. Without it, the APWorld editor's `move-exit-side` wrote `true` on the way out and `false` on the way back, and the room did not round-trip.

### As a sphere-growth leaf

SEEDLING IN THE PIPELINE T3 (2026-09-23) gave the entry the sphere zone realiser, so sphere growth can grow a world around a real room ([Sphere Growth § Seedling as a leaf](./sphere-growth.md#seedling-as-a-leaf-flash_seedling) says why it is always a leaf).

- **The hooks.** `generateZoneForSpecs(zoneSpecs)` takes exactly one exit side (the back door; more is refused, with the sentence naming the leaf rule), picks the tightest room no other region of this generation holds, and binds its door with the SAME binder `extractZoneRules` uses (`bindDoorsToSides`). `exitRules` is empty: the back door's logic is the parent's forward gate, which `buildRulesJson`'s bidirectional pass copies onto it. `canHostExitGates: () => false`, `backPortalGated: () => false`, and `prepareSphereGrowth` clears the placed rooms once per generation. No `victoryItem`: a Seedling leaf holds no goal, and the scenario pool names the victory item.
- **Locations keep the compiler's names.** The node's items go onto the room's own marked locations, in order, under their compiled names (`Starting House - Chest`), through a `global_name` the engine's zone path now passes on. Only `starting_house` has one, so a 1-item leaf lands there and a 2-item leaf is refused; a 0-item filler takes a room with no location.
- **The door is paired.** Sphere growth links reverse exits: the back exit's `exitName` is the parent's region id and its `targetExitId` is the parent's forward exit (`insertBackExit`), and the parent's exit points back at it. So an arrival from the maze reaches the binding with `arrivedFrom.exit_id` = the door's `exitName` — the **second** arrival arm — and a departure reaches the maze with the forward exit's own id, its **first** arm (`resolveMazeArrival`'s `exit_id`). Neither `source_region` arm is needed.
- **The world.** `seedling_sphere_room` (`frontend/?game=seedling_sphere_room&seed=1`, from `SEEDLING_SPHERE_ROOM_STATE` via `make-seedling-spiral-room-preset.mjs --state=sphere`; the panel's *Seedling room as a sphere leaf*): three maze rooms and `dungeon1_room1/r0c4` (level 3) behind `region_2_2`'s `exit_1`, gated on `key_blue`, which lies in `region_2_2`. `check-seedling-sphere-room-play.mjs` plays it on the box: without the key the maze stops the player beside the exit; with it the keys cross, the Flash Game tab comes forward, ▶ Start, and the arrival is `new Game(3, 64, 16)` — the return spawn one tile below `stairs_up`. ArrowUp fires the stairs (`pendingExit …|3|teleporter|64|0|2`), and the maze lands the player ON `exit_1`.
- **Top-down does not place these rooms.** Its zone path reaches the same realiser and is refused by name: a top-down region asks for every exit the source world gave it, and a room is a leaf. It also never calls `prepareSphereGrowth` (measured at T3, not fixed).

### As the APWorld Editor's atlas-room source

APWORLD SUBSTRATE CHANGE R5c (2026-09-24) gave the entry the zone read-back pair the hub's `replace-region-content` rides (`zoneConfigFromSlot` + `zoneOfPayload` in `substrate-registry.md` § *Build-time — content sources*; the hub side is `docs/json/modules/apworldEditor.md` § *The atlas-room source*). A region of a document can then take another real room of the atlas the document's rooms were placed from, in the hub, without a pipeline run.

- **Which atlas.** A rules.json names its atlas only by id: `region_atlas.atlas_id`, which every placed room's `atlas_ref` repeats. `region_atlas.map_document` is the LEVEL map (`seedling-map.json`, 116 levels), not an atlas. `zoneConfigFromSlot` reads the id; the bundled starter atlas (`atlases/seedling.json`) needs no fetch, and any other is resolved through the served index `atlases/atlas_files.json` (`mapDocumentPath.atlasPathInIndex`) and FETCHED — in the generation worker, and by the hub's picker for the room names. The page never installs; the worker installs the fetched atlas through `applyPipelineConfig({atlasDoc})`. The index is derived from the directory (`atlasIndex.test.js` pins it; a restamped atlas reds that row).
- **Which room.** `zoneOfPayload(payload, cfg)` matches `atlas_region` + `atlas_sub_region` in the atlas's placeable rooms. The picker lists those rooms by AP name (`zoneNames`), a room another region plays disabled and named, and the doorless rooms disabled with the channel's reason (*"no wired door — a placed room is entered through a door, and a room with none has no arrival spawn"*).
- **The doors.** The hub hands the channel the region's own exit sides in document order, so the k-th door binds to the k-th existing exit, and `serializeWorld` joins the bound doors onto the region's unchanged exits (their `exitName`, target and `target_substrate`). A room with fewer doors than the region has exits is refused in the channel's own sentence; a surplus door is pruned with its note.
- **What reproduces.** The two content-source documents (`seedling_spiral_room`, `seedling_sphere_room`) take their own room back byte-identically. The atlas COMPILER's projections (`seedling_atlas`, `seedling_playthrough`) are refused by name: their exits are the level's own transitions, not doors bound to sides, so the content source never made them and cannot rebuild them.

## Generated rooms (`flash_seedling_gen`)

SEEDLING GENERATED LEVELS G1 (2026-09-23) added a second Seedling entry, `flash_seedling_gen` (`flashPanel/flashSeedlingGenLibrary.js`). `flash_seedling` places a real room of the installed atlas. `flash_seedling_gen` asks the Seedling generator for a new room, built to the pipeline's spec: its size, one door per exit the driver asks for, and the AP locations it must hold. G1 built the rooms into sidecars. G2 assembles the level set from them at play and delivers it to the game (§ *Delivery and play*, below).

- **Two entries, not one entry with two modes.** The engine picks a realiser by hook precedence. `generateRegionCore` shadows `generateZoneForSpecs` in `generateRegionGen` and in the sphere realise, so one entry with both hooks would stop placing real rooms. The two entries share the flash panel, the `flashSeedling:loadRegion` event (imported, so there is one spelling) and the `flash_panel` block. The glue treats both ids as its own (`SeedlingRegionGlue.substrateIds`).
- **Procedural, in the text adventure's SIDES shape.** The entry has `generateRegionCore`, `placeFromItems`, `placeFromRules`, `extractPathsAndObstacles`, `serializeWorld` and `deserializeWorld`, with `regionGeometry: 'sides'` and `SIDE_AGNOSTIC_EXIT_SIDES`. It serves the spiral, sphere growth, top-down and grid growth through one contract. There is no four-side limit: a top-down region with seven exits gets a seven-door room. The room is a LEAF (T3's law): `canHostExitGates` and `backPortalGated` both answer false, because a generated door cannot enforce an AP gate yet.
- **The entry is light; the generator is installed.** The five build hooks need `procgenSeedling.js` synchronously. A static import from `flashPanel/index.js` would add 94 files (4.96 MB) to the panel's static closure. So the entry delegates its build hooks to `seedlingDemo/seedlingGenRoom.js` through `installSeedlingGenRoom`. Headless callers import `flashPanel/flashSeedlingGenBuild.js`, which `REGISTRY_LIBRARIES` and the regenerate worker's list name. The live app loads the room module through a computed specifier at `register()`, so the bundle does not change. A build hook called before either has run is refused by name. The play-time half (`deserializeWorld`, the payload's refusal, the knob defaults) is `seedlingGenRoomPayload.js`, which imports nothing heavy.
- **The sidecar carries the room.** The payload is `{gameId: 'seedling', generated: true, seed, size, record, start, goal_cell, generation, locations, level, tile_size: 16, exits, exitGates}`. `record` is the generator's core record for `seed`, byte-equal to what `export-seedling-level-set.mjs --exits=none` writes at that seed and knobs. It carries no door entity and no `apitem`: G2's assembler adds both from `exits` and `locations`. The seed is drawn from the engine's rng (`(rng.next() * 0x7fffffff | 0) || 1`, since Seedling refuses seed 0). The knobs (biome, obstacle target, tries per step, skeleton, elements, areas, fill) ride `generation`, and the per-region form reads them back (`procgenParamsFromPayload`).
- **The relabel law.** A Seedling door has no side. Doors are minted by the linker's own rule, `levelSetExits.pickDoorCells`: one flood from the start with every solid live, farthest first, never next to another door, never on the start. The k-th exit asked for takes the k-th door. G2 added two rules for generated rooms only (`pickDoorCells`' opt-in `keepReachable`; the linker's own sets do not move). First, no door may SEAL an approach: with every door cell a wall, the start must still reach every door's approach cell and the goal. G1's spiral room had door 0's approach in a one-cell pocket between two doors. Second, no door, approach or location may stand on water, lava or a pit (`seedlingGenRoom.hazardCells`), because those cells are not solid but kill or respawn the player. The goal is also re-certified by the generator's own solver with the doors as walls. A room that cannot meet these is RE-ROLLED: the next seed is a fixed hash of the drawn seed and the attempt (`rerollSeed`, up to `GEN_ROOM_DOOR_REROLLS` = 8), so no engine rng is used and a room that fits on its first draw does not change. `seed` is the seed used, and `generation.rerolls` records the count. After 8 re-rolls the room is refused, saying it cannot seat its doors "without sealing an approach". An exit the engine adds after the core ran cannot be re-rolled, because the room is fixed by then; it is refused instead. The payload's `exit_id` is the door, spelled `out_teleporter_<px>_<py>` (the atlas derivation's spelling, so the binding's departure arm matches it). `exitName` is the AP exit name, the key the engine's exit Map uses. An exit the engine adds after the core ran (sphere growth's back exit to the parent) gets its door at serialize time, from the same picker, away from the doors already bound and the location cells.
- **The approach-cell law.** `entrance_spawn` is the door's approach cell, in pixels: the flood cell the door was reached from. It is never the door tile. A door the player lands on does not fire until they step off it (the `check()` latch), and the game does not draw the player on a teleporter tile.
- **Locations.** The first AP location stands on the generator's goal cell (its `torchpickup`, the one reach the generator certifies). The rest stand on the cells nearest the start that the player reaches SAFELY (no hazard, no door crossed on the way), never on the start, a door, or a door's neighbour. Each location's `tag` comes from `procgenSeedling.placementTagId`, allocated against the room without its goal pickup. A room that cannot seat its locations is refused by name, with a sentence listing the free cells and saying to lower `maxItemsPerRegion` or the quota. A room that cannot seat its doors is refused with a sentence saying to raise the region size.
- **The ordinal.** `level` is the room's level in the set assembled at play: its index among the world's `flash_seedling_gen` regions, in sidecar order. `buildPresetSidecars` hands every serializer `ordinalOfRegion` beside `substrateOfRegion` (its 5th argument); G2 verifies the value at assembly.
- **The top-level blocks.** `rulesJsonBlocks()` answers `flash_panel` only, read off the installed atlas's compile (`seedlingFlashPanelBlock()`), never retyped. A generated world has no map, so there is no `region_atlas`. A world with both Seedling entries would ask for `flash_panel` twice, and `buildRulesJson` refuses that by name. Mixed worlds are out of scope until the replan.
- **Not declared.** No `regionRoundTrip`: the APWorld hub reports the editor round trip as not checked. `generationCost` stays `light` (a room costs 0.3–1.5 s).

The headless rows are `flashPanel/flashSeedlingGen.test.js` (the room and the entry), `flashPanel/seedlingGeneratedWorld.test.js` (the four drivers) and `seedlingDemo/seedlingGenRoomDoors.test.js` (the door law). The two world states are `SEEDLING_GENERATED_ROOM_STATE` (spiral: two maze rooms and two generated rooms, 10x10) and `SEEDLING_GENERATED_LEAF_STATE` (sphere: a 1-item generated leaf behind a maze gate), in `procgenPipeline/presetDefs.js`. The spiral state is the committed dev preset `seedling_generated_room` (`make-seedling-spiral-room-preset.mjs --state=generated`).

### Delivery and play (G2)

The level set of a generated world is not stored anywhere. It is a pure function of the rules.json, rebuilt each time the game starts.

- **The fifth fact.** The Seedling randomizer decides from data whether it applies (§ *AP's item placement*). A fifth check, `generated`, sits between the build's `apitem` capability and the vanilla placement. It reads `seedlingGenRoomPayload.generatedRoomCensus(rules)`: which sidecars are generated rooms, and which are real rooms of the same game. Unlike the other four checks it can DIVERT. If the world has generated rooms, the verdict is decided there: eligible, on the `generated` arm, and the vanilla-only checks are reported as skipped. A world with both kinds of room is refused by name, because the game mounts one level set at a time. A world with no generated room passes the check, and the vanilla checks decide as before.
- **The assembler.** `seedlingDemo/seedlingGeneratedSet.js`'s `assembleGeneratedSeedlingSet(rules, {locationItemOf, selfPlayer})` is pure: no DOM, engine or generator. Rooms are the generated sidecars in sidecar order, room i being level i, and each sidecar's `level` must say so. Every door becomes a teleporter on its tile. A door to another generated room leads to that room's level and arrives on the PAIRED door's approach cell (the target's door back to this room; a one-way pairing is refused). A door to any other substrate leads to the PARKING room. Every location becomes an `apitem` on its cell, replacing the goal pickup under location 0. No door shows a region sign (none are declared). The set is built with `buildLevelSet(…, {link: false})`, validated (an error refuses; the parking room's one-way warning is reported), stamped `seedling-gen-<seed>-<content hash>`, and given its `apMappingInvalidation`. The table the check binding reads is keyed `placementKey(level, tag)`.
- **The parking room.** Level N, after the generated rooms: a walled 3×3 room with one floor cell and no exit. When the player takes a door out to the maze, the game swaps into the parking room, and that swap is swallowed like any external door's (`pendingDeparture`). The game waits there while the maze plays, and nothing in the world's own rooms is entered by accident.
- **The load.** `flashPanelUI._startSeedlingRandomizer` computes the census from the raw rules and picks the arm. The generated arm is `seedlingRandomizerWiring.loadSeedlingGenerated`: no map or vanilla record set is fetched, and the assembler comes in through a computed specifier (`AP_GENERATED_MODULE_PATHS`, so the bundle does not change). It returns the vanilla load's shape, so `runSeedlingRandomizerLoad` runs unchanged: overlay, deliver, reset to the set's explicit start, then bind.
- **What a person sees** (`?game=seedling_generated_room&seed=1`, Flash Game ▶ Start). The panel log says "ap placement: the GENERATED arm". The player appears on the start room's first door's approach cell. There are two landings on that cell: the region glue's arrival, then the load's reset. The AP item is drawn with the `ap` logo, and walking onto it logs "found key_blue for you" and sends the check. A portal to the maze parks the game and brings the Maze Room tab forward with the keyboard. Walking the maze back lands the player on that door's approach, standing still. A portal to the other generated room is the game's own swap, which lands on the paired door's approach. The host then moves the AP region and re-lands the player on the same cell.
- **One binding change.** Mounting a delivered set makes the game report `level -1`, its "no game" value, between the arrival and the reset. The binding now ignores negative levels, which before this read as two undeclared crossings and warned twice.

The box gate is `scripts/procgen/check-seedling-generated-room-play.mjs` (arms A–F: the delivery, the boot, the check, the maze door, the way back, room to room). Its node rows are `seedlingDemo/seedlingGeneratedSet.test.js` (the assembler) and `flashPanel/seedlingGeneratedArm.test.js` (the fifth fact and the arm).
