### Module: `Client`

-   **ID:** `client`
-   **Purpose:** Manages the WebSocket connection to the Archipelago server, processes incoming messages, sends client commands, and provides the primary UI for server interaction.

---

#### Key Files

-   `frontend/modules/client/index.js`: Module entry point, registration, and dispatcher handler setup.
-   `frontend/modules/client/ui/mainContentUI.js`: The UI class for the main console and connection panel.
-   `frontend/modules/client/core/apClient.js`: Handles the low-level WebSocket connection, including connection, disconnection, and reconnection logic (it replaced the former `connection.js`).
-   `frontend/modules/client/core/messageHandler.js`: Processes all incoming messages from the server (e.g., `Connected`, `ReceivedItems`, `PrintJSON`) and updates the application state accordingly.
-   `frontend/modules/client/utils/idMapping.js`: Provides utility functions to map server-side numeric IDs for items and locations to their human-readable names using the data package.

#### Responsibilities

-   Establishes and maintains a WebSocket connection to an Archipelago server.
-   Handles the authentication handshake (`Connect` command).
-   Requests and processes the room's `DataPackage` for ID-to-name mappings. `GetDataPackage` names the room's games plus `Archipelago` (`dataPackageRequestFor`): an upstream 0.6.8+ server answers only the games named, and a bare request gets nothing.
-   On connect, scouts every one of the slot's locations (`LocationScouts` with `create_as_hint: 0`, so no hints are created) and records what the server says each one holds.
-   Listens for and processes all incoming server messages.
-   Updates the `StateManager` (via commands to its proxy) with state changes received from the server, such as received items or locations checked by other players.
-   Sends commands to the server, such as location checks (`LocationChecks`), chat messages (`Say`), and status updates.
-   Provides the main UI panel for server connection, console output, and command input.
-   Acts as a primary "host" for the `Timer` module's UI, providing a placeholder for the progress bar and control buttons.

#### Which rules a room uses

For a game whose rules can be built from server data (Metamath, DepGraph, APCalc), the client builds them after login. For any other game the order is (`client/core/messageHandler.js`):

1. **The exact-seed preset**: a committed preset made from this room's seed, loaded as it is.
2. **The rules the server sends.** A world built by world_generator sends its own rules document in slot_data (`worldgen_rules`, an envelope `{format, player, doc}`; `world_generator/README.md`). The client checks it against the room (game, location and item IDs) and lays the server's placements and slot_data over it (`client/core/localRulesOverlay.js`). Two hand-written worlds send one the same way: Baking Adventure and Coding Adventure ship `worlds/<w>/_embedded_rules.json`, their seed-1 export with every placement stripped, and `fill_slot_data` sends it as `worldgen_rules` (sdc-embed-handwritten-rules, 2026-11-15). So a room of either plays with no preset file, on plain upstream Archipelago too. The document is generator output: `scripts/test/check-handwritten-embedded-rules.py` rebuilds it from the world's Python (`--write` to refresh it, then repack the apworld) and fails on a stale one; on push it runs as `test/test_handwritten_embedded_rules.py`. Such a document has no `use_canonical_options`, so it is not a generated world's: its goal is reported through its `reports_goal_by_server_item` key, as with its preset. For worlds whose code we can't edit (upstream games), the host can install the **Upstream Rules Add-on** (`apworlds/upstream_rules_addon.apworld`, source `worlds/upstream_rules_addon/`; [host guide](../../features/upstream-rules-addon.md)). It wraps `AutoWorld.call_all`: after `pre_output` it exports every slot once with its vendored copy of the exporter, strips placements, `itempool_counts` and, at the host's `strip_level: play` (the default; `editor` keeps them), the fields the client never needs to play (`_unused_fields.py`), and after `modify_multidata` it writes each slot's `worldgen_rules` (with `source: "upstream_rules_addon"`) or `worldgen_rules_omitted` (`over_cap`, `export_degraded`, `export_failed`). It leaves alone a slot whose world already sends either key. Its documents come in through this same route; it never adds `reports_goal_by_server_item`, so `goalMet` stays off for them; their goal is reported when the goal location is checked instead (`core/upstreamGoal.js`, see *The goal report* below).
3. **A local document** of a generated world: the loaded rules or a committed preset of the game at another seed, overlaid the same way.
4. **Wait.** With none of these, the client stays logged in but holds the Connected and runtime-state packets (no checks are sent), prints what it needs, publishes `client:rulesNeeded`, and continues once a document of that game loads.

A hand-written world's committed preset is only its own seed's room, so presets at other seeds are not used for it: the room goes to steps 2 and 4, and the console warns that this room needs its own preset file, naming its seed. The rules already loaded are never kept for a slot they don't fit (another game's, such as the boot preset, or another player's); when they are the game's own at another seed, a warning names both seeds. Loading a document of the game during the wait is the player's choice: it is used as it is, with the seed-mismatch warning. Loaded rules that DO fit the slot (the slot's name, the room's game) connect as they are at any seed, with that warning.

Because slot_data only arrives with `Connected`, a game with no exact-seed preset and no builder always connects first and decides after login. A server document is refused by name and the client falls back to a local document when its `format` is not the client's `WORLDGEN_RULES_FORMAT` (an older or newer generator), when it carries a retired rules.json shape, when it fails the ID check, or when it fails to load. A world whose document was not sent carries `worldgen_rules_omitted` instead, and the console prints one line for it (`localRulesOverlay.omittedRulesMessage`) that reads the note's `reason` and never assumes its sizes. A world_generator package's note (no `source`; reason `over_cap`) names the slot's `rules_in_slot_data_max_kb` option. A note from the host's [Upstream Rules Add-on](../../features/upstream-rules-addon.md) (`source: "upstream_rules_addon"`) names the add-on: `over_cap` with its host.yaml `max_kb`, `export_degraded` with the count of unanalysed rules or "fell back to an older rule format", `export_failed` with the error (one line, cut to 160 characters). An unknown reason is quoted as is. Every one then goes on as with no server document (a local document, else step 4). A document the add-on sent (`source` on the envelope) says so in the one "Loaded the server-sent `<game>` rules" line. When the slot's world sent neither a document nor a note, the step-4 message adds that a host can send them by installing the Upstream Rules Addon (never for APCalc, which the add-on skips).

#### The server's item groups

On the builder, server-document and local-overlay paths (everything that builds the slot's rules after login), the client also asks for the slot's game's item groups: a `Get` of the read-only data storage key `_read_item_name_groups_<game>` (`client/core/serverItemGroups.js`). The build waits for that answer as well as for the scouts, and then applies the groups to the document before the one load. `item_groups[slot]` becomes the server's group names, and each of the game's own items gets the groups the server lists it in. An event item and another game's item placed at the slot keep the document's groups, because the server has no group for them. When the document's groups differ from the server's, the server's are used, and one console line names the difference. When the key is missing (null, from an old server) or no answer comes within `GROUPS_TIMEOUT_MS` (10 s), the document's own groups are kept, and one console line says so. An exact-seed preset loads before `Connect`, so its groups are used as they are. Static data is never patched after load. Location groups (`_read_location_name_groups_<game>`) are not fetched: rules.json has no field for them, and nothing reads them. The console's `item_groups` command lists the loaded player's groups with their item counts.

#### The room's spoiler data

A world that uses the Spoiler Export Hook (`worlds/spoiler_export_hook/`, option `spoiler_data_in_slot_data`) sends its slot's sphere order in slot_data as `spoiler_data`: format 1, `steps` of `[walk label, own location or null, item received or null]`, plus `[sender player, sender location]` as a 4th element with `own_slot_with_senders`, and, with the world's `spoiler_data_include_regions`, `regions: {start, steps: [[row index, [region names]]]}` (the regions first reachable at the start and after that row). Each value is the AP id where the DataPackage gives that exact name back, otherwise the name. On `Connected`, `client/core/spoilerData.js` expands it with the DataPackage into an incremental sphere log and publishes it as `client:roomSpoilerData`. The expanded lines are those of the exporter's per-player sphere log (`json_tools.sphere_log_per_player`) for the same seed: a sender appears as the sending world's own entry on that line (`player_data[sender]`, empty deltas, `sphere_locations: [its location]`), and regions fill `new_accessible_regions`; `client/core/spoilerData.logFormat.test.js` compares the two line for line. Readers that look only at the current player's entry (sphereState, the cost planner, JTA balance and cost generator) ignore the senders' entries. **A file for the room's seed beats the room:** an exact-seed preset's `.jsonl` (or an embedded log) is kept, and replaces the room's log if it finishes loading later; a file for another seed loses to the room (the rule is in [sphereState](./sphereState.md)). The room's log fills the gap on the server-document, local-overlay and builder paths, which have no file log. `spoiler_data_omitted` gives one console line saying why (for example, the generator had no Spoiler Export Hook); with neither key nothing is said. A format the client does not read (`SPOILER_DATA_FORMATS`), another slot's record, or a game missing from the DataPackage gives a warning and no log. The overlay never copies `spoiler_data` or `spoiler_data_omitted` into the world's slot_data (`slotDataWithoutRules`). Fixtures: `client/core/fixtures/spoilerData/make_fixtures.py` regenerates them from the real helper. How a world sends the record: [Spoiler Export Hook developer notes](../guides/spoiler-export-hook.md).

The overlay also writes the room's item into each procgen pickup's sidecar entry (`playable_payload.items[].id`, and `locations[].item` for the Seedling generated rooms). A maze draws and collects a pickup only when its id is set, and a server-sent document carries none.

#### Events Published

While most of its actions result in calls to the `StateManager` (which then publishes state changes), the `Client` module's core components publish key network status events on the `eventBus`:

-   `game:connected`: Published when the connection and authentication handshake is successfully completed. ⚠ It comes BEFORE the `Connected` packet's state reset (`applyRuntimeStateData`), so anything re-applied on it is wiped by that reset.
-   `client:connectedStateApplied`: Published on every `Connected` (a reconnect is a second one) right after its state reset was handed to the state manager. The payload is `{ slot, team }`. The state manager's worker runs its commands in order, so a check sent on this event lands after the reset. The Seedling glue re-derives its game-state events on it (see below).
-   `game:roomInfo`: Published when server room information is received.
-   `game:locationsScouted`: Published when the server answers the connect-time scout. The payload is `{ locations }`, one entry per location: `{ locationId, locationName, itemId, itemName, player, playerName, game, flags, progression, useful, trap }`. `player`, `playerName` and `game` describe the slot that receives the item. `itemName` comes from that slot's game in the DataPackage, and is `null` if the DataPackage doesn't have it.
-   `network:connectionRefused`: Published when the server refuses the connection attempt.
-   `client:locationCheckRefused`: Published when the connected logic gate refuses a check (see `user:locationCheck` below). The payload is `{ locationName, reason, originator }`. The Locations panel clears the card's pending state on it. The Playback Bot parks a check it was waiting on (a connected check counts when the server's echo marks it, not at the send).
-   `client:roomSpoilerData`: Published on `Connected` when the room's slot_data carries a `spoiler_data` record this client reads. The payload is `{ source, text, entries }`: `source` is `room:<seed>:P<slot>`, `text` the expanded incremental sphere log (JSONL). `sphereState` subscribes.

#### Events Subscribed To

-   **`eventDispatcher`**:
    -   `user:locationCheck`: Acts as the highest-priority handler for location check requests when connected to a server. It gets the server ID for the location and sends the check command. If not connected, it propagates the event for local handling.
        -   **The logic gate** (`core/checkGate.js`). Connected, a `user:locationCheck` is refused when the state manager's snapshot says the location is not reachable, the same answer its offline guard gives. Nothing is sent, the event is not passed on, `client:locationCheckRefused` `{ locationName, reason, originator }` is published (`reason` is `not_accessible`, or `reachability_unknown` when there is no answer: the gate fails closed), and the console shows a warning. **Exempt:** a pickup the game itself reported, whose payload carries `reportedByGame: true` (the substrate bridges, the Seedling glue, the Flash adapter, the text adventure's examine, apcalc, vibeCodingSim, jtaArchipelago), and every `system:locationCheck`. A new game publisher must set the flag, or its out-of-logic pickups are refused while connected. `originalDOMEvent` is not read: it cannot tell a click from a game report.
        -   **A location with no server ID** (an event, or a location only this client knows) is applied **locally** while connected, exactly as offline: after the gate, the event is passed up to the state manager, whose own logic guard judges it (a refusal there is `stateManager:locationCheckRejected`, which the Playback Bot also treats as a refusal). It used to be dropped: the rules' `id: null` read as 0 and the send filter discarded it. The server never echoes such a check, so a resync (ReceivedItems index 0, `/sync`) re-adds its event item once (`rederiveIdlessLocations`) and never twice. It never counts toward the goal: `goalMet` reads only server-delivered items. `sendBatchLocationChecks` (the timer, which has already checked every name locally) splits a mixed batch with `splitLocationChecks`: ID-bearing names are sent, ID-less ones stay local. A reconnect's `Connected` payload replaces the checked set with the server's, so a locally collected event is dropped by that reset (not doubled). The ID checks made while disconnected would be lost by the same reset (and by the connect flow's own rules reload before it); they are captured at `RoomInfo` first and offered to the player (*Offline progress at connect*, below). Events with no `event_kind` are collected again by reachability. Seedling's `game_state` events are re-applied by the region glue on `client:connectedStateApplied` (RE1): the game's flags (`botStatus().persistence_cleared`), together with what the glue collected and what the state manager had checked for the same rules, each through the same forced local check. The state manager dedupes (`already_checked`), so a /sync never doubles one. A world whose fail-closed event kind has no such collector would still lose its events on a reconnect.
        -   **No false alarm.** A `RoomUpdate` that checks a location the frontend logic calls unreachable is force-checked to stay in sync. The `[INACCESSIBLE LOCATION DETECTED]` error (with its sphere-log downloads) is raised only for a genuine mismatch: not for a location this client sent on this connection, and not after the slot's goal (this client's `reportGoal`, or a `Goal`/`Release` PrintJSON for this slot), when the server's release checks the rest.
        -   **The goal report** (`core/goalCheck.js`). The client sends `StatusUpdate` 30 (goal) at most once per connection, and only once the items the SERVER delivered on that connection satisfy the slot's `completion_condition` (never the frontend's own state, which holds auto-collected events). A goal cannot be undone, so `goalMet` says no to anything unclear: a rule that holds with no items, a rule an inventory cannot answer, or a document for another game or slot. It reports only for a world whose goal is an ID-bearing location holding an ID-bearing goal item, so the server delivers that item when the game checks the location. Such a world is admitted in one of two ways: a `world_generator` world by its marker (the `use_canonical_options` option), or a hand-written world that declares it with the `slot_data` key **`reports_goal_by_server_item: true`**, set in its `fill_slot_data`. The key reaches the client both in a preset (`world[p].slot_data`) and in `Connected`'s slot_data (`overlayServerData`). Only a strict `true` counts. APCalc declares it (sdc-goal-apcalc, 2026-11-14): its Victory location is 234810601 and the Victory item is 234810015, and the APCalc panel checks Victory once its own state has visited every node. Baking, Coding and JtA declare it too (sdc-goal-handwritten, 2026-11-15): Cool on Wire Rack 300000016 / Victory 300100016 and Production Deployment 400000062 / Victory 400100052 (the IDs their WorldGen twins already used), and JtA's Reach Goal Zone 590141 / Victory 590056; the player finishes by checking that location (Locations panel). A hand-written world without the key (APQuest ServerData today) never reports: its goal is still an ID-less event. ⛔ Don't reuse `use_canonical_options` as the opt-in, because it also switches the local-rules overlay.
        -   **The add-on's goal** (`core/upstreamGoal.js`, sdc-upstream-goal-report, 2026-11-17). A slot whose rules the server sent from the host's Upstream Rules Add-on (`source: "upstream_rules_addon"`, chosen and loaded on this connection) has an event goal the server can never deliver, and we can't change its Python. So for these slots only, the client decides, narrowly; a missed report is acceptable, a false one is not.
            -   **Derivation, before the rules load** (`_prepareUpstreamGoal`): `completion_condition` must name exactly ONE item of this slot that sits only at ID-less locations, at exactly ONE location, and the rule must be decidable on it (false without it, with every other named item; true with it). No game names. That location gets `event_kind: 'goal'` on the client's own overlay copy, which the state manager never auto-collects (`stateManager/core/eventKinds.js`), so it shows as an ordinary location to click. Otherwise nothing changes and one console line says the game's own client reports the goal. Census over the committed presets: 61 upstream-shaped slots derive one; `state_method` goals (SC2 `can_reach_location`, ChecksFinder `has_all_counts`, SM64 `can_reach`) don't, and 0 have several goal events.
            -   **The report** (`_noteUpstreamGoalCheck` / `_reportUpstreamGoalIfMet`; ⚖ Robert 2026-11-17: no send restrictions this mode doesn't have elsewhere). A check of the goal location takes the ordinary path, whoever sends it: a Locations card, a Region Graph node or its bulk check, the Timer, a bot, the Loop queue, a game report. The landed out-of-logic gate applies as for every location. The goal is reported when THIS connection saw the location go from unchecked to checked (the ID-less branch of `handleUserLocationCheckForClient`, and the Timer's `sendBatchLocationChecks`, whose batch the timer has already checked locally) and the rule is false over the server-delivered items (`_serverItems`) and true with the goal item added. If the items aren't there yet, the console says so and the `ReceivedItems` that completes them reports (`_reportGoalIfMet`). Then `reportGoal()` (once per connection). A goal already checked before the check (e.g. offline on a kept document), or checked on an earlier connection (`_connectionSeq`), never reports. The Timer checks the goal like a location: `eventKinds.playerChecksEvent` (`playerCheckable: true` on the `goal` row) keeps it out of the timer's event skip. The record `{goal, doc, slot, seedName}` counts only while its document is the loaded one (identity), for that room seed and slot (`_upstreamGoalFor`); otherwise the check is an ordinary ID-less one, which never reports. A same-seed reconnect keeps the loaded rules and so the record (measured live: the client doesn't rebuild then). A reconnect or `/sync` sends nothing on its own: offline progress (the goal included) reaches the server only when the player answers **Send** to the offer at connect (see *Offline progress at connect* below), and then through this same path.
            -   **An exact-seed preset** (`_loadPresetRules` → `_preparePresetGoal`, sdc-preset-goal-report, 2026-11-19). When the connect flow loads the committed preset made from this room's own seed (`_findPresetForRoom`; a multiworld `_P<n>` file counts, with the slot = that preset's player), the same derivation runs on that fetch's own object before it loads, and the same record, report and negatives follow. The document's `seed_name` must equal the room's. Rules ALREADY loaded at the room's exact seed (the Presets panel, the boot preset, any file: ⚖ Robert 2026-11-19, any document with the exact seed) take `_connectWithLoadedRules`: a `structuredClone` is marked and loaded (same source and player) before Connect, since the loaded document is unmarked and its goal may already be auto-collected; Connected replaces the checked locations and inventory anyway, so the reload loses nothing. A document that already is the record's (a same-seed reconnect) is kept as it is. Our hand-written worlds that report no goal otherwise (APQuest ServerData, TOEM, Rule Builder Test) are included (⚖ Robert 2026-11-19). A world that reports its own goal gets no record (`upstreamGoal.reportsOwnGoal`): a world_generator world or one declaring `reports_goal_by_server_item` (both `goalMet`), or a proof/graph world (`slot_data.proof_structure` / `graph_structure`, whose proof modules publish `user:goalReached`). Rules loaded under a seed mismatch (warning, but allowed), or picked by the player while logged in (`_awaitLocalRules`), get no record. Census over every committed preset folder × player: 111 derive a goal (9 of them multiworld `_P` slots), 72 don't (40 not an event at a location, 17 a rule naming no item, 15 a constant), and 39 are our own reporting worlds.
        -   **Offline progress at connect** (`core/offlineProgress.js`, sdc-offline-progress-op1; ⚖ Robert 2026-11-21, per the offline-progress design).
            -   **The record** (`_captureOfflineProgress`, in `_handleRoomInfo` before `_connectForRoom`): the loaded document's identity (`seed_name`, player, game, player name) and the ID-bearing locations the state manager has checked, in check order, plus the document's goal location (`deriveUpstreamGoal`: an unmarked document auto-collects it offline). Events are not kept: they re-derive. Pickups the game reported offline (`reportedByGame`, or `system:locationCheck`; recorded by the offline branch of `handleUserLocationCheckForClient`) stay exempt from the gate when pushed, as they are while connected. A seedless document gives no record. A later capture of the same identity is merged into the kept record, never replaces it. Records live in this page session only: a reload loses them, as it loses the offline play itself.
            -   **The offer** (`_offerOfflineProgress`, at the end of every `_handleConnected`, a server build's included): only when the record is this connection's own — the room's seed, the connected slot, that slot's game (`slot_info`), and the same player name when both name one (`matchesRoom`). A mismatched seed, another player's document and a seedless document are never offered. Checks the server already has (`checked_locations`, later `RoomUpdate`s) are skipped; a name this room has no location for is dropped with one console line (the server would ignore it silently). The player is asked with `client:offlineProgressOffer` `{ key, count, goal, message }` (the Console & Status panel's inline bar, and the same text in the console): **Send** / **Not now** / **Discard** (`respondToOfflineProgress('send'|'later'|'discard')`; `client:offlineProgressOfferClosed` `{ choice }`). When the goal is in the set (`goalInPending`: the exact-seed / add-on goal location, or a generated world's completion rule met by the pushed locations' own items), the same offer names it and says it finishes the game and the server may release the remaining items. Not now keeps the record and offers it again at the next connect; Discard deletes it; a rules load the client did not start itself (`_clientRulesSources`, so the connect flow's marked copy, preset and server build don't count) discards every record.
            -   **The push** (`_offlineProgressPass`, one at a time): each pending check that the state manager says is reachable now, or that the game reported, goes through `handleUserLocationCheckForClient` called DIRECTLY with `originator: 'OfflineProgress'` (as `_replayHeldGameChecks` does: through the dispatcher, Loop mode would queue it). The gate there still decides, so a check is never sent out of logic. The goal goes last in a pass and reports through the ordinary goal paths (once). Our own items come back (`items_handling 0b111`), so each `ReceivedItems` (and `RoomUpdate`) runs another pass; checks still out of logic stay kept for this page session and are retried on each delivery. A reconnect mid-push resumes without asking again (the record remembers Send); a check is removed only once the server has it, so one sent but unconfirmed before a drop is sent again (the server dedupes).
    -   `user:itemCheck`: Handles manual item checks by sending a `!getitem` command to the server when connected. If not connected, it propagates the event.
-   **`eventBus`**:
    -   The internal `messageHandler` listens to `connection:open`, `connection:close`, and `connection:message` events from the `connection` object to process server data.

#### Public Functions (`centralRegistry`)

Most interactions go through the `eventDispatcher`. Among the public functions:

-   `getScoutedLocations()`: the entries from the last `game:locationsScouted` on this connection, or `[]` before the server has answered. They are cleared when the connection opens or closes.
-   `connect(serverAddress, playerName)`: connects from a script, as `window.__apSpike.connect(url)` does. Both refuse a connect made before the module's `initialize()`; see below.

#### Connecting from a script

The ApClient publishes the server's RoomInfo on the module's event bus, and `initialize()` is what sets that bus. A connect made earlier would lose RoomInfo, and nothing would then send Connect: the websocket would stay open and logged out, with no message. So `apClient.connect()`, `apClient.requestConnect()` and the registry's `connect` refuse it before opening anything. They print a console error and throw `ClientNotReadyError` (`code: 'AP_CLIENT_NOT_READY'`; `connect()` returns a rejected Promise). Players never reach this: the connect form's listeners attach after `initialize()`, and `?autoConnect=true` connects from `postInitialize`.

A script polls `window.__apSpike.isReady()`, which is synchronous, before it connects. Playwright probes use `waitForClientReady(page)` from `scripts/procgen/clientReady.js`. Do not wait with `page.waitForFunction(async () => …)`: Playwright treats the Promise an async predicate returns as truthy, so that wait resolves at once.

#### Dependencies & Interactions

-   **StateManager**: The `Client` module is a primary driver of state changes. It calls methods like `stateManagerProxySingleton.addItemToInventory()` when `ReceivedItems` packets arrive and `stateManagerProxySingleton.checkLocation()` for server-side location updates. It also reads static data from the `StateManager` to map location names to server IDs.
-   **EventDispatcher**: It is a key participant in the `user:locationCheck` and `user:itemCheck` event chains, acting as the authoritative handler when an online session is active.
-   **Checks line**: `mainContentUI` shows the "Checked: …, Reachable: …" line by mounting `commonUI/checksLine.js` (`mountChecksLine`), which keeps it current from `stateManager:snapshotUpdated`. The timer's controls are in the Playback Bot panel (its "any reachable location" mode).
