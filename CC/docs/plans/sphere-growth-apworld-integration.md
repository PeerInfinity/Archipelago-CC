# Sphere Growth ⇄ APWorld Editor Integration — Research & Direction

**Date:** 2026-06-22
**Status:** Preliminary research (no implementation this session)
**Scope:** Findings + decisions from a research session evaluating how the
sphere-growth procgen pipeline, the top-down procgen mode, and the APWorld
Editor could fit together, plus the design direction for evolving the
sphere-growth model.

This is a **findings-and-direction** document, not an implementation plan. All
file/line references were accurate as of the date above; treat them as
starting points, not guarantees.

---

## 1. Background: the three features involved

| Feature | What it does | Key files |
|---|---|---|
| **Sphere-growth procgen** | Builds a world from scratch: item pool → spheres (progression layers) → topology (tree of regions + gates) → realized geometry → `rules.json`. The current default procgen mode. | `frontend/modules/procgenPipeline/` (`procgenPipelineUI.js`, `sphereSteps.js`, `procgenPipelineEngine.js`, `sphereConfigHooks.js`, `regionEditors.js`) |
| **Top-down procgen** | Realizes an **existing** `rules.json` as playable geometry: places each source region on a grid (BFS layout, teleporter fallback for non-grid arrangements), generates substrate geometry that respects the source access rules. | `procgenPipelineEngine.js:topDownFromRulesJson` (~line 1292); UI `_runTopDown` (~line 3090); mode radio `procgenPipelineUI.js:604` |
| **APWorld Editor** | GUI CRUD over a `rules.json` (regions / exits / locations / items / access rules / metadata) for Player 1. Sphere-agnostic. Publishes `files:jsonLoaded`. | `frontend/modules/apworldEditor/` (`index.js`, `apworldEditorUI.js`, `ruleTreeEditor.js`, `rulesUtils.js`) |

**Shared substrate that makes integration possible:** all three speak the same
`rules.json` shape and all publish/consume the same `files:jsonLoaded` →
`stateManager:rawJsonDataLoaded` event. A world generated by procgen already
flows into the APWorld Editor today (read path), simply by being loaded.

## 2. Sphere-growth ⇄ APWorld Editor integration

### Finding
The two are two halves of one world-authoring loop, not two things to merge.
They already share the `rules.json` format and the `files:jsonLoaded` event, so
a **loose read-path integration already exists**: generate in procgen → "Load
into frontend" → APWorld Editor's `rulesDoc` refreshes → inspect/tweak by hand.

### The conceptual tension
The APWorld Editor is **sphere-agnostic**. Editing procgen output in it flattens
the sphere structure — the `rules.json` still works, but the logical
sphere/wave/gate grouping is not represented in the editor and can be silently
broken by edits. The bridge is the compact `procgen_metadata.sphere_tree`
(Phase 3), which the editor currently neither reads nor preserves.

### Decision / direction
Do **not** fuse the panels. Build a thin, intentional round-trip:

1. **Preserve `procgen_metadata.sphere_tree` through the editor** — smallest,
   most important change. Without it, every save severs the round-trip.
2. **Make Procgen → Editor an explicit handoff** ("Edit in APWorld Editor"),
   since the plumbing already exists.
3. **Add an Editor → Procgen "Grow / Append spheres" action** feeding the
   editor's `rulesDoc` into the existing append / tree-reconstruction path.
4. Later: surface sphere membership in the editor (color-code by sphere) and
   add sphere-aware validation.

Steps 1–3 are mostly wiring on top of capabilities that already shipped in the
recent Phase 3/4 work.

## 3. Top-down mode emitting sphere-growth metadata

**Goal explored:** could a `rules.json` + sphere-log file that did **not** come
from procgen be run through top-down mode to add the missing metadata, so the
result loads in sphere-growth mode or the APWorld Editor?

### Findings

- **Top-down does NOT read sphere logs today.** Its only input is a
  `rules.json` (`topDownFromRulesJson(rulesJson, opts)`). The sphere log
  (`_sphere_log.jsonl`) is an *output* artifact written by the Python exporter
  (`exporter/sphere_logger.py`) for **all** games during spoiler generation —
  nothing in procgen ingests it.

- **Top-down already builds ~80% of a sphere_tree by construction.** Because it
  places every region on a grid cell, assigns a substrate, builds a BFS parent
  graph + back-exits + teleporter table, and (via the shared `buildRulesJson` /
  `buildPresetSidecars` tail) **already emits `preset_sidecars`**. The engine
  comment at `procgenPipelineEngine.js:1166-1168` confirms top-down "produces
  the same `{grid, startCell, stats}` shape so the existing compile/emit tail
  handles the output unchanged."

- **What top-down emits today:** `procgen_metadata` with
  `driver: 'top-down'`, `source_game`, `source_counts`
  (regions/locations/exits/logic_gates), `stop_reason`. It does **not** emit
  `sphere_plan` or `sphere_tree`.

### The narrow gap

| `sphere_tree` field | Available from top-down today? | Source if not |
|---|---|---|
| `index`, `cell`, `substrate` | ✅ Yes (grid placement) | — |
| `parent`, `side`, `isTeleporter` | ✅ Yes (BFS graph + teleporters) | — |
| `preset_sidecars` (per-region payloads) | ✅ Yes (shared `buildPresetSidecars`) | — |
| **`wave`** (sphere number) | ❌ No (geometric BFS, not sphere layering) | sphere log: `new_accessible_regions` per `sphere_index` |
| **`gate` / `gateCounts` / `childGates`** | ⚠️ Partial (access rules exist, not distilled) | sphere-log deltas + access-rule analysis |

So the genuinely new work is narrow: **stamp `wave` + `gate` onto regions
top-down already placed, then emit `sphere_tree` + `sphere_plan`.** This is why
feeding **both** a `rules.json` and a sphere log is the right design — each
supplies a different layer.

### Feasibility by goal

- **Load enriched file in the APWorld Editor** → already works; needs no new
  metadata (the editor is sphere-agnostic; any `rules.json` loads).
- **Load in sphere-growth mode to view / inspect / hand-edit** → feasible,
  medium effort (degrades gracefully — a slightly-wrong gate still renders).
- **Load in sphere-growth mode to append / regrow spheres** → larger effort;
  needs correct-enough topology (see §4 non-tree work) and the gate model.

### Suggested framing
Rather than "make top-down emit sphere metadata," scope it as: **"top-down
optionally ingests a sphere log; uses it to assign `wave` + `gate` to the
regions it already placed; emits `driver: 'sphere-growth'`-compatible
`sphere_tree` + `sphere_plan`."** This reuses the whole existing top-down
geometry/sidecar machinery and confines new code to a wave/gate-attribution
pass plus the tree emitter.

## 4. Non-tree graphs (design direction)

**Goal:** expand sphere-growth to handle graphs that aren't strictly trees.

### Decided model
- A **canonical unlock tree** for the intended progression spine.
- Plus **extra (secondary) edges** that don't interfere with the intended
  unlock order — e.g. shortcuts in earlier spheres that only open once the
  player has later-sphere items.
- Construct the **canonical tree from the sphere-log data**; construct the
  **rest of the edges from the rest of the `rules.json` data**.

### Why this fits the architecture
- The sphere log gives a clean region→wave layering (`new_accessible_regions`
  per `sphere_index`) and a canonical parent/gate signal (item collected just
  before a region unlocks) — i.e. the BFS-parent structure top-down already
  builds, plus wave/gate stamping.
- The remaining `rules.json` exits/access-rules are exactly the edges the spine
  doesn't explain → the secondary edges.

### Objective acceptance test for a secondary edge
**An extra edge is "non-interfering" iff adding it does not change any region's
first-reachable sphere.** Checkable against the sphere log: add the edge,
recompute reachability, confirm no region's unlock sphere decreased. This gives
a precise definition of "shortcut, not a logic change."

### Realization risk — reduced by existing teleporter fallback
The node model moves from "one `parent`/`side`/`gate`" to "one canonical parent
+ a set of secondary incoming edges, each with its own access rule." Since gates
are **not** load-bearing downstream (see §6), this is additive: secondary edges
just compile to additional exits with their own `access_rule`.

The previously-flagged "hard geometry" concern (placing multiple incoming
connections) is **largely mitigated by the existing teleporter fallback**: a
secondary edge is "another exit pointing at the target region; place on a free
side if adjacent, else teleporter." This pushes the feature toward data-model +
edge-acceptance-test work and away from hard grid geometry.

## 5. Per-region "expected items" → region editor (decided, low effort)

**Goal:** track, per region, what items the player can be expected to have when
that region first becomes accessible, and pass it to the region editor.

### Decision
Use the **simplest** definition for now: **items from the spheres *before* the
current sphere** — strict `<`, not `≤`.

Concretely: collect `st.plan.spheres[w].items` for `w < node.wave` →
`contract.expectedItems`.

### Why strict `<` is also the correct boundary
Items placed *in* the current sphere are precisely the ones gated behind
reaching this region (or its wave-peers), so the player shouldn't be assumed to
hold them at first access. Strict `<` also automatically excludes the region's
**own** pickups (they live at `node.wave`).

### Why it's easy
The data is already in scope at edit time. `_buildRegionContract`
(`procgenPipelineUI.js:2176`) already holds `st.plan.spheres` and `node.wave`,
already passes `node` and an (unfiltered) `itemPool` into the editor. This is a
~5-line slice-and-collect. The natural first consumer is the bounce editor's
per-pickup item picker (`bounceRegionEditorUI.js:133`), which currently draws
from the full pool with no filtering.

### Region editor interface (reference)
- Registry: `regionEditors.js` — substrate-keyed; `open({ region, contract,
  onSave? })`.
- Call site: `_editRegion` (`procgenPipelineUI.js:2152`) → `_buildRegionContract`
  → `open(...)`.
- Save path: `_buildEditedRegion` writes back `locationSpecs` (per-pickup
  `{id, item}`) + exit rules, keeps geometry; `_onRegionEdited`
  (`procgenPipelineUI.js:2250`) splices into `st.grow.grid` and invalidates ④.

### Future refinement (not now)
"Could have" (maximal reachable set, including via shortcuts) is the reachability
computation — once sphere-log ingestion exists (§3), it comes essentially for
free. If expected-items becomes first-class (validation, rendering, multiple
consumers), stamp `node.expectedItems` during wiring rather than recomputing per
editor-open.

## 6. The `gate` mechanism — free to redesign

**Question:** is `gate` data used by anything other than the sphere-growth
algorithm?

### Finding: NO. `gate` is 100% internal to sphere-growth generation.

- The **only** downstream effect of a gate is being lowered into an exit's
  `access_rule` via `sphereGateRule()` (`procgenPipelineEngine.js:3618`),
  producing `And(Has(item, count), …)`. After that conversion, the canonical
  `rules.json` carries only `access_rule`.
- `gate` / `gateCounts` / `childGates` appear **only** inside
  `procgen_metadata.sphere_tree` — never in the region/exit schema.
- Every consumer is part of generation itself: `pickHostAndGate` /
  `wireSphereTree` (wiring), `rebuildSphereTopology` (post-edit validation),
  `compactSphereTree` (serialization), `rebuildEnvelopeFromRulesJson` (append
  rehydration), the ②b topology dropdown, and tests.
- **Not** read by: region editors, grid rendering, `world_generator`, the
  Python runtime (only ever evaluates `access_rule`), or the APWorld Editor.

### Implication
Redesigning/replacing gates is a localized procgen-internal refactor.
Constraints:
- Keep `compactSphereTree` ⇄ `rebuildEnvelopeFromRulesJson` (serialize ⇄
  rehydrate) coherent.
- Update tests asserting on `node.gate`.

Because the real contract is `access_rule`, gates can become arbitrarily rich
(or be replaced by "arbitrary access rule per exit/location") without breaking
anything downstream. The gate is just the **authoring abstraction** that gets
lowered to a rule.

## 7. Zones (design direction)

### Intended model
A **zone** is a predefined structure with:
- a set of **pickups** that can later be assigned to any item or disabled;
- **exits** that can later be connected anywhere or disabled;
- **one entrance** marking the start of the zone, which all incoming exits
  connect to (future: **multiple entrances that match the exits**);
- **logic gates** (= arbitrary access rules) on locations and exits.

If a region is registered as a zone, its **predefined structure stays intact
during rerolls and other modifications** — only the item↔pickup assignments,
exit connections, and enable/disable flags change.

### Why it fits existing seams
- The region-editor save contract is **already pickup/exit-oriented**:
  `_buildEditedRegion` writes back `locationSpecs` (`{id, item}`) and exit rules
  while keeping `playable_payload` geometry. "Keep structure, reassign contents"
  *is* the zone concept; zones formalize it as the rule rather than a
  bounce-editor convention.
- "Fixed structure survives reroll" is the cleanest dividing line: a registered
  zone makes reroll a no-op on structure and only re-randomizes assignments.
- This **dissolves the current reconstruction blocker**: zone substrates today
  throw in `rebuildEnvelopeFromRulesJson` ("no path extractor"). A zone doesn't
  need a path extractor because its structure is canonical and stored, not
  reverse-engineered from geometry.

### "Zone behavior for arbitrary regions"
If locations/exits can carry arbitrary `access_rule`s directly (what gates
already lower to — see §6), then "zone" can be a **property** of how a region is
edited/rerolled (structure frozen, contents fluid) rather than a special
numbered type. The numbered-zone registry would be the predefined-structure
*library*; the freeze-on-reroll behavior could apply to any region flagged that
way.

### Substrate fit
- **Bounce**: poor conceptual fit (gameplay leans on movement items) but fine as
  a **test** substrate.
- **JtA**: a much better fit, but not finished yet — the real target.
- Zones work better for substrates that have interesting gameplay without
  requiring late-game items.

### Multi-entrance (future)
Design the entrance-binding interface so the single-entrance case is just
`entrances.length === 1`, to avoid a later migration. Multi-entrance pairs
naturally with §4 secondary edges: a secondary incoming shortcut would bind to
its own matching entrance rather than being forced through the canonical one.

## 8. Suggested next research step

Highest-leverage open measurement: **graph→tree flattening on a real world.**
Run an existing AP preset's `rules.json` through `topDownFromRulesJson` and
count teleporters / multi-entrance regions. That single measurement sizes the
§4 non-tree feature (how many secondary edges a real world actually produces)
and indicates whether the "append/regrow" goal is reachable or whether top-down
enrichment stays view-only for now.

## 9. Decisions log (this session)

- **Expected items** = items from spheres strictly **before** the current
  sphere (`w < node.wave`). Simplest option for now.
- **Non-tree graphs**: canonical tree from sphere log + non-interfering extra
  edges from the rest of `rules.json`; non-interference defined as "doesn't
  change any region's first-reachable sphere."
- **Teleporter fallback already exists** for non-grid arrangements — reuse it
  for secondary-edge realization.
- **Gate** is safe to redesign (internal to sphere-growth only).
- **Zones**: fixed structure survives reroll; only assignments/connections/
  enable-flags change. Single entrance now, multiple entrances (matching exits)
  later. Possibly generalize to a per-region property rather than a numbered
  type.
- **APWorld Editor integration**: keep panels separate; build a thin round-trip
  (preserve `sphere_tree`, explicit handoffs both directions).
