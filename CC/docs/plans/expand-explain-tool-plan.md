# Expand Rule Builder Explain Tool for Generated Worlds

## Overview

This document outlines the plan to expand the Rule Builder's `explain_json()` and `explain_str()` functionality to support more rule types, particularly those generated by the world generator.

Currently, when `cc_format.py` parses AST format rules into Rule Builder objects, many rule types fall through to `True_()`, losing their explain functionality. This plan addresses that gap.

## Problem Statement

### Current State

The Rule Builder (`rule_builder/rules.py`) has explain support for these rule types:

| Rule Type | Class | Explain Support |
|-----------|-------|-----------------|
| `constant` | `True_`, `False_` | Yes |
| `item_check` | `Has` | Yes |
| `count_check` | `Has` | Yes |
| `group_check` | `HasGroup` | Yes |
| `and` | `And` | Yes |
| `or` | `Or` | Yes |
| `can_reach` | `CanReachRegion` | Yes |
| `location_check` | `CanReachLocation` | Yes |
| `can_reach_entrance` | `CanReachEntrance` | Yes |
| `state_method` (some) | Various `Has*` classes | Partial |

### The Gap

Analysis of 145 generated worlds revealed **22,395 rule instances** without explain support:

| Rule Type | Count | Current Behavior |
|-----------|-------|------------------|
| `state_method:count` | 6,974 | Returns `True_()` |
| `region_check` | 2,325 | Returns `True_()` |
| `helper:*` (various) | 3,000+ | Returns `True_()` |
| `compare` / `comparison` | 1,696 | Only prog_items pattern works |
| `state_method:_hk_option` | 757 | Returns `True_()` |
| `sum` | 660 | Returns `True_()` |
| `binary_op` | 572 | Returns `True_()` |
| `conditional` | 459 | Only parses if_true branch |
| `setting_value` | 306 | Returns `True_()` |
| Other types | ~3,000 | Returns `True_()` |

### Use Case

The `/explain <location>` command in the tracker (`worlds/tracker/TrackerClient.py:1743`) calls `access_rule.explain_json(state)` to show users why a location is accessible or blocked. For generated worlds, this currently shows incomplete or incorrect explanations.

## Design Goals

1. **Explain support** for all common AST format rule types
2. **Hybrid approach**: Rule Builder classes for boolean types, generic wrapper for complex types
3. **Helper evaluation** using generated Python functions, with explain support via embedded body data
4. **Minimal complexity**: Start with explain-only, defer full evaluation to future work
5. **Self-contained rules**: All data needed for evaluation/explain must be captured at generation time

## Design Constraints

### No Runtime Dependency on rules.json

**Important**: After world generation completes, we cannot assume access to the original `rules.json` file. All data needed for rule evaluation and explanation must be:

1. **Embedded in Rule Builder objects** at parse/generation time
2. **Generated as Python code** in the world's `Rules.py` file
3. **Stored on the world object** if needed for runtime access

This means:
- Helper function bodies must be either converted to Python code OR embedded in the rule structure
- Setting values must be resolved at instantiation time
- No lazy loading of rule definitions from external files

## Architecture

### Hybrid Approach

```
CC Format Rule (JSON)
        │
        ▼
┌───────────────────────────────────────┐
│         cc_format.py parser           │
├───────────────────────────────────────┤
│  Is rule type directly supported?     │
│                                       │
│  YES → Create native Rule Builder     │
│        class (Has, And, Compare, etc) │
│                                       │
│  NO  → Wrap in CCRule generic class   │
└───────────────────────────────────────┘
        │
        ▼
Rule Builder object with explain_json()
```

### Phase 4: Helper Function Support via HelperCall

The world generator already converts helper definitions from `rules.json` into Python functions in `Rules.py`. We leverage this with a tiered approach:

1. **Simple helpers**: Convert the body to a Rule Builder rule at generation time (best: full evaluation + explain)
2. **Complex helpers**: Use generated Python function for evaluation, AST format body for explain
3. **Fallback**: Just display the helper name

#### 4.1 HelperCall Rule Builder Class

```python
@dataclasses.dataclass()
class HelperCall(Rule[TWorld], game="Archipelago"):
    """Calls a helper function with explain support.

    This class supports three tiers of helper integration:
    1. body_rule set: Full Rule Builder evaluation and explain (best)
    2. helper_func + body_data set: Python evaluation, AST format explain
    3. helper_func only: Python evaluation, helper name display
    """
    helper_func: Callable[[CollectionState, int, ...], bool] | None = None  # Fallback Python function
    helper_name: str = ""                                                    # Name for display
    args: tuple[Any, ...] = ()                                               # Arguments to pass
    body_rule: Rule[TWorld] | None = None                                    # Rule Builder rule (if convertible)
    body_data: dict | None = None                                            # AST format for explain fallback

    @override
    def _instantiate(self, world: TWorld) -> Rule.Resolved:
        # Instantiate the body_rule if present
        resolved_body_rule = None
        if self.body_rule is not None:
            resolved_body_rule = self.body_rule._instantiate(world)

        return self.Resolved(
            self.helper_func,
            self.helper_name,
            self.args,
            resolved_body_rule,
            self.body_data,
            player=world.player,
            caching_enabled=False,  # Helpers may have complex dependencies
        )

    class Resolved(Rule.Resolved):
        helper_func: Callable | None
        helper_name: str
        args: tuple[Any, ...]
        body_rule: Rule.Resolved | None
        body_data: dict | None
        skip_cache: ClassVar[bool] = True

        @override
        def _evaluate(self, state: CollectionState) -> bool:
            # Tier 1: Use Rule Builder evaluation (preferred)
            if self.body_rule is not None:
                return self.body_rule(state)

            # Tier 2/3: Fall back to Python function
            if self.helper_func is not None:
                return self.helper_func(state, self.player, *self.args)

            # No evaluation available
            return True

        @override
        def explain_json(self, state: CollectionState | None = None) -> list[JSONMessagePart]:
            # Tier 1: Use Rule Builder explain (best - shows actual state)
            if self.body_rule is not None:
                return self.body_rule.explain_json(state)

            # Tier 2: Use AST format explain
            if self.body_data is not None:
                from rule_builder.cc_explain import explain_cc_rule
                return explain_cc_rule(self.body_data, state, self.player)

            # Tier 3: Fallback - just show helper name and args
            messages = [
                {"type": "text", "text": "Helper: "},
                {"type": "color", "color": "magenta", "text": self.helper_name},
            ]
            if self.args:
                args_str = ", ".join(repr(a) for a in self.args)
                messages.append({"type": "text", "text": f"({args_str})"})
            return messages
```

#### 4.2 Helper Body Conversion Strategy

The world generator attempts to convert helper bodies to Rule Builder rules at generation time:

```python
def _try_convert_helper_body_to_rule(body: dict, helper_params: list[str], args: list) -> Rule | None:
    """
    Try to convert a helper body to a Rule Builder rule.

    Returns None if the body contains unsupported constructs (loops, variables, etc.)
    """
    # Create parameter substitution map
    param_values = dict(zip(helper_params, args))

    # Check if body uses only supported rule types
    if _is_rule_builder_convertible(body):
        return _convert_cc_to_rule_builder(body, param_values)

    return None

def _is_rule_builder_convertible(rule: dict) -> bool:
    """Check if a AST format rule can be converted to Rule Builder."""
    convertible_types = {
        'constant', 'item_check', 'count_check', 'group_check',
        'and', 'or', 'not', 'can_reach', 'location_check',
        'can_reach_entrance', 'compare', 'conditional',
    }
    rule_type = rule.get('type', '')

    if rule_type not in convertible_types:
        return False

    # Recursively check nested rules
    for key in ['conditions', 'condition', 'left', 'right', 'test', 'if_true', 'if_false']:
        if key in rule:
            nested = rule[key]
            if isinstance(nested, list):
                if not all(_is_rule_builder_convertible(r) for r in nested):
                    return False
            elif isinstance(nested, dict) and 'type' in nested:
                if not _is_rule_builder_convertible(nested):
                    return False

    return True
```

#### 4.4 Benefits of Tiered Approach

| Tier | Evaluation | Explain | When Used |
|------|------------|---------|-----------|
| 1 | Rule Builder | Rule Builder (with state) | Simple helpers (item_check, and, or, etc.) |
| 2 | Rule Builder | Rule Builder (with state) | Parameterized simple helpers |
| 3 | Python function | AST format | Complex helpers (loops, variables) |
| 4 | Python function | Helper name only | Very complex / opaque helpers |

**Advantages of Tier 1/2 (Rule Builder):**
- Explain shows actual evaluation state (e.g., "Has Flippers: ✓" vs "Has Flippers: ✗")
- Potential for caching integration in the future
- Consistent with non-helper rules

**When to fall back to Tier 3/4:**
- Helper body contains loops (`for_range`, `for_iter`, `while`)
- Helper body contains variable assignments
- Helper body contains unsupported AST format types
- Helper body references external data structures

### Phase 5: CC Rule Explain Function

Create the comprehensive explain function:

```python
# rule_builder/cc_explain.py

def explain_cc_rule(
    rule: dict,
    state: CollectionState | None,
    player: int,
    depth: int = 0
) -> list[JSONMessagePart]:
    """Generate explain output for any AST format rule."""

    if depth > 50:
        return [{"type": "text", "text": "[max depth]"}]

    rule_type = rule.get('type', '')

    handlers = {
        'constant': _explain_constant,
        'item_check': _explain_item_check,
        'count_check': _explain_count_check,
        'group_check': _explain_group_check,
        'and': _explain_and,
        'or': _explain_or,
        'not': _explain_not,
        'compare': _explain_compare,
        'comparison': _explain_compare,
        'conditional': _explain_conditional,
        'helper': _explain_helper,
        'state_method': _explain_state_method,
        'setting_value': _explain_setting_value,
        'can_reach': _explain_can_reach,
        'region_check': _explain_region_check,
        'binary_op': _explain_binary_op,
        'sum': _explain_sum,
        'min': _explain_min,
        'max': _explain_max,
        'attribute': _explain_attribute,
        'subscript': _explain_subscript,
        'name': _explain_name,
        'function_call': _explain_function_call,
    }

    handler = handlers.get(rule_type)
    if handler:
        return handler(rule, state, player, depth)

    # Fallback for unknown types
    return [{"type": "text", "text": f"[{rule_type or 'unknown'}]"}]
```

## Future Enhancements

### Full Evaluation Support

Currently, this plan focuses on **explain-only** support. Future work could add full evaluation by:

1. **Port ruleEngine.js to Python** - Create `rule_builder/cc_evaluate.py` that mirrors the frontend's evaluation logic. This would be ~500-1000 lines of Python.

2. **Value-returning rules** - Add infrastructure for rules that return non-boolean values (counts, settings). This could use a parallel `get_value()` method alongside `_evaluate()`.

3. **Local scope support** - For evaluating helper bodies with parameters, add local variable scope tracking similar to the frontend's `localScope` parameter.

### Caching Integration

Currently, CCRule bypasses the Rule Builder caching system (`skip_cache = True`). Future optimization could:

1. **Analyze CC rules for dependencies** - Extract item/region dependencies from rule structure
2. **Integrate with existing caching** - Register dependencies like native Rule Builder classes
3. **Cache evaluation results** - Store computed values per state

### World Generator Updates

The world generator should be updated to emit Rule Builder classes with explain support. This is partially covered in Phase 4 (HelperCall), but could be extended to other rule types:

```python
# In rule_codegen.py
def _convert_compare(self, rule: Dict[str, Any]) -> str:
    # Instead of returning True_(), generate Compare class
    left = self._convert_rule(rule['left'])
    op = rule['op']
    right = self._convert_rule(rule['right'])
    self.required_imports.add('Compare')
    return f'Compare({left}, "{op}", {right})'

def _convert_helper(self, rule: Dict[str, Any]) -> str:
    # Generate HelperCall with embedded body data
    name = rule.get('name', '')
    args = rule.get('args', [])
    body = self._get_helper_body(name)  # From rules.json at generation time

    self.required_imports.add('HelperCall')
    func_name = f"_{self.game_name_lower}_{name}"
    args_str = ', '.join(self._convert_rule(a) for a in args)
    body_str = repr(body) if body else 'None'

    return f'HelperCall({func_name}, "{name}", ({args_str}), {body_str})'
```
