# Seedling JS save: "Use the save" (default off) and "Clear this room's save"

Slice `js-save-toggle-clear`. Launched and reviewed by `seedling-js-planning-21` (js-21).

## Summary for Robert

- **The checkbox: "Use the save".** The JS runtime's per-room save (RE2) is now behind a checkbox, **off by default**. Off means the save is neither read nor written. You find it in the Flash panel's **Settings** section, shown when the JS runtime is selected. It is the same setting as the Settings panel's `flashPanel.seedlingJsSave`.
- **The button: "Clear this room's save".** It sits under the checkbox and removes the stored save of the room that is loaded. Only that room's save goes; any other room's save stays. It works with the checkbox on or off, and the panel log says what it removed. If the save was being written, writing stops, so nothing puts the save back behind your click. The game in front of you keeps its progress until the room is loaded again.
- **The tutorials press the button first.** This covers every Seedling tutorial that can run on the JS runtime: the three Seedling tutorials that start the game (watch the bot, multiworld, whole game) and the three procgen tutorials that start Seedling, through their shared "start the game" steps. It also covers the two JS feature checks. On wasm, the step is skipped, because wasm has no JS save.
- **The Flash (Ruffle) save, `/shrumsave`, is not changed.** It has the same stale-save problem in a broader form: one save per site and SWF, shared by every room and seed. See *The `/shrumsave` finding*.

### Behaviour, stated

- **At the AP load** (`_startSeedlingRandomizer`, JS transport, load ok), `_bindJsSave` awaits the setting. After the await, it checks again that the adapter and the room are still the same.
  - **ON**: the RE2 binding, byte for byte. The previous binding is disposed with a flush, then `bindJsSave` reads, restores and writes as before. The glue re-reads its events after a restore, and the `pagehide` flush works as before.
  - **OFF**: no binding. There is no `getItem`, no `restoreSave` and no `onSaveChange` listener. The panel logs one line: `[js save] the save is off (Settings: "Use the save"): this room's save is neither read nor written`.
- **Switching OFF→ON mid-run** binds **write-only** from then on: the stored save is NOT read. Reading it now would rewind a game in progress. It is restored only at the **next AP load**.
- **Switching ON→OFF mid-run** unbinds and drops a pending write (`discard`). Nothing more is written, and the stored key is left as it was.
- **Only a change of the value acts.** A `settings:changed` with key `*` (a broadcast of every setting) cannot re-arm a binding that the Clear button stopped (`_jsSaveOn` is the value last applied).
- **Clear** removes `jsSaveKey(_mountKeyNow())` and nothing else. *This room* is the room the loaded rules mount: the one playing, or the one the next load will mount. A binding to that room is stopped first, **without writing**. I chose to dispose it rather than re-arm it: the run's memory still holds the progress, so a live binding would write it straight back on the next change. The next AP load binds again, if the save is on, and finds no save. With no rules loaded, the button says so and touches no storage.
  - **Confirmation.** The panel has no confirm dialog anywhere, so the button confirms the way the panel always does, in its log. It logs either `[js save] cleared this room's save (<key>)` or `[js save] this room had no save to clear (<key>)`. When a binding was stopped, it also logs `nothing more is written for this run … the next load of this room starts with no save`. The panel root's `data-js-save-clear` (`removed`, `none` or `error`) and `data-js-save-cleared-at` carry the same result for tutorial steps.

## The proofs

### OFF / ON (vitest, `seedlingJsSaveToggle.test.js`)

- *the setting: a boolean, default OFF*. Checks the schema prop `default: false` and `JS_SAVE_DEFAULT === false`. It also checks that index.js spreads the prop and that the panel's control row exists.
- *OFF: nothing is read and nothing is written*. It uses a counting storage that holds a save for the room. After two changes, the timers and a dispose, `storage.calls` is `[]`, `restoreSave` was never called, no listener is attached, and the log is the one line.
- *ON: exactly the RE2 binding*. The same scenario runs through `bindJsSave` directly and through `controller.load({on:true})`. It compares the storage call list, `restored`, the runtime state, the stored map, the pending timers and the restore calls; all are equal (`['get', 'set']`).
- *the AP load with the setting OFF binds nothing; ON binds and restores (glue re-read)*. This drives the panel's own `_bindJsSave` on a bare panel.
- *switched OFF mid-run* and *switched ON mid-run: write-only*. These check the two mid-run cases above.

### The button

- *Clear removes exactly this room's key*. The storage holds room A, room B, an unrelated key and another `seedlingJsSave_` key. Only `remove(room A)` is called, and the other three survive. A second click logs "had no save to clear".
- *no re-write after a Clear*. The save is ON and bound, with a write pending when Clear is pressed. After the timers run, another change and a dispose, there are zero `set` calls and the key is absent. The next `load` of the room finds no save.
- *Clear with a binding to ANOTHER room leaves that binding writing*.
- *a settings broadcast does not re-arm a binding the Clear button stopped; a real switch acts*. This drives the panel itself.
- *Clear with no rules loaded names that, and touches no storage*.

The step group is two steps:
1. Open the Flash Panel and note whether its Settings section is open. Done when the panel's runtime control has its value, which is when `data-applies` is settled.
2. Open Settings, only when the button applies (`:has(...)`, `optional`). Press the button: `optional` in a startSeedlingGame tutorial, so wasm skips it, and required in the checks. Then close Settings again if it was closed.

⚠ **Not rewound.** The step runs right after the world loads, before the game page loads it. If the Flash panel was already open with the JS runtime and the save ON, the AP load can race ahead of the step and restore the old save. The Clear then stops the writing and removes the key, but the game in front of the player keeps the restored progress, and the log says so ("restored from the save at this load"). With the default (off), nothing is ever restored, so this cannot happen.

## The `/shrumsave` finding (report only; nothing changed)

**Yes, it has the same stale-save problem, in a broader form.** This is a source read, not a runtime measurement: the Flash runtime plays `frontend/modules/flashPanel/swf/seedling_injected.swf`, which is not committed in this tree (the directory holds only its README).

- The key is Ruffle's SharedObject key: `<host>/<swf path>/shrumsave` (the Storage panel's pattern `/shrumsave$`; the census example is `localhost/frontend/modules/flashPanel/seedling.swf/shrumsave`). **Nothing in it names the room, seed or slot.** Every Flash-runtime game on one origin and SWF path shares one save.
- The game reads it at every boot: `Main.begin()` → `SharedObject.getLocal("shrumsave")` → `startSave()` (`vendor/seedling/src/Main.as:44`).
- The level-set guard (`LevelSet.as:595–662`) throws a save away when the delivered set's id differs (`freshSaveForLevelSet`). It is in the **vendor source build**, which is the wasm build. The injected SWF is the **original** game with the API injected (`swf/README.md`: `inject.py` on `598977_Seedling.swf`), so on the evidence here it has no such guard. On wasm the SharedObject is memory-only (flash.md RE2), so wasm has no stale save across reloads.
- The new checkbox and button cover only the JS save. A Flash player who switches presets keeps the previous game's progress unless they clear the key in the Storage panel.
