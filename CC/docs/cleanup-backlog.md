# Cleanup Backlog

Issues noticed while writing the official procgen documentation (2026-07-01) that are worth fixing but were out of scope for the docs work itself. Each entry has evidence and a suggested fix; none are urgent. Check items off (or delete entries) as they're resolved.

## Code

- [ ] **Duplicated loop-cost logic: `loops/costGenerator.js` ↔ `shared/procgen/loopCostGenerator.js`.** Two parallel implementations of the same algorithm, kept in sync only by a comment ("mirrors the runtime CostGenerator's behavior"). Concretely duplicated: the region-cost formula (`maxMana/2` split across uncosted path regions, floor, min 1), the location-cost formula (`Math.max(1, Math.floor(mana / 2))`), the sphere-log entry extraction (`_extractLocationEntries` vs `extractLocationEntries` — same filter, same items-credited-to-last-location rule, same phantom-entry creation), and the default-fill pass (`_assignDefaultCosts` vs `fillDefaults`). Real drift hazard.
  *Suggested fix:* extract the pure core (entry extraction, both formulas, default fill) into `shared/procgen/loopCostGenerator.js` and have `CostGenerator` import those helpers, keeping only its live-engine orchestration (event dispatch, snapshot waits, loop-state save/restore). Do **not** fold in `loopsCostDebugger/costPlanner.js` — its cost model diverges deliberately (XP levels, per-loop budgets, explore/check phases); at most add a header note there stating the divergence is intentional. `costDataManager.js` is fine as the shared store. Note the submodule boundary: `shared/procgen/` changes need a submodule commit + pointer bump.
- [ ] **Three separate BFS/path implementations in the cost family**: `loopCostGenerator.bfsRegions`, `costPlanner._findPath`, and `costGenerator` delegating to the shared `pathFinder.findPathWithExits`. Minor; worth consolidating only if the item above is done anyway.
- [ ] **`jtaCostDebugger` has its own `JTACostPlanner` "modeled after" `costPlanner.js`** — a third sibling in the planner family, copied rather than shared. Revisit if either planner needs a behavior change.
- [ ] **`substrateRegistry.js` header contract is incomplete.** The header documents identity/runtime/playback/loopSupport/build-time slots, but real entries carry more: `applyContentModules` (maze), `iframeId` (flash family), `victoryItem`, `zoneCount`/`synthesizeZonePayload`/`extractZoneRules` (zone-based), and bounce's entire sphere-growth adapter surface (`generateZoneForSpecs`, `exitGateVeto`, `buildRegionContract`, `prepareSphereGrowth`, …). The full contract is now documented in `docs/json/developer/procgen/substrate-registry.md`; the header should shrink to the core contract plus a pointer to that doc rather than trying (and failing) to be exhaustive. Submodule caveat applies.
- [ ] **`gridGrowth` is not marked deprecated in the pipeline panel.** The Mode toggle (`frontend/modules/procgenPipeline/procgenPipelineUI.js:653`) presents "Grid growth (build from a scenario pool)" as a peer of the others. Since it's deprecated in favor of sphere growth, the label should say so — docs alone won't stop someone selecting it.
- [ ] **`jta` `zoneCount: 16` is hand-synced** with the zone table in `iframe_games/journey-to-ascension/build/zones.js` (acknowledged in the entry's comment; drift is only caught by a runtime warning on `loadZone`). Consider generating or asserting it at build/test time.
